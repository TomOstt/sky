## Interpretation

_Assembled from the numbers above by the harness. The explanations name known mechanisms of each engine; they are not profiler output._

- **Against C -O3** (13 cases where both ran): Sky's best engine was faster in 4 and slower in 9; the geometric-mean ratio is 1.40x (Sky time / C -O3 time; range 0.33x to 7.49x).
- **Against Rust -O3** (13 cases where both ran): Sky's best engine was faster in 4 and slower in 9; the geometric-mean ratio is 1.32x (Sky time / Rust -O3 time; range 0.34x to 5.74x).
- **Against the BLAS/LAPACK library** (5 cases where both ran): Sky's best engine was faster in 0 and slower in 5; the geometric-mean ratio is 2.36x (Sky time / the BLAS/LAPACK library time; range 1.32x to 3.94x). Phase 4's target is within 2x of the hand-tuned library: met in 2 of 5.
- **Against CPython** (13 cases where both ran): Sky's best engine was faster in 13 and slower in 0; the geometric-mean ratio is 0.02x (Sky time / CPython time; range 0.00x to 0.09x).
- **Sky was faster than C -O3 on:** `matmul-64` (Sky ast, 0.92x), `matmul-256` (Sky ast, 0.53x), `matmul-512` (Sky ast, 0.33x), `cholesky-256` (Sky ast, 0.85x).
- **Sky was faster than Rust -O3 on:** `matmul-64` (Sky ast, 0.94x), `matmul-256` (Sky ast, 0.52x), `matmul-512` (Sky ast, 0.34x), `cholesky-256` (Sky ast, 0.75x).
- **Sky was faster than CPython on:** `nbody` (Sky auto, 0.06x), `matmul-64` (Sky ast, 0.01x), `matmul-256` (Sky ast, 0.00x), `matmul-512` (Sky ast, 0.00x), `cholesky-256` (Sky ast, 0.01x), `cholesky-32` (Sky ast, 0.02x), `elementwise-1e6` (Sky auto, 0.01x), `linear_chain-1e6` (Sky sir, 0.01x), `elementwise-1e7` (Sky sir, 0.03x), `linear_chain-1e7` (Sky sir, 0.03x), `mandelbrot` (Sky auto, 0.04x), `rk4` (Sky auto, 0.09x), `fib-30` (Sky native, 0.09x).
- Sky beat a compiled baseline on a Matmul workload (`matmul-64`). This harness cannot say why from the numbers alone; the likely candidates are that the C and Rust rows are plain source, not hand-vectorised or hand-blocked code, and that a fixed cost dominates a short run. - Sky beat a compiled baseline on a Cholesky workload (`cholesky-256`). This harness cannot say why from the numbers alone; the likely candidates are that the C and Rust rows are plain source, not hand-vectorised or hand-blocked code, and that a fixed cost dominates a short run. Check that cell's spread and the floors before trusting it.
- Why Sky beats CPython on SmallVector workloads (for example `nbody`): against CPython, which boxes every float and dispatches every operation, an interpreter that resolves types and units ahead of the run pays less per operation.
- Why Sky beats CPython on Matmul workloads (for example `matmul-64`): `@` runs as a compiled loop inside the runtime, so it is not paying interpreter overhead per multiply-add, unlike a pure-Python triple loop.
- Why Sky beats CPython on Cholesky workloads (for example `cholesky-256`): `K⁻¹ @ f` on a positive definite `K` is rewritten to a Cholesky solve (factor plus two triangular solves, about n^3/3 flops) instead of forming an inverse (about n^3): that is the same algorithm the C, Rust and library rows use, so against them it is parity of algorithm, not an edge; against code that forms the inverse it would save about a factor of 3 in flops, which this run did not measure.
- Why Sky beats CPython on ArrayChain workloads (for example `elementwise-1e6`): whole-array operations run in compiled Rust routines inside the interpreter, so on large arrays the interpreter overhead is amortised and Sky behaves like a native loop plus an allocation per operation, which beats a pure-Python loop by a wide margin.
- Why Sky beats CPython on Scalar workloads (for example `mandelbrot`): the compiled row it beat here is the interpreted one (CPython): Sky's engines run on unboxed `f64`s with types and units resolved before the run, while CPython boxes every float and dispatches every operation dynamically.
- Why Sky beats CPython on Calls workloads (for example `fib-30`): the compiled row it beat here is the interpreted one (CPython): Sky's engines run on unboxed `f64`s with types and units resolved before the run, while CPython boxes every float and dispatches every operation dynamically.
- **Largest gaps to compiled code (best Sky engine):** `nbody` (7.49x, against C -O3), `cholesky-32` (2.57x, against C -O3), `elementwise-1e7` (2.06x, against C -O3).
- Why Sky loses on SmallVector workloads (worst here: `nbody` at 7.49x): 2 and 3-element vectors in a loop: each vector operation allocates a small array and checks every element, where C and Rust keep the components in registers and unroll.
- Why Sky loses on Cholesky workloads (worst here: `cholesky-32` at 2.57x): Cholesky: an unblocked factorisation with finiteness checks, against a blocked LAPACK `dpotrf` on the library side.
- Why Sky loses on ArrayChain workloads (worst here: `elementwise-1e7` at 2.06x): elementwise chains: arrays are immutable, so an unfused operation allocates a new array and makes its own pass over memory (finiteness-checked), where C makes one fused pass; the `fuse` pass turns a chain into one kernel, but Sky's time here also includes building the inputs from outer products (`@`) and the front end's work on the large literals, which the C and Rust programs do not pay.
- Why Sky loses on Scalar workloads (worst here: `mandelbrot` at 1.57x): scalar-heavy loops: each operation is dispatched by an interpreter and its result checked to be finite (Sky never produces a silent inf or NaN), while a compiled loop keeps the values in registers; reproducible mode also forbids the fused multiply-add and reassociation that `-O3 -march=native`, and `-ffast-math` even more, are free to use.
- Why Sky loses on Calls workloads (worst here: `fib-30` at 1.36x): function-call-heavy code: every call is interpreted (argument passing, a frame, an overflow/finiteness check on each add), while C and Rust compile the recursion to a few instructions and LLVM rewrites part of it into a loop.
- **Engines:** `sir` was faster than `ast` in 7 of 13 cases (median sir/ast time ratio 0.87x).
- **Ratios are floor-limited** where the fastest baseline takes under 3x an empty process (1.45 ms): `matmul-256`. There the ratio measures start-up and the front end as much as the computation.
- **Assembly was not measured.** No hand-written assembly is part of this run; the vendor BLAS/LAPACK rows are the nearest measured proxy for hand-tuned code, and only for matmul and Cholesky. Nothing here supports or refutes a claim about assembly.
- **Different guarantees.** Sky results are finite-checked, unit-checked and bit-reproducible (no fused multiply-add, no reassociation); the C and Rust rows give none of that, and the `-ffast-math` row deliberately gives up more. Faster or slower here is not the same contract.
- **One machine, one run.** Medians of a handful of runs on a laptop-class machine; the spreads above say how noisy each cell was, and differences inside the spread mean nothing. Workload inputs are built from outer products (`COL @ ROW`, since arrays are immutable and Sky has no array constructor beyond literals, `zeros` and `identity`), which makes them dense but structured.
