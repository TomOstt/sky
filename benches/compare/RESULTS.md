## Method

- Each cell is a separate program run as a subprocess: 1 untimed warmup run(s), then 5 timed repetitions; the table shows the **median wall time** and, in parentheses, the **spread** (max - min) / median. A `†` marks a cell whose first run took more than 20 s and was measured once.
- Wall time includes process start-up and, for Sky, lexing, parsing, checking and lowering. The fixed part is in the floors below.
- All implementations build the same deterministic inputs and print the result on the last line; a cell whose numbers differ from the reference (the first implementation that ran, normally C) by more than the workload's relative tolerance is marked `!` and left out of every ratio.
- Sources: `benches/compare/{sky,c,rust,python,numpy,lib}`. Sizes are `--quick`-scalable; the report is only written for a full, unfiltered run.

## Interpretation

_Assembled from the numbers above by the harness. The explanations name known mechanisms of each engine; they are not profiler output._

- **Against C -O3** (11 cases where both ran): Sky's best engine was faster in 0 and slower in 11; the geometric-mean ratio is 23.8x (Sky time / C -O3 time; range 1.78x to 646x).
- **Against Rust -O3** (11 cases where both ran): Sky's best engine was faster in 0 and slower in 11; the geometric-mean ratio is 23.8x (Sky time / Rust -O3 time; range 1.65x to 681x).
- **Against the BLAS/LAPACK library** (5 cases where both ran): Sky's best engine was faster in 0 and slower in 5; the geometric-mean ratio is 11.8x (Sky time / the BLAS/LAPACK library time; range 3.81x to 42.7x). Phase 4's target is within 2x of the hand-tuned library: met in 0 of 5.
- **Against CPython** (11 cases where both ran): Sky's best engine was faster in 7 and slower in 4; the geometric-mean ratio is 0.26x (Sky time / CPython time; range 0.02x to 20.0x).
- **Sky was faster than CPython on:** `matmul-64` (Sky ast, 0.02x), `matmul-256` (Sky ast, 0.02x), `matmul-512` (Sky ast, 0.02x), `cholesky-256` (Sky ast, 0.03x), `cholesky-32` (Sky ast, 0.02x), `linear_chain-1e6` (Sky ast, 0.09x), `linear_chain-1e7` (Sky ast, 0.40x).
- **Sky did not beat compiled C, compiled Rust or the hand-tuned library on any workload in this run.** Any claim that it is faster than them is unsupported by these numbers.
- Why Sky beats CPython on Matmul workloads (for example `matmul-64`): `@` runs as a compiled loop inside the runtime, so it is not paying interpreter overhead per multiply-add, unlike a pure-Python triple loop.
- Why Sky beats CPython on Cholesky workloads (for example `cholesky-256`): `K⁻¹ @ f` on a positive definite `K` is rewritten to a Cholesky solve (factor plus two triangular solves, about n^3/3 flops) instead of forming an inverse (about n^3): that is the same algorithm the C, Rust and library rows use, so against them it is parity of algorithm, not an edge; against code that forms the inverse it would save about a factor of 3 in flops, which this run did not measure.
- Why Sky beats CPython on ArrayChain workloads (for example `linear_chain-1e6`): whole-array operations run in compiled Rust routines inside the interpreter, so on large arrays the interpreter overhead is amortised and Sky behaves like a native loop plus an allocation per operation, which beats a pure-Python loop by a wide margin.
- **Largest gaps to compiled code (best Sky engine):** `nbody` (646x, against C -O3), `mandelbrot` (533x, against C -O3), `fib-30` (167x, against C -O3).
- Why Sky loses on SmallVector workloads (worst here: `nbody` at 646x): 2 and 3-element vectors in a loop: each vector operation allocates a small array and checks every element, where C and Rust keep the components in registers and unroll.
- Why Sky loses on Scalar workloads (worst here: `mandelbrot` at 533x): scalar-heavy loops: each operation is dispatched by an interpreter and its result checked to be finite (Sky never produces a silent inf or NaN), while a compiled loop keeps the values in registers; reproducible mode also forbids the fused multiply-add and reassociation that `-O3 -march=native`, and `-ffast-math` even more, are free to use.
- Why Sky loses on Calls workloads (worst here: `fib-30` at 167x): function-call-heavy code: every call is interpreted (argument passing, a frame, an overflow/finiteness check on each add), while C and Rust compile the recursion to a few instructions and LLVM rewrites part of it into a loop.
- Why Sky loses on ArrayChain workloads (worst here: `linear_chain-1e7` at 23.8x): elementwise chains: arrays are immutable, so each operation allocates a new array and makes its own pass over memory (finiteness-checked), where C makes one fused pass; fused kernels are Phase 4 work and only count here once the run shows them.
- Why Sky loses on Matmul workloads (worst here: `matmul-512` at 6.29x): dense matmul: Sky's `@` is a plain loop inside the interpreter's runtime, not a cache-blocked SIMD kernel, so it trails vectorised C and is far behind a vendor BLAS.
- Why Sky loses on Cholesky workloads (worst here: `cholesky-32` at 2.74x): Cholesky: an unblocked factorisation with finiteness checks, against a blocked LAPACK `dpotrf` on the library side.
- **Engines:** `sir` was faster than `ast` in 1 of 10 cases (median sir/ast time ratio 3.02x).
- Engines not present in this build, so not measured: native.
- **7 cell(s) did not run** (see Notes): Sky rejects or cannot yet execute those programs, so nothing is claimed about them.
- **Ratios are floor-limited** where the fastest baseline takes under 3x an empty process (4.52 ms): `nbody`, `matmul-64`, `matmul-256`, `matmul-512`, `cholesky-256`, `cholesky-32`, `linear_chain-1e6`, `rk4`, `fib-30`. There the ratio measures start-up and the front end as much as the computation.
- **Fixed cost of Sky's engines:** an empty program (`print(1)`) takes 15.7 ms on the fastest engine but far longer on `sir` (216 ms), `auto` (210 ms). That start-up cost is paid on every run and is included in every Sky number above, so it decides the short cases.
- **Assembly was not measured.** No hand-written assembly is part of this run; the vendor BLAS/LAPACK rows are the nearest measured proxy for hand-tuned code, and only for matmul and Cholesky. Nothing here supports or refutes a claim about assembly.
- **Different guarantees.** Sky results are finite-checked, unit-checked and bit-reproducible (no fused multiply-add, no reassociation); the C and Rust rows give none of that, and the `-ffast-math` row deliberately gives up more. Faster or slower here is not the same contract.
- **One machine, one run.** Medians of a handful of runs on a laptop-class machine; the spreads above say how noisy each cell was, and differences inside the spread mean nothing. Workload inputs are built from outer products so Sky can express them (arrays are immutable and have no elementwise product or math functions yet), which makes them dense but structured.
