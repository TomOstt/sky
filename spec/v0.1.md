# Sky v0.1: first release spec

Status: approved by Tom on 2026-09-29. Owner: Product Manager. Date: 2026-09-29.

## Goal
Prove Sky's core bet: units, tensor shapes, and matrix properties can be checked together, before anything runs, in a language that reads like Python. v0.1 is a checker plus an interpreter. It is not fast yet, and that is deliberate.

## Who it's for
Physicists, engineers, and scientific-ML developers who have shipped a unit or shape bug and would rather have the compiler catch it. The first users are us and a handful of early testers. We have no user data yet, so we will validate that this pain is real in early interviews rather than assume it.

## Why pick Sky over Julia + Unitful + ModelingToolkit
Julia checks units and shapes when code is compiled for specific argument types or when it runs, and each concern lives in a separate package. Sky checks units, symbolic shapes, and matrix properties in one static pass over the whole program, with a single set of error messages, before any data exists. v0.1 will not compete with Julia on speed or ecosystem, so the pitch for this release is correctness only.

## In scope
- Syntax: indentation-based, Python-like functions, `if`/`elif`/`else`, `while`, `for`, and bindings. Every Unicode operator (`∂`, `⁻¹`, `ᵀ`, `ħ`, `±`) has an ASCII spelling (`inv(A)`, `transpose(A)`, `+/-`). `±` (ASCII `+/-`) writes an uncertainty (see "Uncertainty"); the ASCII `+-` is just `+` followed by unary `-`.
- Identifiers must be in Unicode NFKC form (Normalization Form KC, Unicode 18.0.0). A non-NFKC identifier, such as `e` followed by U+0301 instead of `é`, `ﬁ`, fullwidth `ｘ`, mathematical `𝑥`, or MICRO SIGN `µ`, is an error. It is never silently normalized, and keywords match only their exact ASCII spelling.
- An identifier may have at most 30 combining marks in a row (the Unicode stream-safe limit, UAX #15: characters with a nonzero canonical combining class, counted in each character's full compatibility decomposition, so U+0344 counts as two). A 31st mark in a row is an error at that mark.
- Units: the seven SI base units (m, s, g, K, A, mol, cd), derived units (J, N, Pa, W, Hz, C, V, Ω, F, T, Wb, H, S, rad, L, t), the angle unit deg, SI prefixes (`km`, `ms`, `μm`, `GeV`), the non-SI units min, h, day, yr, ly, pc, AU, eV, and physical constants (`c`, `h`, `ħ`, ...) as predefined names. A unit may follow only a numeric literal (`10 km`). `5 meters + 20 kelvin` is a compile error.
- Shapes: `Matrix[M, N]` and `Tensor[...]` with symbolic dimension variables solved by equality. `Matrix[3,4] @ Matrix[4,8]` gives `Matrix[3,8]`, and a mismatch is a compile error.
- Matrix properties: tags such as Symmetric, PositiveDefinite, Diagonal, and Orthogonal, arranged in a subtyping lattice. `A⁻¹ @ b` is a solve whose algorithm the compiler chooses from the tags (Cholesky for a positive-definite `A`, LU for any square one), an unparenthesized `@` chain is associated by the compiler, and `sky check --explain` shows each choice with its estimated flops (see "Algorithm choice").
- Tools: `sky check`, `sky run` (SIR, with the tree-walking interpreter as the fallback and the oracle), and `sky repl` (tree-walking interpreter). Diagnostics include source spans, in the format defined in [`spec/diagnostics.md`](diagnostics.md).

### Operator precedence
The placement of `and`, `or`, and `not` is signed off by Eng Lead (2026-09-29). From loosest to tightest:

| level | operators | associativity |
|---|---|---|
| -1 | `v as unit` | none: covers the whole expression, and nothing may follow it (see "Showing values in a unit") |
| 0 | `a if c else b` | right (in the `else` arm); the condition `c` is an `or` expression |
| 1 | `or` | left |
| 2 | `and` | left |
| 3 | `not x` | prefix |
| 4 | `==` `!=` `<` `<=` `>` `>=` (also `≠` `≤` `≥`) | none: `a < b < c` is an error |
| 5 | `+` `-` `±` (`+/-`) | left (`±` is the uncertainty operator, see "Uncertainty") |
| 6 | `*` `/` `@` | left |
| 7 | `-x` `+x` `∂x` `∇x` | prefix |
| 8 | `^` | right; its right operand may be a prefix expression (`2^-1`) |
| 9 | `A⁻¹`, `Aᵀ`, `f(x)`, `M[i, j]`, `x.name` | postfix |

An array literal `[a, b]` is an atom (see "Array literals"), so it takes postfix forms: `[1, 2][0]`.

#### Unicode operators and their ASCII spellings
Every Unicode operator has an ASCII spelling, and it is a function call, never new punctuation (the one exception is the infix `±`, whose ASCII spelling is `+/-`, see "Uncertainty"), so the ASCII program needs no extra grammar and the same rules hold: a user function of that name shadows the builtin, and a wrong argument count is an error on the call.

| operator | glyph | ASCII | meaning |
|---|---|---|---|
| inverse | `A⁻¹` (U+207B U+00B9) | `inv(A)` | the reciprocal of a number, the inverse of a square matrix |
| transpose | `Aᵀ` (U+1D40) | `transpose(A)` | swaps the two axes of a matrix |
| uncertainty | `x ± dx` (U+00B1) | `x +/- dx` | the value `x` with a standard uncertainty `dx`; infix, level 5 (see "Uncertainty") |

- **Transpose.** `Aᵀ` is a postfix operator at the same level as `⁻¹` (level 9), so `Aᵀ @ A` is `(Aᵀ) @ A`, `-Aᵀ` is `-(Aᵀ)`, `Aᵀ^2` is `(Aᵀ)^2`, and `(A @ B)ᵀ` needs its parentheses; `Aᵀᵀ` and `A⁻¹ᵀ` chain. `Matrix[m, n]ᵀ` is `Matrix[n, m]`; the dimension is unchanged (entries only move); the tags are `tags::preserved_by_transpose`, which keeps every tag (Symmetric, PositiveDefinite, Diagonal and Orthogonal all hold for the transpose). A number is its own transpose (`5 mᵀ` is `5 m`). A **vector has no transpose**: v0.1 vectors have no row or column orientation (`@` accepts a vector on either side, and `u @ v` is the dot product), so `vᵀ` as the identity would make an outer product written `v @ vᵀ` silently compute a dot product. `vᵀ`, and the transpose of a Bool or of a rank-3 array, is an error whose help points at `u @ v` and at the matrix literals `[[1, 2, 3]]` and `[[1], [2], [3]]`. There is no `.T` spelling: `.name` is attribute syntax (reserved), and `T` is also the tesla, so a function is the unambiguous ASCII form. The shape debugger's help ("the shapes would match if the right operand were transposed") names the syntax.
- **The glyph is not NFKC-stable, on purpose, like `⁻¹`.** U+1D40 MODIFIER LETTER CAPITAL T is a letter whose NFKC form is a plain `T`, so a tool that normalizes source would turn `Aᵀ` into the name `AT` (and `A⁻¹` into `A−1`); the lexer never normalizes. It is excluded from identifiers, so `Aᵀ` is the name `A` followed by the operator, not one identifier (an identifier containing U+1D40 was already an error, being non-NFKC). Look-alikes `⊤` (U+22A4) and `⊺` (U+22BA) are lexer errors that name the right glyph; `ᵗ` (U+1D57) is a non-NFKC identifier character and gets the ordinary NFKC error. Where the glyph is hard to type or a pipeline may normalize it, use `transpose(A)`.

- `as` is a keyword too (`v as km/h`, see "Showing values in a unit"). `and`, `or`, and `not` are keywords. As with every keyword, they may still be used as an attribute name after `.` (`x.and`).
- `and` and `or` short-circuit: operands are evaluated left to right, and evaluation stops at the first operand that decides the result.
- `not a < b` is `not (a < b)`, `a < b and b < c` needs no parentheses, and `a and b or c` is `(a and b) or c`.
- `not` cannot be the operand of a tighter operator: `-not x`, `a < not b`, and `2^not x` are errors; write `-(not x)`.
- `&&`, `||`, and `!` are not operators. The lexer rejects `&`, `|`, and a `!` that isn't part of `!=`, and suggests `and`, `or`, and `not`.
- `-x^2` is `-(x^2)`.
- The conditional expression `a if c else b` (level 0) is looser than `or`, so `a or b if c else d` is `(a or b) if c else d`. Its `else` arm may be another conditional (`a if c else b if d else e` is `a if c else (b if d else e)`), but its condition may not: `a if b if c else d else e` needs parentheses. Anywhere a tighter operator wants an operand, a conditional needs parentheses: `(a if c else b) + 1`. Only the chosen arm is evaluated at run time. The checker types every part.

#### Booleans and conditions
Signed off by Eng Lead (2026-09-29).
- `true` and `false` are the Bool literals. They are keywords, so they can't be assigned to, but they may be attribute names after `.`. A unit may not follow them (`true m` is a parse error). `True` and `False` are ordinary names.
- The operands of `and`, `or`, and `not` must be `Bool` of shape `()` (a scalar), and the result is `Bool`. The same rule applies to the conditions of `if`, `while`, and conditional expressions.
- v0.1 has no truthiness. `0 m`, empty containers, and tensors are never implicitly true or false.
- A non-Bool or non-scalar operand is a checker error on that operand's span. For a scalar quantity, the help suggests a comparison such as `x != 0 m`. For a tensor, the help says that a condition must be a single `Bool` (shape `()`).
- At run time, `and` and `or` evaluate left to right and stop early. The checker still types every operand, so `true or (3 m + 2 s)` is a check error.

### Statements and assignment
The simple statement forms the parser accepts (a statement ends at a newline; blocks are in "Blocks and control flow" below):

```text
statement   := expr
             | target "=" expr
             | target compound_op expr
             | NAME ":" type [ "=" expr ]          (see "Type annotations")
             | "accuracy" NAME "within" tolerance   (see "Accuracy budgets")
             | "cost" MEASURE ( "<=" | "==" ) bound  (only in a def header: see "Performance contracts")
target      := NAME
             | postfix "[" index_item ( "," index_item )* [ "," ] "]"
             | postfix "." ( NAME | KEYWORD )
compound_op := "+=" | "-=" | "*=" | "/=" | "^=" | "@="
index_item  := expr | [ expr ] ":" [ expr ]
```

- `x op= e` rebinds `x` to `x op e`, evaluating the target once; the result must have `x`'s declared type (unit, shape, tags) or it is a check error. `+=`, `-=`, `*=`, `/=`, `^=`, `@=` stand for `+`, `-`, `*`, `/`, `^`, `@`. There is no compound form for comparisons or `and`/`or`, and `**=` is an error (Sky writes powers as `^`, so use `^=`).
- Only a name can be annotated: `a.b: T = 1` and `A[0]: T = 1` are parse errors.
- Any other target is a parse error on the target: `f(x) = 1`, `(x) = 1`, `1 = x`, `a + b += 1`, and `true = 1`.
- Assignments don't chain: `a = b = c` and `x += y += z` are parse errors.
- Slices select a range along one axis: `A[0, :]` is row 0, `A[1:3]` is rows 1 and 2, and `A[:n, 2:]` leaves out a bound. A slice has no step: `A[1:2:3]` is a parse error. The same index items are allowed when reading and as a target.
- **The parser accepts index and attribute targets, but the v0.1 checker rejects writes through them.** Index writes (`A[i, j] = x`, `A[0, :] = v`) are check errors: that is the v0.1 checker's behaviour while array immutability is pending Tom's confirmation (see Open questions), not a settled language rule. Attribute writes (`a.b = x`, `x.true = 1`) are check errors too, until there is something whose attributes can be assigned.

### Blocks and control flow
Python-style blocks. The tokens (`Indent`, `Dedent`) come from the lexer's indentation rules; this section is the grammar on top of them and what the checker does with it.

```text
statement   := simple_stmt | if_stmt | while_stmt | for_stmt | def_stmt
simple_stmt := (the forms in "Statements and assignment")
             | "return" [ expr ]
             | "assert" expr [ "," STRING ]                (see "Contracts")
             | "pass" | "break" | "continue"
if_stmt     := "if" expr ":" block { "elif" expr ":" block } [ "else" ":" block ]
while_stmt  := "while" expr ":" block
for_stmt    := "for" NAME "in" expr ":" block
def_stmt    := "def" NAME "(" [ param { "," param } [ "," ] ] ")" [ "->" type ] ":" block
               (a block may start with `requires` and `ensures` lines, see "Contracts")
param       := NAME [ ":" type ]
block       := NEWLINE INDENT statement+ DEDENT
expr        := or_expr | or_expr "if" or_expr "else" expr        (level 0)
```

**Layout**
- A block is a line ending in `:`, then one or more lines indented further than the header, all at the same indentation; the first line back at the header's indentation (or the end of the file) ends it. Blocks nest. Blank lines and comment-only lines never end a block.
- **The body goes on its own indented line.** `if x: y = 1` is a parse error, with the help "put the body on its own indented line". Python allows it; Sky doesn't. With one canonical layout, spans, diffs and error recovery stay simple, a statement has one way to be written, and the `:` of a header can't be mistaken for the `:` of an annotation (`y: Matrix[3, 3] = ...`). The parser still reads the statement after the `:` as the body, so one mistake gives one error.
- **An empty block is an error**, with the help "use `pass`": `pass` is the statement that does nothing.
- `elif` and `else` must follow the block of an `if`/`elif` at the same indentation. `else if` is an error ("write `elif`"), and so is an `else` or `elif` with no `if` before it.
- Blocks count toward the nesting limit (256 levels) together with expressions: a block is one level, like a parenthesis. 257 nested `if`s are one clean error ("blocks are nested too deeply"), never a stack overflow, and the rest of that block is skipped.
- Not supported yet, each a precise error: `import` statements (there is no module loader wired into the language yet), and default parameter values (`def f(x=1)`). `field` is reserved for a future version (`equation` and `solve` are statements, see "Differential equations"). `assert`, `requires` and `ensures` are reserved words of "Contracts".
- A bad line does not desynchronize the blocks around it. After an error the parser resumes at the next line; a block header with an error still has its body read (and its errors reported), so the `Dedent` that ends the body is consumed by the right block.

**Conditions**
- The condition of `if`, `elif`, `while`, and of a conditional expression must be a `Bool` of shape `()` (see "Booleans and conditions": no truthiness). The diagnostic and its help are those of `and`/`or`/`not` operands, on the condition's span: "compare it instead, e.g. `x != 0 m`".
- Both arms of `a if c else b` must have the same dimension and shape, and the tags are joined (only the tags both arms guarantee survive). Otherwise it is an error on the `else` arm, with the `if` arm as a secondary label. Shapes are compared after substituting solved size variables; the check never unifies them (see below).

**Scoping**
- `if`, `while` and `for` bodies share the enclosing scope, as in Python. A `def` opens a new scope: its parameters and everything it assigns are local to it and disappear when the body ends.
- After an `if`, the states of the branches that can fall through are merged. A branch that ends in `return`, `break`, or `continue` (or in an `if`/`else` whose branches all do) does not fall through and takes no part. An `if` without `else` counts "no branch ran" as one more state.
  - A name bound in every state with the same type keeps that type. "Same" is the same dimension and shape; tags are joined.
  - A name bound in every state with different types is an error at the later binding: "`x` is a length here but a time in the other branch", with the earlier binding as a secondary label.
  - A name bound in only some states is *maybe-defined*: using it afterwards is an error, "`x` may be undefined here", with a secondary label at a binding and the help "assign it before the `if`". It is reported once per name.
- A `while` loop's condition and body are checked from the state before the loop, with each name's tags joined with the tags it has at the end of the body and at each `continue`, since those are what the next iteration starts from: after `Q = 2 * Q` in the body, `Q` is no longer Orthogonal at the top of it, so a `Q⁻¹ @ b` there is not rewritten to `Qᵀ @ b`. The checker finds these tags by checking the body again until they stop changing; only the last check's diagnostics and rewrites count. A loop nested in another, or one that has not settled after a few checks, drops the tags of every name its body assigns instead, which is sound and needs one more check. What follows the loop merges every way out: the condition failing (before the first iteration, or after the body or a `continue`) and each `break`. A loop whose condition is the literal `true` can only be left by `break`. A name bound only inside the body is maybe-defined afterwards ("assign it before the loop"), and a name the body rebinds with a different dimension or shape than it had on entry is a conflict, as above.
- `break` and `continue` are errors outside a `while` or `for` of the same function (a `def` inside a loop does not inherit it). `return` is an error outside a `def`.

**`for` loops**

```text
for i in range(n):            # 0, 1, ..., n-1
for i in range(a, b):         # a, a+1, ..., b-1
for i in range(a, b, step):   # a, a+step, ... while short of b (past b if step < 0)
for x in v:                   # the entries of a vector; the rows of a matrix
```

- **`range`.** `range(n)` is `range(0, n)`, and `range(a, b)` has step 1. The bounds and the step are dimensionless integers, so `range(3 m)` and `range(2.5)` are errors (a constant is rejected by the checker, a computed one by the interpreter, "`range` needs an integer, found 2.5"). A bound or step may be at most 2^53 in size, the largest integer an `f64` holds exactly, so that `i + step` never stalls. A step of zero is an error ("the step of `range` cannot be zero"). A negative step counts down (`range(10, 0, -3)` is 10, 7, 4, 1). The bounds are evaluated once, before the loop, left to right, so changing `n` inside the body does not change how often it runs. An empty range (`range(0)`, `range(5, 2)`) runs the body zero times.
- **`range` is not a value.** It is recognised only as the whole iterable of a `for` (`x = range(3)` is an error that says so), because Sky has no lazy sequences and no lists: a `range` that could be stored would need a type to be stored as. A user binding named `range` shadows it, as `print` and `inv` are shadowed.
- **The loop index is a dimensionless scalar.** It is an ordinary number that happens to be an integer, so `v[i]` and `A[i, j]` accept it with no conversion (an index is any dimensionless scalar; see "Arrays: indexing, builtins and operations"), and `x = (i + 0.5) * dx` is dimensionally sound when `dx` has a unit.
- **`for x in v`** over a vector gives the entries, each a scalar with `v`'s element dimension (`for f in forces` gives forces if `forces` is a `Vector` of forces). Over a matrix it gives the **rows**, each a `Vector` of the matrix's element dimension and no tags. Rows are what `A[i]` gives, so `for r in A` is `for i in range(len(A))` with `r = A[i]`; that is also Python's and NumPy's meaning, it needs no new notion of iteration order over two axes, and it composes (`for r in A: for x in r:` visits every entry, row-major). Going one entry at a time needs no special form: write the nested loop. The iterable is evaluated once, and arrays are immutable, so the loop cannot see its own changes.
- **What cannot be iterated.** A scalar, a Bool and a string are errors, each with a help ("cannot iterate over a dimensionless number", with "to repeat something that many times, write `for i in range(n):`"). The checker does not type strings, so it rejects a string literal in the header and the interpreter rejects a string held in a variable at run time.
- **`break` and `continue`** work as in `while`: `break` leaves the innermost loop, `continue` goes on to the next item.
- **A `for` is a `while` over an index**, and scoping is `while`'s: the body shares the enclosing scope and is checked as a `while` body is (from the state before the loop, with the tags of the next iteration joined in), and the loop variable stays bound after the loop (as in Python), with the last value it had, including after a `break`. Rebinding the variable inside the body does not change the iteration.
- **Zero iterations.** A `while` may never run, so a name bound only in its body is maybe-defined afterwards. A `for` keeps that rule where the loop might not run and drops it where it must:
  - over an array the body runs at least once (arrays are never empty in v0.1), so the loop variable and every name the body binds are defined afterwards, unless a `break` or `continue` skips their binding;
  - over a `range` whose arguments are all integer constants (`range(3)`, `range(2, 9, 3)`, `range(5, 0, -1)`) with at least one item, the same;
  - over any other `range` (`range(n)`, and empty constant ranges such as `range(0)`) it may not run, so the loop variable and the names the body binds are maybe-defined afterwards: "`i` may be undefined here", "assign it before the loop". A variable bound before the loop keeps its value when the loop does not run.
  Where the loop is known to run, a variable bound before it with another dimension or shape is simply replaced; where it may not, the two states are merged and a different type is a conflict, as for `while`.
- **Errors in the header** are reported once, and the loop is then treated as running, so one mistake does not produce "may be undefined" errors after it.

**Shape variables across branches and functions**
- Shape variables are solved by one constraint set for the whole module, and scopes never snapshot it. A constraint learned in a branch stays afterwards: a size variable names one size for the module, so `N = 3` learned in one branch is a fact about `N`, not about that path.
- Merges never unify. Two branches that leave a name with different shapes (after substituting solved variables) are a conflict, not a new constraint that neither branch wrote.
- A `def`'s size variables are its own: `N` in its annotations is not the module's `N`. After the body is checked, the variables its signature still leaves open are generic, and each call gets fresh copies, so `def apply(A: Matrix[N, N], b: Vector[N]) -> Vector[N]` can be called with size 3 and then size 4. A body that pins a variable (returning a `Vector[N]` where `Vector[3]` is declared) makes the function specific to that size.

**Functions**
- Parameter and return annotations use the same type grammar as bindings (see Type annotations): `def kinetic(m: kg, v: m/s) -> J`. An annotated parameter has the annotation's shape, tags and unit. An argument's shape must unify with it and its dimension must be equal. Its tags are taken on trust and verified where the body uses them (a Cholesky or diagonal solve checks its operand), except Orthogonal, which is never verified (see "Algorithm choice"): an argument for an Orthogonal parameter must be known to be Orthogonal, from a declaration, `identity(n)`, or a product or negation of Orthogonal matrices (`` `Q` of `f` must be Orthogonal, but `A` is not known to be Orthogonal ``). An argument whose type is unknown is not checked. An annotation with no unit (`Vector[3]`) is dimensionless, the convention of a binding annotation without a value. Leave a parameter unannotated to accept any unit. An unannotated parameter is unknown inside the body: nothing is checked against it and there is no error (Python-like). Duplicate parameter names are an error.
- The return type is the declared `-> T` when there is one: every `return` must have a value of that shape, and of that unit's dimension if `T` names one ("expected energy, found mass"); without a unit, the dimension is the one the returned values agree on. Without `-> T`, the type is inferred from the `return`s, which must all give the same type (dimension and shape, tags joined), or it is an error at the later one. Mixing `return value` with a bare `return` is an error. A function that returns a value on some path but can finish without returning on another is an error at its name ("can finish without returning a value"). A function with no `return value` at all returns nothing, and a call to it is unknown.
- A call checks arity ("`f` takes 2 arguments, found 3") and each argument against its annotated parameter (shape, then dimension), and has the function's return type. Calling something that is not a function is an error. A call whose return type is unknown (unannotated parameters flowing into it) is unknown, and an unknown value is never an error by itself.
- A function's own name is in scope in its body (recursion). A recursive call is checked for arity and annotated arguments, and its result is unknown.
- **Names in a body.** A body is checked where it is defined, against the names bound so far. (Python looks names up at call time; Sky checks them at definition time, so a function that calls a helper needs the helper defined above it. The error says so: "a function body sees only names defined above its `def`".) Assigning to a name inside a function binds a new local and never changes an outer name. `x += 1` on a name that belongs to an enclosing scope is an error (Python fails it at run time with `UnboundLocalError`), with the help to bind a new name.
- **Calls bind where the caller is defined (early, lexical binding).** A call inside a function body, of a name that is not a local of that body, refers to the definition of that name that was in scope at the caller's `def`: the function of that name, or the built-in if the name was not bound then. A later `def` of the same name, a `def` that shadows a built-in (`def max` after a function that calls `max`), or a rebinding to a non-function (`f = 5` after a `def g` that calls `f`) does not change what `g` calls. The function's own name is bound to itself, so a redefined recursive function recurses into its new self while functions defined before keep the old one. A call at the top level of the file uses the binding current at that point, as every other name does. Variables are not affected: a function still reads a module variable as it is when the function runs (a name that is not called is looked up when the body runs, in the function's locals and then the module). Its *type* cannot change, though: the body was checked once, with the type the name had at the `def`, so a later module-level binding of a name some function reads must keep that type, the same dimension and shape and at least its tags (a rewrite in the body, `Q⁻¹` to `Qᵀ` for an Orthogonal `Q`, may rely on one). Anything else is an error on the rebinding, with the read as a label: "`kk` cannot become a length: `rate` reads it as a frequency", "`Q` cannot lose its tags: `solveq` reads it as ...". Without it, `return kk` in a `-> Hz` function would return metres after `kk = 2 m`, and `Q = 2 * Q` would make `solveq` return `Qᵀ @ b` for a `Q` that is no longer orthogonal. The way out is a new name, or a parameter. The reason is soundness: the checker types a call against the signature it sees at the `def`, with its units and shapes. If a later redefinition, possibly with other units, could change the callee at run time (Python's late binding), a checked body would run against a function it was never checked against, and the units the checker guaranteed would silently not hold. Early binding makes the function the checker typed the function that runs, in `sky run` and in the SIR lowering alike.
- **Limits of the SIR lowering (`sky check --emit-ir`).** Two programs that `sky run` runs have no SIR; the lowering says so with a note, and `sky run` runs them with the tree-walker. A function defined in more than one arm of an `if` (or otherwise not one `def` at the call) cannot be called after it: a call in SIR names one function fixed at compile time, and SIR has no function values. A nested `def` that reads a local of its enclosing function is refused whole ("cannot find `a` in this scope"), also when the inner function is never called; `sky run` gives the inner function no access to the enclosing locals either (there are no closures) and fails only if it runs. These are design limits of v0.1, not errors in the program.
- A user function named `inv` shadows the built-in `inv(x)`; without one, `inv(x)` is `x⁻¹` as before.
- The checker never runs user code: bodies are typed, not executed (Security non-negotiable 1).

### Contracts
A scientific invariant is code, not a comment: the program states what must hold, and `sky run` stops, saying what was false and what the values were, when it does not. There are three forms. `assert` is a statement anywhere. `requires` and `ensures` are the lines a function starts with, its precondition and its postcondition (ROADMAP ideas 3, 29 and 81). `conserve` (a conserved quantity of an ODE) belongs to `equation`/`solve` and is not part of this section.

```text
assert_stmt   := "assert" expr [ "," STRING ]
contract_line := ( "requires" | "ensures" ) expr [ "," STRING ]
def_stmt      := "def" NAME "(" ... ")" [ "->" type ] ":" NEWLINE INDENT { contract_line NEWLINE } statement+ DEDENT
```

```sky
def fall_time(h: m) -> s:
    requires h >= 0 m
    ensures result > 0 s
    return sqrt(2 * h / g_n)

E = kinetic(m, v)
assert E > 0 J, "energy must be positive"
```

`assert`, `requires` and `ensures` are reserved words, like `def` (no edition has shipped yet, so 2026 reserves them; see "Editions"). `result` is an ordinary name except inside `ensures`, below. The message after the comma is a string literal; there is no other form of it (no formatting: the values are shown for you).

**The condition.** It is checked like the condition of an `if` (see "Booleans and conditions"): a `Bool` of shape `()`, no truthiness, and the dimensions of its comparisons are checked as usual, so `requires h >= 0` on a length is an error ("cannot compare length and dimensionless"). A condition the checker cannot type (it calls a function with unannotated parameters) is checked when it runs: anything but a Bool is a runtime error, "`assert` needs a Bool condition, found a number".

**`assert cond`** is a statement. Where it runs, `cond` is evaluated; if it is false the run stops with an error on the condition's span (exit status 1, output before it stays, as for every runtime error):

```text
error: assertion failed: `E > 0 J` (E = -3.2 J)
error: assertion failed: energy must be positive (`E > 0 J`, E = -3.2 J)
```

**The message** is built from the condition as written (white space collapsed to single spaces; capped and escaped like any quoted source text) and the values of **every name the condition reads**, once each, in order of first appearance, written as Sky source in SI (`x = [1 m, 2 m]`, `s = "a"`, `pi = 3.141592653589793`). The name of a called function is not a value and is not shown. The values are those where the contract is checked; names the evaluation never reached (`false and x > 0`) are shown too, because the point is what the state was, not what the evaluation happened to touch. A value longer than the usual cap is cut with `…`, and an array of more than 16 entries is shown by its shape and unit (`v = Vector[300] m`), so a message never costs the size of the data. With the author's message it leads: `assertion failed: energy must be positive (`E > 0 J`, E = -3.2 J)`.

**Function contracts.**
- **Placement.** `requires` and `ensures` lines come first in the body of a `def`, before every other statement (a docstring's place). Anywhere else they are parse errors ("`requires` is only allowed at the start of a function body"). A function may have any number of each, and a nested `def` has its own.
- **`requires cond`** is a precondition. It is checked when the function is called: the arguments are evaluated in the caller, the function's frame is made, and the `requires` lines run in the order written, before any statement of the body. Its scope is the parameters and the names the body sees anyway (the module's names above the `def`, the constants). A failure is an error on the condition (which lies in the callee) and a secondary label "called here" on the call, and reads `precondition of `fall_time` failed: `h >= 0 m` (h = -1 m)`. The blame is the caller's.
- **`ensures cond`** is a postcondition. It is checked when the function returns: at every `return`, and at the end of a body that falls off its end (a function with no value). It sees the **parameters as they were passed** (a body that reassigns `x` does not change what `ensures` sees) and **`result`**, the returned value, typed as the function's return type. It does not see the body's other locals: a postcondition states what a call promises, not how the body does it. `result` inside `ensures` is always the returned value, so a parameter called `result` in a function with an `ensures` is an error ("rename the parameter"); in `requires` and everywhere else `result` is an ordinary name (using it in `requires` when nothing by that name exists is an error that says `result` belongs to `ensures`). A function that returns no value has no `result`: an `ensures` that names it is an error; one that talks about the arguments is fine. A failure reads `postcondition of `fall_time` failed: `result > 0 s` (result = 0 s)` and is an error on the condition.
- **Order.** If the body fails (division by zero, a failed `assert`), that error is the one reported and the `ensures` lines do not run. Each call of a recursive function checks its own contracts.
- **Contracts are not switched off.** There is no flag that disables them: a run that passes them is the run the author reasoned about. A contract the compiler proves needs no check (below), and costs nothing.

**What the checker says.** The checker never runs user code, so it knows a contract's truth only where it is arithmetic on numbers the source spells out (literals with units, `+ - * /`, comparisons, `and`, `or`, `not`, the same `f64` arithmetic the interpreter does, with a division by zero or an overflow making it "unknown"). Two warnings, never errors (the checker does not know whether the line runs, and warnings do not fail a check):
- a contract whose condition is such an expression and false: "this `assert` always fails: `1 m > 2 m` is false" (and "this `requires` can never hold", "this `ensures` can never hold");
- a call whose arguments are all constants (`fall_time(-5 m)`, `f(-(2 m))`) of a function with a `requires` that the arguments make false: "this call breaks the precondition of `fall_time`", with the `requires` as a secondary label and the values.

**What SIR proves (`--explain`).** After lowering, the `contracts` pass removes every check it can prove true, and says so:

```text
prog.sky:2:14: note: [CONTRACT-002] this `requires` always holds, so its check is removed: `h >= 0 m`
  = note: applied by the `contracts` pass
  = note: because in every call of `fall_time` in this program, `h` is between 5 and 20
  = note: because the left side of the `>=` is between 5 and 20 and the right side is 0, so it cannot be false
```

It uses the exactness analysis (`sky_ir::exact`): every scalar has an enclosure (an interval that contains every `f64` the interpreter can compute for it), and a comparison is decided only if it is the same for every value in the enclosures (`a >= b` when the least `a` is at least the greatest `b`); `not`, `and` and `or` follow. The enclosure of a function's parameter is the hull, over **every call of the function in the module**, of the enclosure of the argument, computed in the caller without assuming anything about the caller's own parameters (so recursion needs no fixed point: `f(n - 1)` inside `f` passes "any finite number", and a `requires n >= 0` keeps its check). A function that is never called gets no facts, and neither does a parameter of unknown type or an array. So `fall_time(20 m)` as the only call discharges `requires h >= 0 m`, and, through the square root, `ensures result > 0 s` too; add a second call with `0 m` and the postcondition stays (the result may be zero), and one with `-1 m` and the precondition stays. `assert 2 m > 1 m` is discharged where it stands. A discharged check is only removed: the operations that compute the condition stay (until dead-code elimination proves them infallible), so a condition that fails to compute still fails, and the program's output, errors and their order are the same as with the check. The rule ids are `CONTRACT-001` (`assert`), `CONTRACT-002` (`requires`) and `CONTRACT-003` (`ensures`). What is not proven keeps its check; the analysis does not know the results of calls, array entries, or anything about values of unknown type.

**Both engines.** The tree-walker evaluates contracts as described. SIR has one operation for all three, `assert[kind] "text" [fn "name"] [msg "message"] names("a", ...) %cond, %a, ...`, with effect `Fail` (so no pass moves or removes it, except `contracts` when it proves it): its operands are the condition and the values of the names, its attributes the condition's text, the author's message and the function's name, and it fails with the same message and on the same span as the tree-walker (both build them with `sky_interp::contract`). A `requires` is lowered as the first operations of the function; an `ensures` just before its `return`, in the scope the function started with plus `result`. `derivative(f, x)` of a function keeps its contracts: the derivative function checks them on the primal values. `sky run --engine=sir` prints the tree-walker's diagnostic for a failed contract (with the "called here" label), as for every runtime error ("Engines").

**Not in v0.1.** Loop invariants, `old(x)` (the value of an expression at entry; `ensures` sees the arguments as passed, which covers the common case), quantifiers, contracts on a module, `conserve`, and an option to log a violation and go on. Performance contracts (`cost flops <= 2 * N^3`) are a separate kind, checked by `sky check` and not by a run: see "Performance contracts".

### Unit literals
Signed off by Eng Lead (2026-09-29). A unit literal is a numeric literal followed by a unit. `~` below means the two tokens touch, with no whitespace between them.

```text
unit_literal := NUMBER unit                  (whitespace required between NUMBER and unit)
unit         := factor ( ~("*" | "/")~ factor )*
factor       := NAME ( ~"^"~ exponent )?
exponent     := [ "-"~ ] INT
              | "("~ [ "-"~ ] INT ~"/"~ INT ~")"
```

- A unit may follow only a numeric literal, separated from it by whitespace (`10km` is rejected by the lexer: "put a space before the unit"). Unit names are ordinary names; a name is a unit only when it directly follows a number.
- `*`, `/`, and `^` are part of the unit only when there is no whitespace on either side. A spaced `*` or `/` is an ordinary operator on the quantity. A `^` right after a unit with whitespace on either side (`10 m ^2`, `10 m^ 2`, `10 m ^ 2`) is a parse error: write `10 m^2` for a power of the unit or `(10 m)^2` for a power of the quantity. For `*` and `/` the spacing never changes the value, because `(10 km)/h` equals `10 km/h`. For `^` it does (10 m² vs 100 m²) and the dimension is the same, so the checker couldn't catch the difference.
- Compound units use `*`, never juxtaposition. `*` and `/` group left to right, and `^` binds tighter.
- An exponent is a signed integer or a parenthesized rational. The denominator must not be zero. The numerator must fit in a signed 64-bit integer and the denominator in an unsigned 64-bit integer.

#### Units and prefixes
- Base units: `m`, `s`, `g`, `K`, `A`, `mol`, `cd`. `kg` is kilo + gram and is the coherent SI unit (scale exactly 1).
- Derived: `J`, `N`, `Pa`, `W`, `Hz`, `C`, `V`, `Ω` (ASCII `ohm`), `F`, `T` (tesla), `Wb`, `H`, `S`, `rad`, `L` (litre, exactly 10⁻³ m³), `t` (tonne, exactly 10³ kg). Other units: `deg` (degree of arc, π/180 rad; dimensionless, so `sin(30 deg)` works and `180 deg` is π), `min` (60 s), `h` (hour, 3600 s), `day` (86 400 s), `yr` (Julian year, 365.25 d), `ly` (light-year, c × 1 yr), `pc` (IAU 2015), `AU` (IAU 2012), `eV` (exact, 2019 SI). Factors follow the SI Brochure, 9th edition, and IAU 2012/2015.
- Prefixes: `q r y z a f p n μ m c d da h k M G T P E Z Y R Q` (quecto to quetta). ASCII `u` is an alias for `μ` (the MICRO SIGN `µ` U+00B5 is not NFKC and is a lexer error; use `μ` U+03BC or `u`). Prefixes attach only to `m s g K A mol cd J N Pa W Hz C V Ω F T Wb H S rad L t yr ly pc eV`; `min`, `h`, `day`, `AU` and `deg` take none (`kmin` and `kdeg` are errors).
- Resolution: an exact unit name always wins over prefix + unit. Otherwise the name splits into one prefix and a prefixable unit. Consequences: `min` is the minute; `h` is the hour and `hPa` is hectopascal; `pc` is the parsec (`Mpc` mega-parsec); `Pa` is the pascal; `cd` is the candela (there is no unit `d`; write `day`); `ms`, `mm`, `nm` are milli/nano + unit; `T` is the tesla and also tera (`TT`, `mT`), and `t` is the tonne (`kt`); `da` is deca (`dam`) and `day` is the day; `Gyr` is giga-year and `Gy` is not a unit (the checker suggests `Gyr`). Full names such as `meters` or `micrometer` are not units; the checker suggests the symbol.
- Spellings are case-sensitive, and lookup is a pure function of the text: no unit is ever guessed.

#### Physical constants
Constants are values with a dimension, not units. They are predefined names in scope (the checker's prelude), so `E = 2 kg * c^2` is energy, and `10 c` is an error (a unit follows only a number; write `10 * c`). Values are CODATA 2018 in SI; the SI defining constants are exact.

| name | ASCII | meaning |
|------|-------|---------|
| `c` | | speed of light, exact |
| `h` | | Planck constant, exact |
| `ħ` (U+0127) | `hbar` | reduced Planck constant |
| `k_B` | | Boltzmann constant, exact |
| `N_A` | | Avogadro constant, exact |
| `q_e` | | elementary charge, exact |
| `G` | | gravitational constant |
| `ε0` | `eps0` | vacuum permittivity |
| `μ0` | `mu0` | vacuum permeability |
| `m_e`, `m_p`, `m_n`, `m_u` | | electron, proton, neutron, atomic mass |
| `σ_SB` | `sigma_SB` | Stefan-Boltzmann constant |
| `g_n` | | standard gravity, exact |
| `π` (U+03C0) | `pi` | the circle constant, dimensionless (see "Math functions") |

- The elementary charge is `q_e`, not `e`: `e` is the natural name for Euler's number and a common variable (eccentricity, error). `σ_SB` is not bare `σ`, which is a standard deviation or cross section in most programs. `ε0` and `μ0` are written without subscripts because a subscript zero is not NFKC (`ε₀` normalises to `ε0`, so it is a lexer error); `ℏ` U+210F is likewise not NFKC, so `ħ` is U+0127.
- A program may rebind a constant (`h = 0.1 s`), as with a Python builtin. The first rebinding of each name is a warning ("`h` shadows the Planck constant"), not an error. A size variable in an annotation may share a name with a constant that was not rebound.
- The hour `h` and the constant `h` never clash: units appear only after a number, constants only as names.
- `check_module_with` starts from the caller's environment as given; only `Env::with_prelude()` (used by `check_module` and so `sky check`) adds the constants.

Examples: `10 km`, `9.8 m/s^2`, `kg*m/s^2`, `3 s^-2`, `m^(1/2)`, `m^(-3/2)`.

Counter-examples:
- `10 km / 30 min` is `(10 km) / (30 min)`, and `10 m / t` is `(10 m) / t`: spaced `/` divides the quantity.
- `5 kg m` is a parse error; write `5 kg*m`.
- `x km` is a parse error, because a unit must follow a numeric literal; write `x * km`.
- `10 km` written as `10km` is a lexer error.
- `10 m/2`, `3 s^x`, and `1 m^(1/0)` are parse errors.
- `10 m ^2`, `10 m^ 2`, and `10 m ^ 2` are parse errors (ambiguous `^` after a unit); write `10 m^2` or `(10 m)^2`.

### Math functions
Built-in functions, checked for dimensions like everything else. A number goes in and a number comes out. **An array goes in and an array of the same shape comes out**, the function applied to each entry with the rule below applied to the entries' dimension (`sqrt(v)` of a `Vector[3]` of areas is a `Vector[3]` of lengths); see "Arrays: entry by entry". The rules live in one table, `sky_units::MathFn`, shared by the checker, the interpreter and the IR.

| function | arguments | result dimension |
|----------|-----------|------------------|
| `sqrt(x)` | any dimension | every exponent halved: `m²` gives `m`, `m` gives `m^(1/2)` |
| `cbrt(x)` | any dimension | every exponent divided by 3: `m³` gives `m` |
| `abs(x)` | any dimension | the same dimension |
| `exp(x)`, `log(x)`, `log10(x)`, `log2(x)` | dimensionless | dimensionless |
| `sin(x)`, `cos(x)`, `tan(x)` | dimensionless (an angle) | dimensionless |
| `asin(x)`, `acos(x)`, `atan(x)` | dimensionless | dimensionless |
| `atan2(y, x)` | `y` and `x` share a dimension | dimensionless |
| `hypot(a, b)` | `a` and `b` share a dimension | that dimension |
| `min(a, b)`, `max(a, b)` | `a` and `b` share a dimension | that dimension |
| `floor(x)`, `ceil(x)`, `round(x)` | dimensionless | dimensionless |
| `expm1(x)`, `log1p(x)` | dimensionless | dimensionless |
| `sinh(x)`, `cosh(x)`, `tanh(x)` | dimensionless | dimensionless |
| `asinh(x)`, `acosh(x)`, `atanh(x)` | dimensionless | dimensionless |
| `erf(x)` | dimensionless | dimensionless |
| `sign(x)` | any dimension | dimensionless: -1, 0 or 1 |

- `rad` and `deg` are dimensionless units, so `sin(30 rad)` and `sin(30 deg)` work (`30 deg` is stored as 30π/180, so `sin(30 deg)` is `0.49999999999999994`, correct to the last digit of an `f64`), and `omega * t` with `omega: Hz` is dimensionless (`Hz` is `T⁻¹`), so `cos(omega * t)` works. `log(3 m)` has no answer in any unit (`log 3 + log m`), and `exp(3 m)` would add a length to a length squared, so both are errors; divide by a reference: `exp(x / (1 m))`.
- `floor`, `ceil` and `round` reject a dimension on purpose. Values are stored in SI, so `round(1.5 km)` would round 1500 m, while a reader thinking in kilometres expects 2: the result depends on a display unit Sky does not keep. Say the unit: `round(x / (1 km))`.
- `expm1(x)` is `exp(x) - 1` and `log1p(x)` is `log(1 + x)`, computed without the cancellation those forms suffer for small `x` (see "Catastrophic cancellation"). `erf` is the error function, `2/√π ∫₀ˣ exp(-t²) dt`; the standard library has none, so Sky computes it from the series A&S 7.1.6 below 1 and the continued fraction A&S 7.1.14 (as `1 - erfc`) from 1 up, to within about 1e-15 relative (mean under one ulp; measured against the C library's `erf`).
- `sign(x)` keeps no dimension: the sign of `-3 m` is the pure number `-1`, so `abs(x) * sign(x)` is `x`. It is the one math function that takes any dimension and returns a dimensionless number. `sign(0)` and `sign(-0)` are `0`.
- `round` is half away from zero (`round(2.5)` is 3, `round(-2.5)` is -3). A result of `-0` is `0`.
- At run time results are finite, like arithmetic (see "Arithmetic"). A domain error is a runtime error on the call, never `NaN`: `sqrt` of a negative number, `log`, `log10`, `log2` of zero or a negative number, `asin`/`acos` outside [-1, 1], `atan2(0, 0)`, `log1p` of -1 or less, `acosh` below 1, `atanh` at or outside ±1. A result too large for a 64-bit float (`exp(1000)`, `expm1(1000)`, `sinh(1000)`, `cosh(1000)`) is an overflow error; a result too small (`exp(-1000)`) is `0`.
- `pi` and `π` (U+03C0) are dimensionless constants in the prelude (the constants table above), so `2 * pi * r` is a length when `r` is. They are prelude constants, not literals: rebinding `pi` is a warning, as for `c`. `e` is not defined (see `q_e` above); write `exp(1)`.
- A user binding or `def` named like a builtin (`sqrt = 4`, `def max(a, b)`) shadows it in the checker and at run time, exactly as for `print` and `inv`.
- A wrong argument count, or a Bool or function argument, is an error naming the expected call.
- **Arrays.** The one-argument functions take a vector or a matrix and apply to every entry: `sqrt(v)`, `exp(v)`, `sin(v)`, `abs(A)`. The two-argument functions (`atan2`, `hypot`, `min`, `max`) take two arrays of **one shape**, or an array and a number (the number is every entry): `max(v, 0 m)`, `atan2(y, x)`. `hypot(x, y)` of two arrays is entry by entry, not a norm (`norm(v)` is the length of a vector). Arrays of different shapes are an error ("cannot apply `atan2` to Vector[3] and Vector[4]"), because there is no broadcasting between arrays. A domain error or an overflow at any entry is the scalar function's runtime error on the call ("`sqrt` of a negative number has no real value"), reported once, for the lowest entry that fails; the message does not name the entry, exactly like an overflow in `v + w`.

### Derivatives
`derivative(f, x)` is the derivative of the function `f` with respect to its parameter `x`. It is a function with the parameters of `f`, so it is called like `f`, and it gives a value with the unit a derivative has:

```sky
def position(t: s) -> m:
    return 5 m/s^2 * t^2

v = derivative(position, t)(2 s)        # 20 m/s
```

```text
derivative_call := "derivative" "(" NAME "," NAME ")" "(" [ expr { "," expr } ] ")"
                 | "(" "∂" NAME "/" "∂" NAME ")" "(" [ expr { "," expr } ] ")"
gradient_call   := "grad" "(" NAME ")" "(" [ expr { "," expr } ] ")"
```

`(∂f/∂t)(args)` is another way to write `derivative(f, t)(args)`, and `grad(f)(args)` is the gradient; both are described at the end of this section.

- **`f` is a function defined with `def`**, named as any function is. **`x` is the name of one of its parameters.** It is a bare name, not a value: it is not looked up in the scope of the call (`t` above need not exist there), and a position (`derivative(position, 0)`) is not accepted, because every parameter has a name and one way to say it reads better. The other parameters of `f` are constants for this derivative.
- **It is called where it is written.** The arguments are those of `f`, in order, and are checked as a call of `f` is (arity, shape, and the dimension of every annotated parameter); the value is the derivative at those arguments, evaluated left to right in the caller. `derivative(position, t)(3 s)` reads as f′(3 s), and `derivative(spring, k)(0.1 m, 200 N/m)` passes both arguments of `spring`, whichever one is differentiated.
- **Type.** The dimension is `dim(result of f) / dim(x)`; the shape is that of whichever of `x` and the result is an array (see "Arrays" below), and scalar when both are. The derivative of a position with respect to time is a velocity, the derivative of an energy with respect to a length is a force, and `derivative(position, t)(2 s) + position(2 s)` is the same unit error as adding a velocity to a length ("cannot add length and velocity", with the help that they differ by a factor of time). Assigning it to an annotated name checks the unit like any value (`v: m/s = ...`).
- **Not a value.** Sky has no function values in SIR, so `derivative(f, x)` can only be called at once: `d = derivative(f, x)`, passing it, or returning it is an error ("must be called where it is written"). To name a derivative, define it: `def v(t: s) -> m/s: return derivative(position, t)(t)`. That also gives higher derivatives: `derivative(v, t)(2 s)` is the second derivative, 10 m/s² for the position above. The first argument must be a `def`, not another `derivative(...)`, for the same reason.
- **Why this form.** It fits what the language has: the callee is known when the program is checked, exactly like a `def` (so lowering and the interpreter resolve it without function values), the call syntax is the one people already read as f′(args), and the ordinary call rules check the arguments and type the result. When function values arrive, `d = derivative(f, x)` followed by `d(3 s)` will work without changing anything written today. Rejected: `derivative(f, x, at: 3 s)` (Sky has no keyword arguments, and with several parameters "at" would have to be all of them); `derivative(f, x, 3 s)` (which arguments follow, and who is `x`, when `f` takes two?); `d = derivative(f, x)` (needs function values).
- **Errors**, each with the fix in its help: a wrong number of arguments; a first argument that is not a `def` (a built-in such as `sqrt`, a number, another derivative; wrap a built-in in a `def` that states its units); a second argument that is not a parameter of `f` (the message lists its parameters); a parameter without a unit annotation (its dimension is unknown, so the derivative's unit cannot be computed; this applies to every parameter of `f`, since the derivative flows through all of them, and a Bool parameter cannot be annotated, so a function with one cannot be differentiated yet); `x` an array (a `Vector` or `Matrix`) while the result is an array too (a Jacobian, which Sky does not have; see "Arrays"); a result whose unit is not known (no `-> unit` and nothing to infer it from, or a Bool or nothing).
- **Meaning.** The derivative is exact (automatic differentiation, not a finite difference), through arithmetic, powers, the math functions, arrays, `if`, `while`, calls and recursion. At a kink the slope of the side that runs is used: `abs` takes the right-hand slope at 0, `min` and `max` the slope of their first operand when the operands are equal, an `if` differentiates the arm that runs, and `floor`, `ceil`, `round` and `sign` have slope 0. Where the derivative is infinite the run fails like any other arithmetic: the derivative of `sqrt(a)` at 0 (or of `acosh` at 1, `atanh` at ±1) is a runtime error ("division by zero"), never `inf`.
- **How it runs.** The derivative is a program transformation of the function's SIR (`sky-ad`), which types every tangent as `dim(value) / dim(x)`. SIR lowering calls the derivative function it builds; `sky run` lowers the program's `def`s (only those) to SIR on the first derivative, builds the same function and runs it with the SIR reference interpreter on the values the tree walker holds, so both engines print the same bytes and there is one set of differentiation rules. The file's other top-level statements are not lowered, so a derivative works in a program whose top level SIR cannot express yet: `-grad(U)(r)` can be the right side of an `equation` (see "Differential equations"), and a program may use `±` outside the functions it differentiates. A `def` SIR cannot express (one that `solve`s, say) is left out, with every `def` that calls it, so it does not stop the derivative of a function that never reaches it; the derivative of one that does is a runtime error that names the calls leading there and points at what stopped it ("`twice` calls `drop`, which cannot run on SIR: differential equations are not supported by SIR yet", with the `solve` labelled). One consequence: a function the transformation cannot handle (an unannotated parameter deep in a callee, or a gradient through a loop over an array whose size is not known, say) is a runtime error on the derivative call, because `sky check` never lowers.
- **Arrays.** Differentiation goes through vectors and matrices (indexing, slices, literals, `+`, `-`, scaling, `@`, transpose, `inv` and `A⁻¹ @ b`, the elementwise kernels the optimiser fuses), and the derivative takes the shape of the array involved:

  | `x` | `f` | `derivative(f, x)` |
  |---|---|---|
  | scalar | scalar | a scalar, `dim(f)/dim(x)` |
  | scalar | `Vector[n]` or `Matrix[m, n]` | an array of `f`'s shape: `derivative(position, t)(2 s)` for a position vector is a velocity `Vector[3] m/s` |
  | `Vector[n]` or `Matrix[m, n]` | scalar | an array of `x`'s shape: the **gradient** of `f`, `dim(f)/dim(x)` per entry |
  | `Vector`/`Matrix` | `Vector`/`Matrix` | an error: it would be a Jacobian (an entry for every result and every entry of `x`), which Sky has no type for |

  `derivative(f, p)` for a vector `p` is the gradient rather than a directional derivative because it needs no second argument and has the physical reading (the force is `-derivative(U, p)(p)`); the derivative of a scalar function along a direction `v` is `derivative(f, p)(p) @ v`, which `@` already writes. Only `p` is differentiated: other array parameters are constants, and `p` may have any of the shapes above, not only three entries.
#### `∂f/∂t`
- **`(∂f/∂t)(args)` is `derivative(f, t)(args)`.** `(∂position/∂t)(2 s)` reads like the physics it is, and gives the same value, type, errors and code. It is sugar for the call form only, and needs both names bare: `∂` and a name on each side of the `/`, `f` a `def` and `t` a parameter of it, all checked as for `derivative` (a name that is not a `def`, or not a parameter, is the same error, and a `∂x/∂t` whose `x` is a number is an error that says Sky has no dependent variables).
- **Why it is unambiguous now.** The parser does not change: `∂` is a prefix operator that binds tighter than `/`, so `∂f/∂t` has always parsed as the division of two prefix nodes, `(/ (∂ f) (∂ t))`. `∂` has no other meaning (it was a runtime "not supported"), so the checker, the interpreter and lowering read that exact shape, a quotient of `∂name` and `∂name`, as a derivative when it is the callee of a call. Nothing that meant something before changes meaning, and a program never gets two readings.
- **What is not accepted, and why.** A call and a power bind tighter than `∂`, so `∂f/∂t(2 s)` is `∂f / ∂(t(2 s))` and `∂f/∂t^2` is `∂f / ∂(t^2)`: neither is the form. The first is a check error that says so and shows the fix, `(∂f/∂t)(2 s)`; the parentheses are required. `∂f/∂t` on its own is a function, so it is the same "must be called where it is written" error as `derivative(f, t)`. There is no `∂²f/∂t²` (write a `def` for the first derivative, as above) and no partial derivatives of an expression: `∂` names a function and one of its parameters, as `derivative` does. The earlier objection (that physicists mean the rate of change of a quantity that depends on another) is kept as the error for `∂x/∂t` with a number `x`, rather than a reason to leave the notation out.
- **`∇` stays reserved.** `∇f` would be `grad(f)`, but `(∇f)(args)` gains nothing over `grad(f)(args)`, so it is not added.

#### Gradients
- **`grad(f)(args)` is the gradient of a scalar function**: either of scalar parameters, giving the derivative with respect to every parameter, in parameter order, as a `Vector[n]`; or of *one* array parameter, giving the gradient with respect to it, an array of its shape. `f` is a `def`, and the arguments are those of `f`, as for `derivative`.

```sky
k = 3 N/m
def U(x: m, y: m) -> J:
    return k * (x^2 + y^2)

F: Vector[2] N = -grad(U)(1 m, 2 m)     # [-6 N, -12 N]
```

- **The rule.** A Vector has one element unit, but ∂f/∂xᵢ has dimension `dim(f) / dim(xᵢ)`. So `grad(f)` of scalar parameters is allowed when **all the parameters have the same dimension** (not necessarily the same unit: `km` and `m` are both lengths), and it is then a `Vector[n]` whose entries have dimension `dim(f) / dim(x)`: the gradient of an energy in lengths is a force, and of a scalar field in lengths is the field's unit per metre. When the dimensions differ, it is a check error, "its parameters have different units", that marks each parameter with its dimension, names the quantities the derivatives would be ("force and power"), and suggests the way out: `derivative(f, x)(...)` for each parameter, which has its own unit. There is no mixed-unit vector and no silent conversion; a gradient over a length and a time is not a vector in any physical sense.
- **The gradient of a potential of a position vector.** The physically common case, a potential of a position vector, is one array parameter, and its gradient is a force with the vector's shape:

```sky
M = 5.972e24 kg
mass = 1000 kg

def U(p: Vector[3] m) -> J:
    return -G * M * mass / norm(p)          # G is the constant of gravitation

p = [7000 km, 0 km, 0 km]
F: Vector[3] N = -grad(U)(p)                # [-8134.47 N, 0 N, 0 N]: toward the origin
```

  `grad(f)` of a function of a single `Vector[n]` or `Matrix[m, n]` parameter has the parameter's shape and the unit `dim(f) / dim(p)` per entry, and is `derivative(f, p)(...)` (see "Arrays" above). A spring network is `0.5 * (d @ (K @ d))` with a stiffness matrix `K`, whose gradient `K d` is the force on each node.
- **Other errors** (each with its fix in the help): not exactly one argument; an argument that is not a `def` (as for `derivative`); a function without parameters; a parameter without a unit annotation; a result that is not a scalar number with a known unit (an array-valued function has a Jacobian, not a gradient); and an array parameter next to other parameters, which has no single vector to gather them in: name the array, `derivative(f, p)(...)`.
- **How it runs.** For scalar parameters it is forward mode, one derivative per parameter, all from the same `sky-ad` transformation as `derivative`: the arguments are evaluated once, left to right, `df/dxᵢ` is called for each parameter with them, and the derivatives are gathered in an array. The cost is `n` runs of `f` (with `f`'s prints, if it prints, `n` times). For an array parameter it is **reverse mode**: `f` runs once forward and the derivative propagates backwards through it in one sweep, however many entries the array has (the cost is a small multiple of one run of `f`, not `n` runs). Reverse mode handles straight-line code, `if`, arrays and calls; a helper that takes or returns arrays is inlined, so the gradient goes through it. A loop that carries a value the gradient depends on has no tape to run backwards over, so it falls back to forward mode, one pass per entry (the array's size must then be known and at most 256: `Vector[3]`, not `Vector[N]`), which prints once per entry. Both engines run either the same way, so they print the same bytes.
- **Not a value.** Like `derivative(f, x)`, `grad(f)` can only be called where it is written; `g = grad(f)` is the same error, and `grad` of a `derivative` or of another `grad` is too (name it with a `def`). A `def` that calls `grad` can be called, run and differentiated: `def Fx(p: Vector[3] m) -> N: return grad(U)(p)[0]` and `grad(Fx)(p)` is a row of the Hessian, in `N/m`.

### Powers of quantities
- In `x^e` with a unit on `x`, the exponent `e` must be a constant number: an integer literal, a decimal literal, or a quotient of them, optionally negated or parenthesized (`(3 m)^2`, `(3 m)^-1`, `(3 m)^(1/2)`, `(3 m)^0.5`). Anything else is the error "the exponent must be a constant number".
- A decimal literal means exactly the fraction its text spells, never a float: `0.5` is 1/2, `1.5` is 3/2, `0.25` is 1/4, `2.0` is 2, `0.1` is 1/10. It is read from the source text and reduced. Exponent forms (`1e-1`) and literals whose numerator or denominator does not fit in a signed 64-bit integer are not constants.

### Unit values
- Types carry dimensions only. `km` and `m` are both the length dimension; there is no separate type per unit.
- Each unit has an `f64` factor to the coherent SI unit of its dimension (`km` is 1000, `min` is 60; a prefixed unit's factor is the prefix's power of ten times the unit's, exact when the unit's factor is itself a power of ten). The unit table in `sky-units` is the only place these factors live.
- A unit literal is converted to SI once, at the literal: `10 ms` is the value `0.01` with dimension time. After that no value remembers its unit, so `1 km + 1 m` is length plus length (the value `1001`), and there is no rule for mixing scales.
- A converted value is an ordinary `f64`, so arithmetic on it rounds like any float. `100 ms` is stored as `0.1`, and `3 * (100 ms)` is `0.30000000000000004`, so `3 * (100 ms) == 0.3 s` is false. Compare quantities with a tolerance, as with any float.
- Values print in SI units: `10 ms` prints as `0.01 s`. To print in a chosen unit such as `km` or `ms`, use `as`: `print(10 ms as ms)` (see "Showing values in a unit").
- Offset units such as `°C` and `°F` (a unit that needs an added offset, not just a factor) are out of scope for v0.1. Temperature is written in `K`.

### Showing values in a unit
`v as unit` writes a value in a unit of your choice. Values are stored and printed in SI (see "Unit values"), so `print(90 km/h)` prints `25 m/s`; to see it as people read it, write `print(90 km/h as km/h)`, or `print(v as km/h)` for a variable.

```text
show := expr "as" unit          (unit is the unit-literal grammar; `~` is touching, as there)
```

```sky
v = 90 km/h
print(v)                    # 25 m/s
print(v as km/h)            # 90 km/h
print(1 AU as km)           # 149597870.7 km
print(511 keV as MeV)       # 0.511 MeV
print(u as mm)              # [100 mm, 200 mm]
v as km/h                   # in the REPL: echoes 90 km/h
```

**Why `as`.** The candidates were `v as km/h`, `v.to(km/h)`, `convert(v, km/h)` and `v in km/h`. `as` reads as the sentence ("print v as km/h") and puts the unit after the value exactly where a unit goes after a number (`10 km/h`), so the unit needs no brackets and is the same grammar as a unit literal. `v.to(km/h)` and `convert(v, km/h)` put a unit where an expression is expected, and `km/h` there reads as the quotient of two names; Sky has no methods either. `v in km/h` reads well, but `in` belongs to `for` loops and to Python's membership test, where `x in y` is a Bool. `as` is a keyword. It may still be an attribute name after `.` (`x.as`), like every keyword. It is reserved before any release, so no existing program changes meaning.

**Precedence.** `as` is the loosest construct of all, looser than `a if c else b`, so it covers the whole expression to its left: `a + b as km` is `(a + b) as km`, and `x if c else y as km` is `(x if c else y) as km`. That is the reading of "print the sum as km". It ends its expression: nothing may follow the unit, and it does not chain. `v as km + 1`, `v as km as m` and `v as km if c else w` are parse errors whose help says to put the arithmetic before `as` or to use parentheses. Parentheses and call arguments start a new expression, so `print(a + b as km, c)` shows only the first argument in km.

**What it means.** `v as unit` is a *display value*: the number (or array) `v` together with the unit to write it in. It is not a number. No value remembers its unit (see "Unit values"), so a display value has no dimension to compute with, and the checker allows it in two places only:
- as an argument of `print`: `print(v as km/h, w)`;
- as an expression statement, which the REPL echoes: `sky> v as km/h` prints `90 km/h` (and `sky run` ignores a top-level expression, as always).

Anywhere else, including as an operand of arithmetic or a comparison, in a binding, an argument to a function, or an array element, it is a check error, "a value shown in km/h can only be printed", with a help. Why an error and not a number in km: if `(v as km) + 1` were allowed, it would have to mean 1 km, 1 m or plain 1, and each is a way to reintroduce the scale-mixing bug that converting to SI at the literal removed. To compute with a number of kilometres, divide by the unit, which is a dimensionless number: `x / (1 km)`. To show the result of arithmetic, put `as` last: `print((a + b) as km)`.

**Rules.**
- The unit must have the value's dimension. `90 km/h as kg` is the check error "cannot show a velocity in kg" (with the derivation note of any dimension error and the unit's dimension as a secondary label). A plain number has no unit to convert from: `3 as m` is an error. A Bool, a string or a function cannot be shown in a unit.
- The unit is read with the unit-literal grammar and resolved by the same code, so prefixes, `^`, exponents and the did-you-mean for unknown units are exactly those of a unit literal: `km/h`, `kg*m^2/s^2`, `MeV`, `m^(1/2)`. A spaced `m / s` is an error, as in a type annotation. Offset units such as `°C` stay out of scope.
- The conversion divides by the unit table's factors, the inverse of the unit literal's arithmetic (`sky_types::express_in_unit`, one walk with `apply_unit`): factors are undone in the opposite order, so `25 m/s` is `25 * 3600 / 1000` km/h, exactly 90.
- The number is written with the SI printer's number format (`sky_interp::format_number`): shortest digits that read back, plain decimal from 1e-4 up to 1e16, `e` notation outside. One rule is added so that the display matches what a person wrote: the number shown is the shortest decimal that converts back to exactly the stored SI value. `100 km/h` is stored as `27.77777777777778 m/s`, whose exact quotient is `100.00000000000001`, and `100` is what is shown. A value with real float noise still shows it: `0.1 s + 0.2 s as ms` is `300.00000000000006 ms`, as `0.1 s + 0.2 s` prints `0.30000000000000004 s`.
- The unit is written after the number as spelled in the source: `90 km/h`, `0.511 MeV`. The whole text is valid Sky, like every printed value.
- Arrays show every entry in the unit: `[100 mm, 200 mm]`, `[[100 cm, 200 cm], [300 cm, 400 cm]]`.
- A conversion whose result does not fit an `f64` is a runtime error, like any overflow: `1e300 m as nm` is "arithmetic overflow".

**Implementation.** `as` is `ExprKind::As { value, unit, as_span }`. In SIR it is one operation, `show "km/h" %v : str`, which carries the unit's text and calls the same function as `sky run` (`sky_interp::show_unit_text`), so the two interpreters print the same text and fail the same way. SIR has no arrays yet, so an array shown in a unit runs with `sky run` and is not lowered.

### Uncertainty
Phase 3 (ROADMAP idea 10). A number may carry an uncertainty: `m = 5.31 ± 0.02 kg` is a mass of 5.31 kg with a standard uncertainty of 0.02 kg. This section is the first step, **linear (first-order) propagation with correlations tracked**; it supersedes the v0.1 decision that `±` is out of scope.

```text
uncertain := expr ( "±" | "+/-" ) expr           (level 5, with `+` and `-`; left-associative)
```

```sky
m = 5.31 ± 0.02 kg          # 5.31 kg, 1σ = 0.02 kg
g = 9.81 +/- 0.05 m/s^2     # the ASCII spelling
t = 1.5 s ± 20 ms           # each side may carry its own unit
T = 2 * π * sqrt(L / g)     # T is 2.006 ± 0.007 s when L = 1.000 ± 0.005 m
print(T as ms)              # 2006 ± 7 ms
```

#### Syntax
- **`±` and `+/-` are one token.** `+/-` is unambiguous: `/` cannot begin an expression, so `a +/- b` was never a valid `a + (/ ...)`, and the lexer reads `+/-` greedily as the uncertainty operator. `+-` is unchanged (`+` then unary `-`, so `a +- b` is `a + (-b)`); when `5.31 +- 0.02 kg` fails on a dimension mismatch the error says so and suggests `±`. The lexer accepts the glyph U+00B1 and rejects `∓` with a help. This is the one Unicode operator whose ASCII spelling is not a function call (see the table above): it is infix in both spellings, and a function `pm(x, dx)` would read worse than the glyph it replaces.
- **The uncertainty is one standard uncertainty (1σ)**, the standard deviation of the value. Sky never reads `±` as a range or a confidence interval.
- **Precedence and associativity are those of `+` and `-`** (level 5, left), as in Julia's Measurements.jl. So `a + b ± c` is `(a + b) ± c`, `a ± b + c` is `(a ± b) + c`, `a * b ± c` is `(a * b) ± c` (`*` binds tighter), and `a ± b == c` is `(a ± b) == c`. `as` is looser still: `x ± dx as km` shows the whole uncertain value. It is not a prefix operator, and `x ± dx ± dy` is left-nested (see Meaning).
- **`±` applies to any two expressions**, not only literals: `x ± dx`, `mean ± std / sqrt(n)`, `sqrt(9) ± 0.1`. The value and the uncertainty must have the same dimension.
- **Shared unit.** In `5.31 ± 0.02 kg` the number before `±` has no unit, and the unit after the uncertainty belongs to both sides, as in a lab notebook. The parser applies the rule, so nothing else needs to know it: when the left operand is a bare number literal (under any unary `-` or `+`: `-5.31 ± 0.02 kg`) and the right operand is a unit literal, the left operand becomes the unit literal with the same unit, and `5.31 ± 0.02 kg` parses as `5.31 kg ± 0.02 kg`. In every other shape the operands are what they are: `5.31 kg ± 20 g` (two units, both converted to SI at their literals), `x ± 0.02 kg` (`x` must be a mass), `(5.31) ± 0.02 kg` (a parenthesized number is not a bare literal: a dimension error).
- The right operand of `±` stops before `+`, so `5 ± 1 m + 2 m` is `(5 ± 1 m) + 2 m`.

#### Meaning
- `x ± dx` is the value `x` with an *additional, independent* standard uncertainty `dx`. `dx` must be an exact number (not itself uncertain) of the dimension of `x` and not negative; `x` may be exact or already uncertain (`(a ± 0.3) ± 0.4` has uncertainty `sqrt(0.3² + 0.4²) = 0.5`). A zero uncertainty is allowed (`5 kg ± 0 kg` is exact but still prints as `5 ± 0 kg`). A negative one is a runtime error ("an uncertainty cannot be negative") and, when it is a constant, a check error.
- **Uncertainty is a run-time property of a number, not part of its type.** Every number may carry an uncertainty; a plain number carries none. Units and shapes are the checker's, unchanged: `5.31 ± 0.02 kg` has type mass, exactly as `5.31 kg` does, and every rule of dimensional analysis applies to it as before. Why not a type: (1) a type would need the same treatment everywhere a dimension is threaded (function signatures, annotations, arrays, SIR types), for a property that never changes a dimension error or a rewrite; (2) whether a value has an uncertainty often depends on the run (`x - x` is exactly zero, `sqrt(0)` is exact, `min(1, 2 ± 0.1)` is exact), which a type cannot know; (3) it lets exact code and uncertain code share every function, as `sqrt(x)` does for a plain `x`. The price is that the checker cannot flag every comparison of measurements (see Comparisons).
- **Representation and correlations.** Following Python's `uncertainties` package (BSD; the technique, not its code), an uncertain value is `x₀ + Σ cᵢ εᵢ`: a nominal value plus a linear combination of independent, unit-variance *error sources* `εᵢ`. Every `±` makes one fresh source. An operation gives the nominal result of the exact operation, and each source's coefficient becomes `Σⱼ (∂f/∂xⱼ) · cᵢ(xⱼ)`, the chain rule on the linear part. The standard uncertainty is `σ = sqrt(Σ cᵢ²)` and the covariance of two values is `Σ cᵢ(x) cᵢ(y)` over their shared sources, so correlations follow from the names of the sources alone and no covariance matrix is stored. Consequences:
  - `x - x` is exactly `0 ± 0` and `x / x` is exactly `1 ± 0` (the sources cancel); `x + x` has uncertainty `2σ`, not `sqrt(2) σ`; `x * x` and `x^2` agree (`2 x₀ σ`), while `(a ± da) * (a ± da)`, two independent measurements, gives `sqrt(2) a₀ σ`;
  - `(x + y) - y` has the uncertainty of `x`; `sin(x)^2 + cos(x)^2` is `1` with no uncertainty (to rounding);
  - averaging `n` independent readings divides the uncertainty by `sqrt(n)`, but adding the same reading `n` times does not.
- Sources are numbered by a process-wide counter and summed in that order, so a run gives the same bits every time.
- **Propagation is linear** in each argument: `+`, `-`, `*`, `/`, `^`, unary `-`, `x⁻¹`, and the math functions, with the partial derivatives of "Derivatives":

  | operation | partial derivatives |
  |---|---|
  | `a + b`, `a - b` | `1`, `±1` |
  | `a * b` | `b`, `a` |
  | `a / b` | `1/b`, `-(a/b)/b` |
  | `a ^ b` | `b a^(b-1)` (the exponent is usually exact), `a^b ln a` (needs `a > 0`) |
  | `sqrt`, `cbrt`, `exp`, `expm1`, `log`, `log10`, `log2`, `log1p` | `1/(2r)`, `1/(3r²)`, `r`, `r+1`, `1/x`, `1/(x ln 10)`, `1/(x ln 2)`, `1/(1+x)` |
  | `sin`, `cos`, `tan`, `asin`, `acos`, `atan` | `cos x`, `-sin x`, `1+r²`, `1/sqrt(1-x²)`, `-1/sqrt(1-x²)`, `1/(1+x²)` |
  | `sinh`, `cosh`, `tanh`, `asinh`, `acosh`, `atanh`, `erf` | `cosh x`, `sinh x`, `1-r²`, `1/sqrt(x²+1)`, `1/sqrt(x²-1)`, `1/(1-x²)`, `(2/√π) e^(-x²)` |
  | `hypot(x, y)` | `x/r`, `y/r` |
  | `atan2(y, x)` | `x/(x²+y²)`, `-y/(x²+y²)` |
  | `abs` | `-1` for `x < 0`, else `+1` (the right-hand slope at 0) |
  | `min`, `max` | `1` for the operand returned (the first if they are equal), `0` for the other; an exact operand that is returned stays exact |
  | `floor`, `ceil`, `round`, `sign` | `0`: constant between jumps, so the result has no uncertainty |

  The nominal result, every dimension rule and every domain error are those of the exact operation (`sqrt` of a negative nominal value is the same error; `sin(1 ± 0.1 m)` is the same dimension error), by construction: the exact rules run on the nominal values first.
- **Where the slope is infinite** at the nominal value (`sqrt(0 ± 0.1)`, `asin(1 ± 0.01)`, `(0 ± 0.1) ^ 0.5`) and the argument carries an uncertainty, the call is a runtime error ("cannot propagate an uncertainty through `sqrt` at 0"), as the derivative of the same expression is. An exact argument needs no slope: `sqrt(0)` is `0`, and so is `sqrt(0 ± 0)`.
- Linear propagation is exact for linear functions and a good approximation when the uncertainty is small against the scale on which the function bends. It is not a distribution: `sqrt(1 ± 0.5)` has a first-order uncertainty and nothing else. Monte Carlo and higher-order propagation are future work.
- Results are finite like every Sky number: a coefficient that does not fit an `f64` is an "arithmetic overflow" error.

#### The checker
- `x ± dx` is typed like `x + dx`: two scalars of one dimension, giving that dimension. A dimension mismatch is "cannot use a time as the uncertainty of a mass" (with the derivation notes of any dimension error). A Bool or function operand, and a constant negative uncertainty, are errors. Arrays are not uncertain in this step: `[1, 2] ± 0.1` is the error "`±` needs scalar operands", and an uncertain number as an array element is a runtime error.
- **`nominal(x)` and `uncertainty(x)`** are builtins (a user binding of the same name wins, as for `print` and `inv`). `nominal(x)` is the value of `x` and `uncertainty(x)` its standard uncertainty, both of the dimension of `x`; for a plain number they are the number and `0` of its dimension. They are how a program looks inside an uncertain value: `uncertainty(T) / nominal(T)` is the relative uncertainty.
- **Warning: comparing uncertain values** (see Comparisons). The checker tracks, cheaply and approximately, which expressions *may* be uncertain: one that contains a `±`, or a name bound (earlier, in any branch) to such an expression, through arithmetic and calls; `nominal(...)` and `uncertainty(...)` are exact. Rebinding a name to an exact expression clears it. The tracking is per name, so a function parameter is not tracked; it can miss a warning or give one that is not needed. It blocks a program in two places only, where run time would stop it anyway:
- **Error: an uncertain number in a `solve`.** `solve` does not propagate uncertainties yet, so an initial value, a time bound, a name the equations' right sides read (they read it when the `solve` runs, see "Differential equations"), a `±` written in them, or a name a `conserve` reads, that may be uncertain is a check error at that place ("the initial value of `th` may be an uncertain number", "the equations of `pend` read `L1`, which may be an uncertain number", with the use as a secondary label), with the way out: solve with `nominal(v)`, and again with `nominal(v) + uncertainty(v)`, to see how far the result moves. Before, it was a runtime error when the `solve` was reached, sometimes on the `conserve` line rather than at the value that caused it.
- **Error: an uncertain argument of a derivative.** `derivative(f, x)(...)` is taken at a point and does not propagate uncertainties yet, so an argument that may be uncertain is a check error on it ("`derivative(f, γ)` needs exact arguments, but `γ` may be an uncertain number"), with the way out: `nominal(...)`, and the first-order uncertainty of `f` is the derivative times `uncertainty(...)`. Run time makes the same check on the values (for what the tracking misses, a function parameter say), on the argument, rather than failing inside `f`.

#### Comparisons
`==`, `!=`, `<`, `<=`, `>`, `>=` compare **the nominal values** and ignore the uncertainties, so `(3 ± 5) < (4 ± 5)` is `true`, and a comparison is an ordinary `Bool`. This is deliberate: a total, cheap and predictable rule, and there is no honest single Bool for "3 ± 5 is less than 4 ± 5". But it is rarely what a comparison of measurements means, so the checker warns ("comparing an uncertain value compares only its nominal value") on any comparison that may have an uncertain operand, with the way to ask the real question: two values agree within `k` combined standard uncertainties when

```sky
abs(nominal(a - b)) < 2 * uncertainty(a - b)      # correlations between a and b are respected
```

`a - b` carries the correlation of the two values, so this is right even when they share a source. Comparing an uncertain value with a plain one, or two values of different dimensions, is the same dimension error as for plain numbers.

#### Printing
A value with an uncertainty prints as `value ± uncertainty unit`, in SI, and the text is valid Sky (it reads back as a value with that uncertainty). The digits follow the metrology convention (GUM; the Particle Data Group's variant): the uncertainty to one or two significant digits, then the value rounded to the same decimal place, so every digit written means something.
- The uncertainty has **two** significant digits if its three leading digits are 100 to 354, and **one** if they are 355 to 949; 950 to 999 round up to `1.0`. A trailing zero of the two-digit form is dropped, so `5.31 ± 0.02 kg` prints as written, and `0.0200` is `0.02`.
- The value is rounded to the last digit of the uncertainty and printed with all its decimals: `9.8123 ± 0.0234` prints `9.812 ± 0.023`; `5.3148 ± 0.0201` prints `5.31 ± 0.02`; `1234 ± 56` prints `1230 ± 60`; `3 ± 1.5` prints `3.0 ± 1.5`; a value that rounds to zero prints `0.00 ± 0.02`, without a sign.
- A zero uncertainty prints as `x ± 0`: `x - x` is `0 ± 0 kg`.
- Numbers use plain decimal from `1e-4` up to `1e16` (and at most nine decimals) and `e` notation outside, on both sides: `6.67400e-11 ± 1.5e-15`.
- `v as g` writes both the value and the uncertainty in the unit (units are factors): `print(5.31 ± 0.02 kg as g)` prints `5310 ± 20 g`. The digits follow the uncertainty in the shown unit. The rules of "Showing values in a unit" (the dimension must match, and the result can only be printed or echoed) apply unchanged.

#### Engines
Uncertainty runs on the tree-walking interpreter (`sky run`, which falls back to it, and `sky repl`). SIR (see `docs/design/ir.md`) has no uncertain type, so lowering a program that uses `±`, `nominal` or `uncertainty` is a lowering error, and:
- `--engine=auto` falls back to the tree-walker silently, as for any construct SIR cannot express yet;
- `--engine=sir` reports "cannot run on SIR: uncertainty (`±`) is not supported by SIR yet";
- `derivative(f, x)(args)` runs on SIR, so it fails in a program that uses `±`, with the same reason.

#### Not in this step
Arrays and matrices with uncertainties (elementwise propagation follows directly from the model; `±` on an array is a check error for now), correlated inputs given as a covariance matrix (build them from shared sources instead: `a = x ± dx`, then `b = 2 * a + c`), non-linear and Monte Carlo propagation, asymmetric uncertainties, and the SIR representation.

### Type annotations
`NAME: type` declares what a name is; `NAME: type = expr` also gives it a value. An annotation reads like English: "`A` is a positive-definite N by N matrix of kilograms". `~` means the two tokens touch, as in the unit-literal grammar.

```text
type  := tag* shape [ unit ]
       | tag* unit
       | "Scalar"
tag   := NAME                  (Symmetric, PositiveDefinite, Diagonal, Orthogonal)
shape := ( "Vector" | "Matrix" | "Tensor" ) "[" dim ( "," dim )* [ "," ] "]"
dim   := INT | NAME            (a NAME is a size variable)
unit  := factor ( ~("*" | "/")~ factor )*      (the unit-literal grammar)
```

```sky
t: s                                   # scalar time
v: Vector[3] m/s                       # vector of velocities
A: PositiveDefinite Matrix[N, N]       # tags before the shape
K: Symmetric Diagonal Matrix[3, 3] N/m
x: Scalar                              # dimensionless scalar
M: Tensor[B, T, D] kg
```

- **A lone name is always a unit.** `x: N` is newtons and `x: K` is kelvin, never a size variable. Size variables exist only inside `[...]`, so `A: Matrix[N, N] N` is an N by N matrix of newtons. A bare unit means a scalar of that unit; `Scalar` alone is a dimensionless scalar (it takes no unit: write `x: m`, not `x: Scalar m`).
- **The parser tells the parts apart by position.** After optional tags, a name followed by `[` is a shape, and `Vector`, `Matrix`, `Tensor` and `Scalar` are the only shape words. Any other name starts the unit, which must be followed by nothing or by a touching `*`, `/` or `^` (so `m/s^2`, `kg*m^2`). Leading capitalized names are tags when they run up to a shape word, so `PositiveDefinite Matrix[3, 3]` has one tag and `Symmetric Diagonal Matrix[3, 3]` two. One of the four property words followed by another name also starts the tags (`Symmetric m`, which the checker reports as a property without a shape). The checker validates tag names, and a misspelling gets `unknown matrix property` with a did-you-mean.
- **Declaration without a value is an input.** `A: PositiveDefinite Matrix[N, N] kg` binds `A` with those tags, shape and unit, taken on trust. This is how a program gets a positive-definite matrix without spelling its entries, and so how `A⁻¹ @ b` reaches the Cholesky rewrite when the entries are not literals. `sky run` has nothing to read such an input from yet, so running a declaration without a value is a runtime error (`` `A` is declared but has no value ``); a literal with a proven tag (below) is the way to run one.
- **With a value, the value must agree.** The shape must unify. If a unit is declared, the value's dimension must equal it (`expected mass, found length`). If tags are declared, the value's closed tag set must include them (`B is not known to be PositiveDefinite`): the checker only knows properties it can prove, from a declaration or an operation that preserves them. Without a declared unit the dimension comes from the value, and is dimensionless when there is no value. The value must be a number, never a Bool.
- Tags need a square matrix shape: `Symmetric Vector[3]` and `Diagonal Matrix[3, 4]` are errors.
- Parse errors, each with the correct spelling as help: a tag after the shape (`Matrix[3, 3] PositiveDefinite`; the checker reports this one, because only it knows the tag names), a value where a type belongs (`x: 5 m`), juxtaposed units (`x: m s`, write `m*s`), spaces around a unit's `*`, `/` or `^` (`x: m / s`), slices, arithmetic (`Matrix[N+1, N]`) and non-integer dimensions in `[...]`.
- A compound unit written with a space is an error with a help pointing at `*`, whatever the case of its first name: `x: N m` suggests `N*m`, and `x: Pa s` suggests `Pa*s`.

### Matrix tags
- PositiveDefinite and Diagonal each imply Symmetric, so a PositiveDefinite or Diagonal matrix can be used where a Symmetric one is expected.
- This holds only because every element of a v0.1 matrix has the same unit. Once matrices can mix element units, whether a matrix is symmetric will depend on its units as well as its values, and this rule will need revisiting.

### Array literals
```text
array := "[" expr ( "," expr )* [ "," ] "]"
```

- `[1 m, 2 m, 3 m]` is a `Vector[3]` of lengths. `[[1, 2], [3, 4]]` is a `Matrix[2, 2]`, written as rows: it is an array whose elements are all array literals, and the row length is the number of columns. Matrices may be spread over several lines, since newlines inside brackets are not statement ends.
- The parser only reads nested brackets; the checker decides the shape. A literal is a scalar list, or a list of scalar lists. Mixing scalars and rows (`[1, [2, 3]]`), a third level of nesting, and an element that is not a number (a Bool, a name bound to a vector) are errors on that element.
- **Every element must have the same dimension.** `[1 m, 2 s, 3 m]` is an error on `2 s` (the dimension held by most elements is the expected one, the first on a tie), and the other elements are not reported. In a matrix the rule covers every entry. Rows must have equal lengths; a row that differs from the rest (again by majority, first on a tie) is an error on that row.
- **Empty literals are rejected**, at parse time: `[]` is an error. An empty literal has no element to fix the dimension of its entries, so `[]` would have to be dimensionless and could then never be added to a vector of lengths, or it would need a type annotation from context, which Sky's inference does not have. Nothing is lost: an all-zero vector is `zeros(n)`, and a zero-length array has no use in v0.1 (`zeros(0)` is an error too).
- The type of a literal is exact: `Vector[3]` or `Matrix[2, 2]`, with the element dimension and **no tags**. A literal can be bound to a declared type that has the same shape and dimension (`v: Vector[2] m = [1 m, 2 m]`; the declared unit must match the entries, so `K: Matrix[2, 2] N/m = [[2, 1], [1, 2]]` is an error, as it is for a scalar).

#### Tags on literals
A declared tag is a promise the checker must be able to keep. For a literal it can be kept from the entries, but only when **every entry is a numeric literal**: a number or a number with a unit, optionally negated (`2`, `-1.5`, `3 N/m`, `-(2)`). Then the checker reads the values as the interpreter will (the same `f64`, after the unit's conversion to SI), and proves:

- **Symmetric**: the matrix is square and `aᵢⱼ == aⱼᵢ` for every pair, exactly.
- **Diagonal**: the matrix is square and every off-diagonal entry is exactly zero.
- **PositiveDefinite**: the matrix is Symmetric, at most 32 by 32, and a Cholesky factorization `A = L·Lᵀ` in `f64` finds every pivot larger than `1e-9` times the largest diagonal entry. This is pure arithmetic on constants the source spells out; it runs no user code, and the checker still never evaluates anything else. The margin is far above the rounding error of a factorization this small, so a proof is not a rounding artifact, and a positive-definite matrix that is that close to singular (condition number about 1e9 or worse) is simply not proven. Declare such a matrix as an input if you need it.
- **Orthogonal** is never proven for a literal: it needs exact equality of sums of products, which decimal entries such as `0.6` and `0.8` do not give in `f64`. (`identity(n)` is Orthogonal.)

If any entry is not a numeric literal (`[[a, 1], [1, a]]`, `[[2 * x, 1], [1, 2]]`) nothing is proven and the usual "not known to be" error stands, with a note that says why. If the entries are all constants and the property is false, the error names the failing entry (`entry [0, 1] is 2 but entry [1, 0] is 3`).

### Arrays: indexing, builtins and operations
- **Reading.** `v[i]`, `A[i, j]` and slices (`A[0, :]`, `v[1:3]`, `A[:n, 2:]`). An index is a dimensionless integer; a slice is `start:stop` with `stop` excluded and either bound optional. A scalar index removes its axis and a slice keeps it, so `A[0, :]` is a `Vector` and `A[0:1, :]` a `Matrix[1, N]`. Fewer indices than axes leave the trailing axes whole (`A[0]` is row 0). The element dimension is kept and the result has no tags. **Writes stay check errors: arrays are immutable in v0.1.**
- **Bounds.** A constant index or slice bound is checked against a known axis length at check time (`v[3]` on a `Vector[3]` is an error on the index). A variable one, or an axis with a symbolic length, is checked when the program runs. Indices are never negative, and a slice is never empty: arrays have at least one element on every axis, so `v[2:1]` is an error.
- **Slice length.** With constant bounds the length is known (`v[1:3]` is `Vector[2]`); otherwise the result has a fresh size variable that equals only itself.
- **Builtins.** `zeros(n)` is a `Vector[n]` and `zeros(m, n)` a `Matrix[m, n]`; `identity(n)` is a `Matrix[n, n]`; all are dimensionless (scale with `3 m * zeros(2)`). `len(x)` is the length of the first axis, as a dimensionless number. `norm(x)` is the Euclidean length of a vector (the Frobenius norm of a matrix, the absolute value of a scalar), with the dimension of `x`, and `dot(a, b)` the inner product of two vectors of one length, with the product of their dimensions (`dot(F, d)` of forces and lengths is an energy); both are scalars. `norm` and `dot` run on both engines (SIR has an operation for each, evaluated by the tree-walker's own functions, so results and errors are the same bytes) and are differentiable: `grad(U)` of a potential written with `norm(p)` needs no `sqrt(p @ p)`. `norm` has no derivative at a zero vector, and says "division by zero" there as `sqrt` does at 0. Sizes are part of the type, so they must be constant positive integers, and an array may have at most 2^24 elements. `identity(n)` has every matrix tag, `zeros(n, n)` is Diagonal. Like `print` and `inv`, a user binding with the same name shadows the builtin. The `I` in checker help text is written `identity(n)`.
- **Operations (run time).** `+` and `-` between arrays of one shape and dimension are elementwise; `*` and `/` between arrays of one shape are elementwise too, and multiply or divide the dimensions entry by entry (see "Arrays: entry by entry"); `*` and `/` by a number scale (`2 * v`, `v / 2 s`); `-v` negates. `@` multiplies matrix by matrix, matrix by vector, vector by matrix, and vector by vector (a dot product, so a number); dimensions multiply. `A⁻¹` and `inv(A)` invert a square matrix with the inverse dimension. `Aᵀ` and `transpose(A)` swap the axes of a matrix (see "Operator precedence"); the entries move and the dimension is unchanged. `*` between arrays is never the matrix product: that is `@`, always.
- **Inverse.** Gauss-Jordan elimination with partial pivoting. A matrix whose pivot is zero, or no larger than `n · ε · max|aᵢⱼ|`, is singular: a runtime error on the expression, never `inf`. The inverse of an exactly symmetric matrix is computed as one triangle and mirrored, so it is bitwise symmetric (the checker tags it Symmetric; see `tag_ops::needs_mirroring`). This is the inverse of a matrix that is *named or otherwise formed*; `A⁻¹ @ b` written together is a solve, see "Algorithm choice".
- **Cholesky solve.** `A⁻¹ @ b` with a PositiveDefinite `A` is one of the solves of "Algorithm choice" (the site is in `Checked::cholesky_solves`, or in `Checked::chains` inside a longer chain). The interpreter factors `A = L·Lᵀ`, then solves `L·y = b` and `Lᵀ·x = y`; `A⁻¹` is never formed. `b` may be a vector or a matrix of right-hand sides. The rewrite is honoured by the span of the whole `A⁻¹ @ b` expression. Because an input's tags are taken on trust, the interpreter verifies the promise: an `A` that is not exactly symmetric, or has a pivot that is not positive, is a runtime error naming the fact.
- **Finite.** Every entry of every result must be finite; an overflow anywhere is a runtime error on the expression, like a scalar.
- **Printing.** An array prints as a valid Sky literal, entries in SI, each with its unit: `[1 m, 2 m]`, `[[1, 2], [3, 4]]`, `[0.1 m, 0.2 m]`. Numbers follow the scalar rules.

### Arrays: entry by entry
Sky has one product that sums over an index, `@`, and one that does not, `*`. On numbers they agree; on arrays they never do, and each has one meaning.

- **Why `*` on arrays used to be an error, and why it is not now.** The rule "v0.1 has no elementwise `*` between arrays" refused the one product whose meaning readers disagree on: in MATLAB `A * B` is the matrix product and in NumPy it is the entry-by-entry one, and for two `Matrix[3, 3]` both readings type-check, so a wrong guess is a wrong answer that nothing reports. It was also a deferral: there was no run-time array arithmetic to give it a meaning. Both reasons are gone. The matrix product has its own operator, so `*` never sums over an index and is only ever the operator that multiplies numbers, entry by entry when the operands are arrays of one shape. The risk that remains is a reader who writes `A * B` for a matrix product; the checker cannot tell that from intent when the shapes agree, so the rule is stated where the mistake is made: an error about `*` and `/` on shapes that do not agree says that `*` works entry by entry, and, when `A @ B` would have been valid, says "for the matrix product use `@`".
- **`a * b` and `a / b`** of two arrays of one shape (sizes that unify count as one) are elementwise: entry `(i, j)` of the result is `a[i, j] * b[i, j]` (or `/`), the entries' dimensions multiply or divide as for numbers (a vector of lengths times a vector of times is a vector of `m*s`), and the result has the shape of the operands. Shapes that differ, including a vector and a matrix, are a check error worded like the one for `+` ("cannot apply `*` to Vector[3] and Vector[4]", with the shape debugger's notes), and for `*` the help says "for the matrix product use `@`" when `@` would accept the operands.
- **No broadcasting between arrays.** A `Vector[3]` does not stretch to a `Matrix[3, 4]` and a `Matrix[N, 1]` does not stretch to `Matrix[N, M]`; each would be a guess about which axis is meant. A **number** combines with an array as before: `c * A`, `A * c` and `A / c` scale every entry (`c / A` stays an error, since a matrix has an inverse, not a reciprocal), and the functions below take a number for every entry. `+` and `-` are unchanged (equal shapes only; `c + A` stays an error).
- **Math functions** of one array apply to each entry, and the two-argument ones (`atan2`, `hypot`, `min`, `max`) take arrays of one shape or an array and a number (see "Math functions"). The dimension rule of each function is applied to the entries' dimension, so `sqrt` halves it, `exp(v)` needs a dimensionless vector, and `atan2(y, x)` needs `y` and `x` of one dimension.
- **`^` on an array is still an error.** `v^2` reads as the square of every entry in NumPy and as the squared length in every physics text (`½ m v²` is a number when `v` is a velocity vector), and both readings type-check, so `k = 0.5 * m * v^2` would silently be a vector. That is the ambiguity `*` avoided by having `@`, and `^` has no second operator to say which is meant. The error offers both spellings: `v @ v` (or `norm(v)^2`) for the squared length, `v * v` for the entry-wise square, and the product `v * v * v` for higher powers; `A^-1` still points at `A⁻¹`.
- **Run time.** Each entry is computed by the scalar operation, on every engine (the same `f64` arithmetic and `sky_interp::math::apply_f64`), so an array expression gives, entry by entry, the bits of the scalar program run on each entry, and a fused kernel gives the bits of the separate operations. A result that is not finite is an overflow error and a zero divisor a division by zero, on the failing expression; if several entries fail, the error is the lowest entry's, and no message names an entry (as for `+`). In a chain of operations the first operation in program order that fails at any entry decides the error, fused or not.
- **Tags.** A result keeps only the tags that hold for every input, exactly. *Symmetric* survives `a * b` and `a / b` when both operands are Symmetric, `f(A)` when `A` is, and `f(A, B)` when both are (each entry is one deterministic function of the entries at that position, so bitwise equal entries at `(i, j)` and `(j, i)` give bitwise equal results); a number operand takes no part. *Diagonal* survives `a * b` when **either** operand is Diagonal (an off-diagonal entry is `0 * x`, which is zero) and `a / b` when the **numerator** is (`0 / x`; a zero denominator entry is an error, so no wrong result exists); it does not survive a math function, since `exp(0)` and `cos(0)` are 1 and `log(0)` fails, and whether `f(0)` is 0 is not a question the tag rule consults. *PositiveDefinite* and *Orthogonal* never survive: the Schur product theorem gives the first over the reals, but the entries are rounded and a promise the interpreter later finds broken is an error, and `Q ∘ Q` is not orthogonal. `+` and `-` still claim nothing.
- **Cost.** An entry-by-entry operation on `N` entries costs `N` times the scalar cost (see "Performance contracts"), and the SIR pass `fuse` turns a chain of them into one kernel that reads each input once (see `docs/design/ir.md`, "Fusion"), so `sqrt(x*x + y*y) * c + d` over long vectors makes one pass over memory.

### Algorithm choice
Sky knows the shapes, dimensions and matrix tags of every operand, so it may compute a linear-algebra expression by a cheaper algorithm than the one the text suggests. This section says exactly what the program means, which choices change the last bits of a result, and which never do.

- **`@` chains have no fixed association.** An unparenthesized chain `A @ B @ C @ v` is one operation. The compiler picks the parenthesization with the fewest floating-point operations (the classic matrix-chain dynamic program), so `A @ B @ C @ v` on `Matrix[500,500]` factors and a vector is computed as `A @ (B @ (C @ v))`: O(n²) instead of O(n³). The flop model: `m×k @ k×n` costs `2·m·k·n`; a Gauss-Jordan inverse of `n×n` `4·n³`; an LU solve with `k` right-hand sides `⅔·n³ + 2·n²·k`; a Cholesky solve `⅓·n³ + 2·n²·k`; a Diagonal solve or scaling `n·k`. With known shapes the choice is the exact optimum (the written left-to-right order wins ties). With symbolic shapes (`Matrix[N,N]`) costs are polynomials in the size variables, and an order is chosen only if it is provably no more expensive for every size (every size is at least 1); otherwise the written order stays. A vector in the middle of a chain has no orientation, so such a chain is never reordered, and a chain of more than 32 factors is not planned.
- **Parentheses are respected.** A parenthesized product is one factor of the outer chain and is planned on its own: `(A @ B) @ C @ v` multiplies `A @ B` first, always. Writing parentheses is how a program forces an association.
- **Reassociation changes rounding.** Matrix products are associative over the reals, not in `f64`. A reassociated chain gives a result within the ordinary error bound of any association of the same product, and may differ from the written order in the last digits. It can also change whether an *intermediate* overflows: an association whose intermediate is finite succeeds where another fails with `arithmetic overflow`, and the reverse. This is the meaning of an unparenthesized chain, not an optimization that may be skipped.
- **`A⁻¹ @ b` means the solution `x` of `A x = b`**, computed by a method the compiler chooses; `A⁻¹` is never formed. The method follows the tags of `A`, in this order:
  - **Orthogonal**: `A⁻¹` is `Aᵀ` (`QᵀQ = QQᵀ = I` by the tag's definition), so `x = Aᵀ b`, with no inverse and no transposed copy. The tag is a promise the interpreter does **not** verify (checking `QᵀQ = I` costs as much as the product it saves); an operand that breaks it gives a wrong answer. The tag is never proven for a literal (see "Tags on literals"), only declared, or given by `identity(n)` and by products and negations of Orthogonal matrices.
  - **Diagonal**: `xᵢ = bᵢ / aᵢᵢ`, one correctly rounded division per entry. The promise is verified: an off-diagonal entry that is not exactly zero is a runtime error naming it. A diagonal entry that the inverse would call zero (no larger than `n·ε·max|aᵢⱼ|`) is singular.
  - **PositiveDefinite**: a Cholesky factorization, as in "Cholesky solve" above, promise verified.
  - **Otherwise** (any square matrix): LU with partial pivoting, `A = P·L·U`, then two triangular solves. The elimination is the forward phase of the Gauss-Jordan `inverse`, operation for operation, so a matrix is singular for the solve exactly when it is for the inverse, with the same error.

  `x @ A⁻¹` is the transposed solve: the `y` with `y @ A = x`, by the same methods, without forming `Aᵀ`. `A⁻¹ @ B⁻¹` is computed as `(B @ A)⁻¹` when the flop model says so (it does for square matrices: one product and one inverse instead of two inverses and a product). The operands of a solve are evaluated first, left to right, each once, and then the solve runs; a singular `A` is reported after both operands were evaluated, not before `b` is. To compute the inverse itself, name it: `M = inv(A)` is the Gauss-Jordan inverse, and the checker and the tree-walker leave `M @ b` as an inverse followed by a product. (The SIR pass `cholesky` still turns a PositiveDefinite `M @ b` into a Cholesky solve there, and says so.)
- **A solve is not bit-identical to inverse-then-multiply.** It rounds differently, and is at least as accurate: it avoids the rounding error of the inverse and of the product with it. The results agree to the usual conditioning bound `κ(A)·ε`, not bit for bit. `Orthogonal` solves are exact where the inverse only approximates `Aᵀ`.
- **Both engines follow the checker's choice.** The checker records each planned chain under the span of the whole expression (`Checked::chains`, as `Checked::cholesky_solves` records Cholesky sites). The tree-walker evaluates the plan and lowering emits its operations, in the same order and with the same functions (`sky_interp::solve`), so `sky run` gives the same bits and the same errors on either engine. Parentheses exist only in the syntax tree, which is why the choice is made where the tree is, not in SIR.
- **Exact rewrites.** These give the bits of the unrewritten program, need no permission from this section, and are made by passes on SIR (the engines need not follow them):
  1. `transpose(A) @ B` (and `A @ transpose(B)`) becomes `matmul[ta]` (`[tb]`), which is *defined* as the transpose followed by the product; a kernel may read the operand with swapped strides. Rule `LA-TRANSPOSE-001`.
  2. `transpose(S)` of a Symmetric `S` is `S` (the tag means `aᵢⱼ == aⱼᵢ` exactly). Rule `LA-SYMMETRIC-001`.
  3. `D @ X` and `X @ D` with a Diagonal `D` are a scaling of rows or columns, `0.0 + dᵢ·xᵢⱼ`: every other term of the product's sum is `±0` added to a sum that started at `+0.0`, so the bits (including the sign of a zero) are those of `@`. O(n²) instead of O(n³). The promise is verified. Rule `LA-DIAGONAL-001`.
  4. A Gram product, `Aᵀ @ A` or `A @ Aᵀ`, is symmetric bit for bit (`aₚᵢ·aₚⱼ` and `aₚⱼ·aₚᵢ` are the same product), so one triangle is computed and mirrored: half the multiplications. Rule `LA-GRAM-001`.
  5. `x ^ n` for an integer `n` with `2 ≤ n ≤ 14` becomes the multiplication chain that the interpreter's `f64::powi` performs (square and multiply, right to left), which is also the fewest multiplications for those `n`. Bit-identical, and the multiplications fuse with neighbouring arithmetic. Negative exponents and `n > 14` are left as `pow`: `x^-n` is `1/xⁿ`, which today yields `0` where an intermediate overflows, and for `n = 15` the fewest-multiplication chain is a different tree than `powi`'s and would change bits. Rule `POW-CHAIN-001`.
- **Explanations.** Every rewrite is explained. `sky check --explain` prints, for a planned chain (rule `LA-CHAIN-001`), the chain, the reason for each solve, the estimated flops as written and after, and that the result is not bit-identical; for an exact rewrite it prints the rule and the flops before and after. The order of the passes is documented in `sky_opt::pipeline`.
- **Variant choice by shape.** Every `matmul` may record an *algorithm*: `auto` (the engine chooses), `dot`, `matvec`, `vecmat`, `gemm` (the shape classes) or `syrk` (a Gram product). **Every algorithm computes the reference result bit for bit** (each entry is the sum of `a[i,p]·b[p,j]` in index order `p = 0, 1, …` from `+0.0`, with the same errors; for the `dot` class, a product of two vectors, the single sum has the fixed order given in "Arrays: reproducible arithmetic"); that is the contract that lets a kernel or a tuning table plug in its own code per class. A kernel that reorders that sum is not an algorithm variant but a rewrite, and needs permission from this section. The default policy records `syrk` where it applies and otherwise leaves `auto`; a policy is a function from the operand shape class to an algorithm, and kernels and tuning register theirs.

### Arrays: reproducible arithmetic
This is Sky's default numerics; "Relaxed numerics" below is the opt-in alternative that trades it for speed. Every engine that runs Sky (the tree-walking interpreter, the SIR interpreter, and any native one) calls the same array kernels (the `sky-linalg` crate), and a result never depends on the machine, the number of threads, the vector width or the engine: the same program prints the same bits everywhere. The kernels are fast (packed, cache-blocked, vectorized, threaded), so the rule is not "use the slow order" but "fix the order of the additions, then make that order fast". Floating-point addition is not associative, so each operation below has one defined order of arithmetic, and no kernel may change it.

- **Matrix products** (`@` on matrix by matrix, matrix by vector and vector by matrix). Every entry of the result is accumulated in the naive order,

  ```text
  c = 0;  for k in 0..K { c = c + a[i, k] * b[k, j] }
  ```

  with the product rounded to an `f64` first and then the sum (a multiply and an add, **never a fused multiply-add**). Vectorizing across `i` and `j` (each lane a different entry), blocking (a block over `k` continues from the partial sum the last one left, so the chain is unbroken), packing and splitting the output across threads all leave every entry's chain as written, so they are allowed.
- **Reductions** (`a @ b` of two vectors, `dot(a, b)`, and the sums of squares inside `norm`). One sum cannot be vectorized in sequential order, so its order is fixed differently, in a way any hardware can follow. For terms `p₀ … pₙ₋₁` (each product rounded first):
  - with fewer than 8 terms, left to right from `+0.0`: `((0 + p₀) + p₁) + …` (short vectors such as 3-vectors keep the sum everyone expects);
  - with 8 or more, eight partial sums `s₀ … s₇`, all starting at `+0.0`, where `pᵢ` is added to `s[i mod 8]` in index order, combined by the fixed tree `((s₀ + s₄) + (s₂ + s₆)) + ((s₁ + s₅) + (s₃ + s₇))`.

  `norm` sums the squares `xᵢ·xᵢ` this way (the scaled form for entries beyond `1e±100` sums `(xᵢ/s)·(xᵢ/s)`) and then takes the square root. A product with a single output entry that is *not* two vectors (`Matrix[1, K] @ Vector[K]`) is a matrix product and keeps the naive order above. Every sum starts at `+0.0`, so an empty or all-zero sum is `0`, never `-0`.
- **Cholesky solve, the LU solves, and the inverse.** Each is defined by the plain algorithm, entry by entry, and the fast versions (blocked, right-looking or recursive, running their updates in the product kernel) reproduce each entry's chain of roundings exactly.
  - The Cholesky factor: `d = a[j,j]`, `d = d - l[j,k]*l[j,k]` for `k` ascending (a pivot that is not positive is the error), `l[j,j] = sqrt(d)`, and `s = a[i,j]`, `s = s - l[i,k]*l[j,k]` for `k` ascending, `l[i,j] = s / l[j,j]`.
  - The triangular solves: `x[i]` starts as the right-hand side, subtracts `m[i,j]·x[j]` for its `j` in ascending order, then divides by `m[i,i]`, for `L·y = b` and then `Lᵀ·x = y`.
  - The inverse is Gauss-Jordan elimination with partial pivoting exactly as described under "Arrays: indexing, builtins and operations", with its singularity threshold, error and bitwise symmetry unchanged.
  - The LU of "Algorithm choice" is the forward phase of that elimination, operation for operation: each entry of a later row evolves as `a = a - f·u` for the steps in order, `f` being the row's entry in the pivot column at that step and `u` the pivot row's entry after it was divided by the pivot. The solves apply the same operations to the right-hand sides (`x[i]` subtracts `f·x[j]` for `j` ascending and is divided by its pivot; back substitution with the unit upper triangle subtracts `u·x[j]` for `j` ascending), and `x @ A⁻¹` runs them as two triangular solves with the transposed factors. A multiplier that is exactly zero is skipped (which cannot change a finite result).
  - The Gram product `Aᵀ @ A` or `A @ Aᵀ` (`syrk`) computes one triangle by the sums of the product and mirrors it: entry by entry the naive sum.
- **Threads.** The kernels use `--threads=N` if `sky run` was given it, else `SKY_THREADS` (a whole number from 1 to 1024) if set, else the machine's available parallelism (the same setting as the SIR engine's, see "Threads"), and only above a size where it pays (about two million multiply-adds). Work is split by output entry, deterministically, which never changes an entry's order.

Effect on programs: matrix products, the inverse and the Cholesky solve give the same bits as before. `a @ b` of vectors, `dot` and `norm` of eight or more entries may differ from the earlier left-to-right sum in the last bit, and a sum of only negative zeros is now `0` instead of `-0`; no golden output in this repository changes.

### Relaxed numerics
Reproducible numerics cost speed: no fused multiply-add and a fixed order of every sum put Sky's matrix product at about half of `faer`'s (the missing FMA), and Apple's Accelerate, which runs on the AMX matrix coprocessor, about 14 times faster on an M2. **Relaxed numerics** are an opt-in mode that gives that speed up and says so: results are no longer bit-identical across machines, and are still correct to rounding error. The default does not change by a bit.

**Opting in.** Two places, both explicit, and nothing else:

- `sky run --numerics=relaxed <file>` for one run (`--numerics=reproducible` is the default, and is accepted). `sky check --numerics=relaxed` selects what `--explain` and `--emit=clif` describe; a check itself never executes code and is the same in both modes.
- `numerics = "relaxed"` in the project's `sky.toml` for everyone who runs the project (see "Editions"). The manifest has no tables, so the key is flat, next to `edition`. Any other value is a manifest error that names the value and the two words, never a silent default.

The flag wins over the manifest, both ways (`--numerics=reproducible` turns a relaxed project back to the reference, to compare against it). There is deliberately **no per-file pragma**: the mode is a property of a run, and a file that changed it would change what the files that import it compute, so a library could silently make its caller's results non-reproducible. There is **no environment variable**: nothing outside the command line and the project root may change what a program means (non-negotiable 2 makes the same argument for imports). `sky repl` is always reproducible. A flag given twice, or a value that is not one of the two words, is a usage error (exit status 2).

**What relaxed permits** (each is permission, not a promise; a kernel may still choose the reproducible answer):

1. **Fused multiply-add** (`fma`, one rounding for `a*b + c`). In the array kernels (NEON `vfmaq_f64` on aarch64, FMA3 on x86-64 when the CPU has it); in native code, where a scalar `a*b + c`, `a*b - c` or `c - a*b` becomes one `fma` when the product is used by nothing else and the sum is the next operation (only constants may sit between, so nothing that can fail or print is reordered); and in the elementwise `fused` kernels native code compiles, by the same rule.
2. **Reassociation of reductions.** `dot`, `a @ b` of two vectors and the sum of squares behind `norm` add their terms in whatever order is fastest on the machine (sixteen partial sums of the machine's vector width, combined by a fixed tree), instead of the eight-lane order of "Arrays: reproducible arithmetic".
3. **Vendor BLAS/LAPACK.** On macOS, Accelerate: `cblas_dgemm` for products, `cblas_dsyrk` for Gram products, `dpotrf` and `dpotrs` for Cholesky, `dgesv` (and `dgetrf` with `dgetrs`, for `x @ A⁻¹`) for the LU solves. Only for sizes that pay for the call (measured on an M2 Pro: products with every side at least 8 and at least 2¹³ multiply-adds, and matrix-vector products from 2¹⁵; LU solves of order 12 and up; Cholesky of order 32 and up); below that the fused kernels are as fast or faster. Only on macOS: elsewhere the fused kernels of `sky-linalg` run (an OpenBLAS binding is a possible later addition and would slot in the same place).
4. **Thread-count-dependent sums.** A dot product or norm of about a million terms or more is split across `--threads` threads and the pieces added in order, so its bits may depend on the thread count. (Matrix products and factorizations still split their output, which never changes an entry's order, so they do not depend on it; Accelerate manages its own threads and ignores `--threads`.)

The engines need not agree bit for bit in relaxed mode: native code contracts scalar `a*b + c`, the tree-walker and the SIR interpreter evaluate each scalar operation separately, and they may differ in the last bit; all three use the same relaxed array kernels, and all agree to the tolerance below. (A run that deoptimizes, see "Native code", continues on the SIR interpreter skipping the bytes native code wrote, so its output may mix the two.) Constant folding by the optimizer uses the interpreter's own operations, so `0.1 * 0.7 + 0.3` prints the same in both modes.

**What relaxed still guarantees.** Precisely, rule by rule:

- **Units and shapes are checked exactly as before.** Dimensions and shapes are settled by the checker (statically) or by the interpreters' dynamic checks, neither of which relaxed touches; a result has the dimension the reproducible run gives it.
- **Results are finite.** Every value a program computes must be finite, and an overflow is the same error. What relaxes: the check applies to the value the kernel produces, not to a rounding-order-dependent intermediate. So a fused product that overflows while its fused sum is finite (`x*y - z` with `z` nearly as large as `x*y`, beyond the largest double) is accepted in relaxed mode (native code replays the two operations unfused before it decides, so a product that overflows on its own still fails at the product), and a reassociated sum with huge cancelling terms may overflow in a partial sum where the fixed order did not, or the reverse.
- **Errors come in program order, and are the same errors.** Output written before a failure stays, the first failing operation in program order wins, and no operation with an effect moves. A singular matrix, a matrix that is not symmetric, and a matrix that is not positive definite are the same errors, with the same message, labels and notes, at the same place (the row of a failed Cholesky pivot is the same row). They are decided by Sky's tests, not the vendor's: symmetry is checked by Sky's own exact test before any vendor call; a vendor factorization is trusted only when its answer is clearly on the success side (LAPACK reports success, every pivot is more than 1024 times Sky's threshold `n·ε·max|aᵢⱼ|` above zero, resp. every Cholesky pivot is more than `1024·n·ε` of its diagonal entry, and everything is finite); on any doubt the reproducible kernel runs and decides. So a matrix the default rejects is rejected in relaxed mode with the default's diagnostic, and a matrix within a factor of 1024 of the boundary gets the reproducible verdict on macOS. Without a vendor library the fused kernels round differently, so a matrix within rounding error of the boundary can be accepted in one mode and rejected in the other; nothing farther from it can.
- **Accuracy claims stay sound.** `accuracy` budgets are proven for scalar code by the roundoff analysis, whose bounds hold when a multiply and an add round once instead of twice.

**The tolerance.** For a well-conditioned problem the relaxed result agrees with the reproducible one to the rounding error of the operation, and the tests pin it at **1e-12**: every entry of a product, Gram product or dot product within `1e-12 · Σ|aᵢₚ·bₚⱼ|` (the scale a sum of up to a thousand terms is entitled to), and every entry of a Cholesky factor or a solve within `1e-12` of the largest entry of the reproducible result. For an ill-conditioned problem no solver's answer is better than `cond · ε`, so the two agree to about that. Run-to-run, a machine with one thread count and one library gives the same answer, but Sky does not promise it for a vendor library.

**Reporting.** A relaxed run is never silent about it:

- `sky check --explain` starts with `numerics: relaxed (--numerics=relaxed | declared in <sky.toml>): fused multiply-add, reassociated sums and the platform's BLAS/LAPACK; results are not bit-reproducible across machines`, and notes each operation it applies to: `[NUM-001]` for a matrix product, dot product, norm or solve (with what may change and the tolerance), and `[NUM-002]` for each scalar `a*b + c` native code fuses (the last bit can differ from `--engine=ast` and `--engine=sir`). In the default mode `--explain` prints none of this, byte for byte as before.
- `sky run` ends a relaxed run that printed something with one line on stderr, after its diagnostics: `note: results computed in relaxed numerics (--numerics=relaxed): not bit-reproducible across machines` (`(sky.toml)` when the project asked). stdout is the program's alone, the exit status is unchanged, and a run that printed nothing says nothing.
- `sky check --emit=clif --numerics=relaxed` shows the `fma` instructions.

**Not affected.** The inverse (which the checker's numerical warnings also run, so "this matrix is singular" at check time stays the verdict of `sky run`), ODE solvers, constant folding, and tuning (which never changes results in either mode).

### Differential equations
An `equation` says what changes and how fast, in the notation of a textbook; `solve` runs it. The solver (`sky-ode`) picks the method from what the program declares, and says why.

```sky
GM = 1.327e20 m^3/s^2
equation orbit(t: s):
    r: Vector[2] m
    v: Vector[2] m/s
    r' = v
    v' = -GM * r / norm(r)^3

sol = solve orbit from 0 s to 1 yr with r = [1 AU, 0 m], v = [0 m/s, 29.8 km/s]:
    tolerance 1e-9
    conserve energy = 0.5 * norm(v)^2 - GM / norm(r) within 1e-6
print(sol.r, sol.v)
print(explain(sol))
```

```text
equation := "equation" NAME "(" NAME ":" type ")" ":" NEWLINE INDENT item { item } DEDENT
item     := NAME ":" type              -- a state variable
          | NAME "'" "=" expr          -- its derivative
          | NAME "=" expr              -- a local name
solve    := NAME "=" "solve" NAME "from" expr "to" expr
            [ "with" NAME "=" expr { "," NAME "=" expr } ]
            [ ":" NEWLINE INDENT option { option } DEDENT ]
option   := "tolerance" expr
          | "conserve" NAME "=" expr [ "within" expr ]
```

**Syntax.**
- The `'` after a name is the derivative mark: `r'` is dr/dt. It is lexed only directly after a name (or another `'`); anywhere else a `'` is still the "strings use double quotes" error. Second derivatives (`r''`) are a parse error for now: write the velocity as a state variable of its own, as above, which is also what lets the solver see the second-order structure.
- `equation orbit(t: s):` names the equation and its independent variable, with its type (a scalar; a unit such as `s` for time, but any dimension is allowed). The body has three kinds of line, in any order: declarations of the **state variables** (`r: Vector[2] m`, a type as in "Type annotations", with a fixed size), **derivatives** (`r' = v`), and **local names** (`a = -GM / norm(r)^2`), which later lines may use. A `solve` is a statement of the form `name = solve ...`, because it gives a value; the block with the options is optional. An equation is a value that is bound to its name like a `def` and may be defined anywhere a statement may.
- `from`, `to`, `with`, `within`, `tolerance` and `conserve` are ordinary names that mean something only inside these two statements (`to = 3` still works); the keywords are `equation` and `solve`. Inside a `solve`, a number is never followed by a unit called `to`, `with` or `within`, so `from 0 to 1 s` parses (and is a check error: `0` is not a time).
- `norm(x)` and `dot(a, b)` are builtins (see "Arrays"), so equations of vectors read like the physics.

**Typing.** Dimensions are checked, and so are shapes.
- Every state variable has one derivative equation, and `x'` has the dimension of `x` divided by that of the independent variable and the shape of `x`. The right side is typed as any expression is, with the state variables, the independent variable, the local names above it, and the names in scope where the equation is written. Like a function body, it reads those names' values when it runs, that is at each `solve`, not where the equation is written: `k = 2 s^-1` between the equation and the `solve` (a parameter sweep in a loop, say) is what the solve uses. Functions it calls are bound where it is written, as for a `def`. And as for a function, a later binding of a name it reads must keep the type it was checked with (see "Calls bind where the caller is defined"). The error names both: ``error: `v'` is a quantity of dimension L·T⁻², but the right side is a velocity``, with the declarations of `v` and `t` as labels and the derivation of the right side's dimension. A missing equation, a second equation, and a derivative of something that was not declared are errors.
- In `solve`, the bounds have the dimension of the independent variable, and each state variable gets exactly one initial value of its declared dimension and shape (`with r = ..., v = ...`, in any order). `tolerance` is a plain number, and so is `within`. A `conserve` expression is typed with the state variables and the independent variable in scope; it must be a scalar (reduce a vector with `norm` or `dot`), and its dimension is the dimension of the quantity. The name of a conserved quantity is new: it may not be `t`, a state variable, or another quantity.
- The initial values, bounds and options are evaluated in the scope of the `solve`, so they may use any names there.

**What a solve does.** The values are in SI, as everywhere. The state variables are flattened into one vector of `f64` (a scalar is one entry, a vector or matrix its entries row-major), and `sky_ode::solve` integrates it from the start to the end; the right sides run on the interpreter. The tolerance is the relative tolerance (`atol` is a thousandth of it) and must be between 0 and 1; without one, the solver's default applies. A conserved quantity is monitored: its drift `|Q(t) - Q(0)| / |Q(0)|` is reported in the explanation, and with `within` a larger drift stops the solve with an error. A quantity that is zero by construction (the angular momentum of the figure-eight orbit, the momentum of a system at rest) starts at rounding noise, and a drift relative to that would be noise divided by noise; so when `|Q(0)|` is at most `1e-12` of the size of its terms, `S = Σ |y_j ∂Q/∂y_j|` over the state at the start, the drift is relative to `S` instead, and the explanation says so ("relative to the size of its terms, since it starts at 0"). When the automatic choice shrinks a symplectic step for a quantity's drift and a smaller step does not reduce it (by at least a factor 0.9), that drift is the rounding in computing the quantity: it stops setting the step, and the explanation says so; it is still reported. Time runs forward (`to` may not be before `from`).

**Second-order structure.** When every state variable is either a position `q` with `q' = v` (exactly a bare name, no arithmetic) or the velocity `v` it names, and no `v'` mentions a velocity (directly or through a local name), the system is `q' = v`, `v' = a(t, q)`. The solver is then told (`Structure::SecondOrder`) and the state is laid out `[q..., v...]`, so it may pick a symplectic method. Drag (`v' = -k * v`) has no such structure. `sky_types::analyze_equation` is the single reading of this, used by the checker and the interpreter.

**Results.** `solve` gives a solution value, and its **attributes** are read with `sol.name`: the final value of the independent variable (`sol.t`), of each state variable (`sol.r`), and of each conserved quantity (`sol.energy`), typed as what they are (`sol.r` above is a `Vector[2]` of lengths). This is the smallest design that fits the language: attribute reads were already in the grammar (and rejected everywhere), so nothing new is needed but the rule that a solution has them. A solution has no other attributes, and nothing else has any: `x.y` on another value is still an error at run time. Not in this version, and left to a later one: samples at chosen times (`at [...]`), a dense solution `sol(t)`.

**Explanations.** The solver states which method it used and why (structure, tolerance, conserved quantities, and what it observed: steps taken, drift). Two ways to see it:
- `explain(sol)` is a builtin that gives the explanation as text, one sentence per line; `print(explain(sol))` writes it. The program decides whether it is printed, so a script's output is never noisy by default.
- `sky check --explain` prints, for every `solve`, a note with what the checker itself found: whether the equation is second order (and which variables are positions and velocities), the tolerance, and the conserved quantities, and that the method is chosen when the program runs. It never runs the solver, so it does not say which method that is.

**Errors at run time.** A failing solve is a runtime error on the `solve` statement: "cannot solve `orbit`: ..." with the solver's message (gave up after too many steps, the solution overflowed, a conserved quantity drifted more than `within`). An error inside a right side (a division by zero, an overflow) is reported where it happens, on that expression, with the `solve` as a secondary label and the time. A tolerance outside 0 and 1, and a time span that runs backwards, are errors on their expressions.

**Engines.** Equations run on the tree-walking interpreter only: lowering an `equation` or a `solve` is a `LowerError` ("differential equations are not supported by SIR yet"), because the solvers call back into the evaluator for every right side and SIR has no such operation. So `sky run` (the `auto` default) runs them by falling back to the tree-walker without a word, and `--engine=sir` refuses the program with `error: cannot run on SIR: ...`. An equation defined on one REPL line can be solved on the next.

**Why this shape.** The candidates for the derivative were `dr/dt = ...`, `d(r)/dt`, `D(r) = ...`, and `r' = ...`; the prime is what a physicist writes on a blackboard, it is one token, and it puts the variable and its equation on one line. Declaring the state and time with their units in the header makes the dimension rules checkable without inference. Initial values, the span, and the options belong to `solve`, not to the equation, so one equation can be solved many times.

### Numerical warnings
`sky check` teaches two things about floating-point arithmetic. Both are **warnings**: they never fail a check (exit status 0), they never change what a program does, and each is reported once per source site. At most 100 are reported per check.

#### Condition numbers of constant matrices
When a matrix the source spells out entry by entry (a square literal of at most 64 by 64 numeric literals, with units allowed) is inverted or used to solve a system (`A⁻¹`, `inv(A)`, `A⁻¹ @ b`), the checker computes its 2-norm condition number κ(A) = σmax/σmin from a dense singular-value iteration. This is arithmetic on constants the source spells out, the same kind as the tag proofs, and runs no user code. The operand is constant if it is a literal, or a name whose **only** binding in the module is `A = <literal>` (or `A: T = <literal>`). Any other binding of the name anywhere (a second assignment, `A *= 2`, a parameter or a local of a `def` with that name) makes it not constant, whatever path it is on; inside a `while` body only literals are analyzed, and inside a `def` only the function's own locals. These rules over-approximate on purpose: a warning must be about the matrix `sky run` will invert.

- **κ > 1e8** warns, with the digits an `f64` may lose: `estimated condition number κ(A) ≈ 3.2e14: about 14 of 16 significant digits may be lost` (`floor(log10 κ)`, at most 16). The note says what κ means, and the help suggests rescaling, a better-posed formulation, or (later) higher precision. If the ill-conditioning is mostly the size of the rows and columns (`diag(1, 1e10)`: scaling them to unit maximum entry lowers κ 100-fold or more) the help says so and gives the scaled κ. Known values: Hilbert 5 by 5 is 4.8e5 (quiet), Hilbert 10 by 10 is 1.6e13 (13 of 16 digits).
- **Singular** matrices get a stronger, separate warning: `this matrix is singular, so it has no inverse`, and it is the same test `sky run` applies. The checker calls the interpreter's own `linalg::inverse` (the code lives in `sky-types` and `sky-interp` re-exports it), so the two cannot disagree: a pivot that is zero, or no larger than `n · ε · max|aᵢⱼ|`, is singular in both. It is a warning and not an error because the checker does not know whether the line runs (a function may never be called).
- A matrix larger than 64 by 64, or with a non-constant entry, is not analyzed and gets no warning.

#### Catastrophic cancellation
The checker recognizes these expressions (the operands that must repeat are compared as source text, ignoring spaces and outer parentheses; `sqrt`, `exp` and `log` must be the builtins, not a program's own definitions) and shows the stable form in the help:

| written | stable form |
| --- | --- |
| `sqrt(x^2 + c) - x` (also `c + x^2`, `x^2 - c`) | `c / (sqrt(x^2 + c) + x)` |
| `(1 + x) - 1` (also `(x + 1) - 1`) | `x` |
| `x^2 - y^2` (also `x*x - y*y`) | `(x - y) * (x + y)` |
| `exp(x) - 1` | `expm1(x)` |
| `log(1 + x)` (also `log(x + 1)`) | `log1p(x)` |
| `(-b + sqrt(b^2 - 4*a*c)) / (2*a)` (also `sqrt(D) - b`, `-b - sqrt(D)`) | `2 * c / (-b - sqrt(b^2 - 4*a*c))` |

`expm1` and `log1p` are builtins, and the help says `write expm1(x)` or `write log1p(x)` with your own argument. With a variable operand the lint fires on the pattern and the note says when it cancels (whether it does depends on values the checker does not have). When the operands that matter are numeric constants, the checker judges by value and warns only when about three digits or more are lost: `exp(1) - 1` and `(1 + 5) - 1` are quiet, `exp(0.0000001) - 1` warns. An expression with a type error inside it is not linted.

#### No way to silence a warning (yet)
There is no pragma. Every pattern has a stable spelling that is also the fix, so a silenced site would be one where the user knows the operands are far apart, and writing `(x - y) * (x + y)` costs nothing there either; the lint is meant to be rare and confident, so a false positive is a bug to report, not to hide. A comment pragma would make comments meaningful to the parser, which they are not in v0.1, and it should be designed once for every warning class (shadowed constants too) and not for these alone. Revisit when a warning appears that has no rewrite to offer.

### Accuracy budgets
`accuracy x within 1e-12` states how accurate a number must be: the **error budget** of the value `x` holds at that point of the program. It is a statement, not a comment and not a type: it is checked, and it says something about the program.

```text
accuracy y within 1e-12        # relative: |computed - exact| <= 1e-12 * |exact|
accuracy d within 10 nm        # absolute, in the unit written
```

- A bare number is a **relative** error, so it means the same for a value of any unit. A number with a unit is an **absolute** error and must have the value's dimension (`accuracy t within 2 m` for a time is a check error). The tolerance must be a positive number literal.
- `x` must be a name in scope that holds a single number (not a vector, matrix, Bool or function). The budget is about the value `x` has *at the statement*: `x = 1; accuracy x within 1e-3; x = 2` is about the first value.
- `accuracy` and `within` are contextual words: only a statement that starts with `accuracy` and a name is this one. Both stay ordinary identifiers everywhere else (`accuracy = 2` is an assignment).
- Running a program ignores the statement. It changes no value and costs nothing.

"Exact" means the real-number result of the same program: every operation computed without rounding, from the same inputs and literals (a literal is the `f64` it holds). `sky check` compares the `f64` that `sky run` computes with it using the roundoff analysis (`docs/design/ir.md`, "Error budgets and roundoff") and reports one of three outcomes:

| outcome | report |
| --- | --- |
| **proven**: the analysis bounds the error below the budget | a note, shown only under `--explain`: ``x` is accurate to 3.3e-16 relative, within the budget 1e-12` |
| **unproven**: it can neither prove nor refute the budget | a **warning** naming the operations that dominate the error (a catastrophic cancellation, a function that magnifies error, a loop of unknown length), linking to the cancellation warning when that reports the same expression |
| **violated**: the analysis proves the error exceeds the budget | an **error** (exit status 1): the `f64` result is provably too far from the exact one |

Proof is conservative and never wrong about what it claims: an unproven budget may still hold. What the analysis assumes: `+ - * /` and `sqrt` are correctly rounded, and the platform's math library is within four ulps (`erf`, which Sky implements itself, sixteen). A violation is proven only where every input is a constant, because then the exact value can be enclosed to about 27 digits. Inputs of unknown value (a function's parameters, when the function is never called) are analysed as arbitrary finite numbers, which rarely proves a budget: the analysis follows a call with the arguments it is called with. A loop is followed while its trip count is known (a counted `for` over constants) and is otherwise unbounded. A budget in code the analysis cannot lower to SIR yet is reported as not checked.

With `--explain`, `sky check` also states how accurate each printed number is: ``printed value of `0.1 + 0.2` is accurate to within 9.3e-17 relative``.

Nothing chooses a precision from a budget yet: that needs code generation (Phase 4 of the roadmap).

### Performance contracts
What a function costs is part of its contract (ROADMAP idea 86): `cost flops <= 2 * N^3` says a function does at most `2·N³` floating-point operations on an `N`-by-`N` matrix, and `sky check` **proves it or refutes it** from the program, without running it. The cost is a polynomial in the sizes of the arrays, the same sizes the checker already tracks (`Matrix[N, K]`).

```text
cost_line := "cost" MEASURE ( "<=" | "==" ) bound NEWLINE
MEASURE   := "flops" | "bytes_read" | "bytes_written" | "bytes" | "allocations" | "allocated_bytes"
def_stmt  := "def" NAME "(" ... ")" [ "->" type ] ":" NEWLINE INDENT { contract_line | cost_line } statement+ DEDENT
```

```sky
def gram(A: Matrix[N, M]) -> Matrix[M, M]:
    requires len(A) > 0
    cost flops <= 2 * N * M^2
    return Aᵀ @ A

def step(v: Vector[N], w: Vector[N]) -> Vector[N]:
    cost flops == 2 * N
    cost allocations == 1
    return v + 2 * w
```

**Why this syntax.** A `cost` line sits where `requires` and `ensures` sit, in the header of a `def`, and reads like them: a word, then a claim. `<=` states an upper bound (what almost every claim about cost is), `==` an exact count (`cost allocations == 0` is the one people ask for). There is no `>=`, because a lower bound on cost is not a promise anyone wants, and no `<`, so that there is one way to write a bound. The measure is a word (`flops`) and not a call (`ensures cost(flops) <= ...`): a cost is a fact about the whole function that the checker proves, and an `ensures` is a condition on values that a run checks; dressing one as the other would make it look as if it ran.

**`cost` is a contextual word.** Only a statement that starts with `cost` and a name is a cost line, which is never a valid expression today, so `cost = 3`, `cost(2)`, `x = cost + 1`, a parameter or a function called `cost`, and a variable called `flops` all stay what they were. The line may be anywhere in the header, among the `requires` and `ensures` lines, in any order; after the first other statement of the body, or anywhere else, it is a parse error ("`cost` is only allowed at the start of a function body"). A function may have any number of cost lines, also of one measure. A cost line does nothing when the program runs: both engines skip it, as they skip `accuracy`.

**Decision: static cost only, no run-time budget.** The alternative considered was a time budget checked when `sky run` executes the function (`runtime <= 10 ms`, failing or warning when exceeded). It is not in v0.1, for these reasons. Time is noise: it varies with the machine, its load, the cache and the engine, so the same program would pass on one day and fail on another, and a contract that is sometimes false is not a contract (a run that passes `requires` and `ensures` is the run the author reasoned about). A warning-only budget would be a comment that sometimes prints. `sky check` can say nothing sound about a time, and it never runs user code (Security non-negotiable 1). And it would need a clock in the interpreter, which the determinism goal (idea 52) rules out for the language itself. What a run-time budget is for, catching a regression, is better done by comparing measurements (`sky-bench`, ROADMAP idea 87) than by a pass/fail flag in the source. So `cost runtime <= 10 ms` is a parse error whose help says this. What can be promised, and proven, is a count of operations and bytes, which is the same on every machine and in every run.

**The measures.** All are for one call of the function, in the model below.

| measure | what it counts |
| --- | --- |
| `flops` | floating-point operations (weights below) |
| `bytes_read` | bytes of arrays that array operations read, 8 per entry |
| `bytes_written` | bytes of arrays that array operations write |
| `bytes` | `bytes_read + bytes_written`: the memory traffic |
| `allocations` | arrays created |
| `allocated_bytes` | bytes of the arrays created |

**The bound** is a polynomial in the sizes of the function's parameters: numbers (`2`, `0.5`, `1e9`), the names of sizes (the `N` and `M` of `Matrix[N, M]` in the annotations of the parameters), `+ - *`, `^` with a whole exponent (at most 64) and `/` by a number, in parentheses as needed. Coefficients are exact fractions. Anything else is an error at the bound: a name that is not a size of that function ("`K` is not a size of `f`", with the sizes it has), a division by a size, `sqrt`, a comparison, and a number written against a name (`2 N` reads as two newtons, like any unit literal: write `2 * N`). **Domain:** a bound holds for every size **from 1 up**, because an array has at least one entry on each axis. So `N^2 <= N^3` is true, and `2·N³ + 5·N` is not within `2 * N^3` (at `N = 1` it is 7 and 2): lower-order terms count. A contract is not asymptotic.

**The cost model** (`sky_ir::cost`) reads the program as SIR after the optimization pipeline (`sky_opt::default_pipeline`), which is what the SIR engine, and later a code generator, run: a fused kernel is one pass over its operands with one allocation, and a positive-definite solve is a Cholesky solve. It counts what the reference implementation does, not the time a machine takes, by these rules:

- **Flops.** `+ - *` and `/`, negation, `sqrt`, `abs`, `min`, `max`, `floor`, `ceil`, `round` and `sign` cost 1 per scalar operation, and `N` for an elementwise operation on a vector of `N` (a scalar operand of an array operation is broadcast at no extra cost). The entry-by-entry operations of "Arrays: entry by entry" count the same way: `a * b` of two arrays of `N` entries is `N`, `sqrt(v)` is `N`, and `exp(v)` is `20 N`. The other math functions (`exp`, `log`, `sin`, `atan2`, `erf`, ...) and `a ^ b` with a computed exponent cost 20, the rough cost of a library call. `a ^ n` with a constant whole exponent is the multiplications of square-and-multiply (`x^2` is 1, `x^3` is 2, `x^5` is 3) plus a division for a negative one; `x^(1/2)` is 1. Comparisons, `len`, `print` and the checks of contracts cost none (a contract's condition is computed by operations that count).
- **Matrices.** `A @ B` with `A` of `(n, k)` and `B` of `(k, m)` is `2·n·k·m` (a vector is the matrix with an axis missing). The inverse of an `n × n` matrix is `2·n³`. A Cholesky solve of `A x = b` is `n³/3 + 2·n²` (`2·n²·k` for `k` right sides), in two allocations: the result and the factor. A fused kernel is its body per entry (`v + 2 * w` is `2·N`, in one allocation of `N` floats, where the unfused chain has two of each).
- **Memory.** Only arrays count: an operation on arrays reads its array operands and writes and allocates its result; an array literal, `zeros`, `identity`, a transpose, a slice and a row are writes and allocations of their entries (a transpose is counted as a copy, which is what the reference implementation does; a later backend may do better, and a contract proven against this model then holds all the more). A scalar lives in a register and costs no traffic.
- **Loops.** A loop whose trip count the model can name multiplies its body: `for i in range(10)`, `range(len(v))` (the size `N` of a `Vector[N]`), with a start and a constant step (`range(1, len(v))` runs `N - 1` times, `range(0, len(v), 2)` at most `N/2 + 1`), and a `while` on an index that a constant step advances. The index's own increment is bookkeeping and costs nothing. A `break` bounds the count from above only. Any other loop is **unbounded**, and the cost says where: `unbounded (loop at line 7)`. A loop whose body costs nothing costs nothing however long it runs.
- **Branches.** An `if` costs its condition plus the branch that runs. The model's cost is the **maximum** of the branches (the cheaper branch is the lower bound, so the cost is then a range, "at most").
- **Calls.** A call costs the callee's cost with the callee's sizes replaced by the sizes of the arguments. Recursion is unbounded, and so is an operation on a value the checker gave no shape (an unannotated parameter): annotate the parameters to get a bound.

**What the checker says.** `sky check` compares each cost line with the model and reports one of three outcomes, as for an accuracy budget:

| outcome | report |
| --- | --- |
| **proven**: the cost is within the bound for every size from 1 up | a note, shown only under `--explain`: ``gram` costs 2·M²·N flops, within `2 * N * M^2`` |
| **refuted**: some size makes even the cheapest run cost more than the bound (for `==`, a different count) | an **error** (exit status 1): the cost, sizes that show it, the term of the cost that the bound does not cover, and the operation that costs the most there |
| **unproven**: the model cannot decide (an unbounded loop, recursion, an unknown shape, a comparison it cannot settle) | a **warning** naming why, at the loop or the call |

```text
prog.sky:3:5: error: `mm` costs 2·K·M·N flops, which is more than `2 * N^3`
  |
3 |     cost flops <= 2 * N^3
  |     ^^^^^^^^^^^^^^^^^^^^^ the cost is more than this
4 |     return A @ B
  |            ----- `A @ B` costs 2·K·M·N flops
  = note: for example with K = 2, M = 1 and N = 1: it costs 4 flops, and the contract says 2
  = note: the dominant term of the excess is 2·K·M·N, which the bound does not cover
  = help: the cost is exactly 2·K·M·N: write `cost flops <= 2 * K * M * N`
```

```text
prog.sky:4:5: warning: cannot prove that `until` meets `cost flops <= 100 * N`
  = note: the cost has no upper bound: loop at line 4
```

**Soundness.** Both a proof and a refutation are claims about the model, and each is made only where it is exact. *Proven* is claimed only when the upper bound of the cost is shown to be at most the bound for all sizes from 1 up. The test substitutes `x = 1 + y` for each size and asks that every coefficient of the difference be non-negative, which is sufficient (`N² <= N³`, `3·N² <= N³ + 2·N²`) but not complete, so a true contract may stay *unproven* and a false one is never *proven*. *Refuted* is claimed only with a witness: sizes at which the lower bound of the cost (the cheapest run) exceeds the bound, evaluated in exact rational arithmetic, tried over 1, 2, 3, 5, 10, 100, 1000, 10^4 and 10^6 (all sizes alike when there are more than four). Coefficients are `i64` fractions, and terms and degree are capped (256 and 64): arithmetic that would overflow makes a cost unbounded and a comparison unproven, never a wrong answer. The bounds are about runs that finish: a call that stops with an error (a division by zero, a failed `requires`) has done only part of the work. Whatever is not decided is a warning; nothing is silenced.

**`sky check --explain`** also reports the cost of every function that has any, even without contracts, so that it finds the hot spots:

```text
prog.sky:2:5: note: cost of `gram`: 2·M²·N flops, 2 allocations (M·N + M² floats in all)
  |
3 |     return Aᵀ @ A
  |            -- hot spot: `Aᵀ` costs 16·M·N bytes of memory traffic
  |            ------ hot spot: `Aᵀ @ A` costs 2·M²·N flops
  = note: memory traffic: 24·M·N bytes read, 8·M·N + 8·M² bytes written
```

An exact cost is a polynomial, a range is "at most ...", and a cost with no bound reads "cost of `f`: unbounded (loop at line 7)". The hot spots (up to three, and only for a function whose cost depends on a size) are the operations that cost the most, each with what it contributes, loops around it included. The top-level code is not reported. If the program checks but cannot be lowered to SIR yet, a function with cost lines gets a warning that its contracts were not checked ("the cost contracts were not checked: ...") and `--explain` says nothing about costs.

## Running programs
`sky repl` is a tree-walking interpreter over the checked AST. `sky run` has three engines, the same tree-walker, SIR and native code (see "Engines" below), and they behave identically. Vectors and matrices run: an array is its dimension, its shape (one or two axes) and its entries as `f64`, row-major. It is not fast, and that is deliberate (see Goal).

### `sky run <file>`
- The file is opened, size-capped and discovered exactly as `sky check` does, then lexed, parsed and checked.
- **Any error stops the run before anything executes**: the diagnostics go to stderr and the exit status is 1, so a `print` before a type error on a later line prints nothing. Warnings (such as a confusable identifier) are shown and the run continues.
- Program output (`print`) goes to stdout. Diagnostics, including runtime errors, go to stderr. A runtime error is an ordinary diagnostic on the failing expression, exit status 1. Output written before the failure stays.
- Top-level expression statements are evaluated and not printed, as in a Python script; only `print` writes.
- Blocks run as in Python: `if`/`elif`/`else`, `while` and `for` with `break` and `continue`, `a if c else b`. `for` binds its variable at the start of each iteration (a dimensionless number for `range`, an entry or a row for an array). A `def` binds a function value; a call evaluates its arguments in the caller, then runs the body with the parameters as locals. Inside a function, a name is read from its locals and then from the module; assignments make locals. A *call* of a name in a function body is the exception: it runs the definition in scope where the function was defined (see "Functions", "Calls bind where the caller is defined"), each `def` capturing the functions visible when it runs.
- Recursion is limited to 1000 nested calls ("recursion is too deep"). Independently, the interpreter measures how much of its stack it has used and stops with "the program nests too deeply for the interpreter" before it could overflow, which a debug build reaches sooner. Neither is ever a crash.
- Exit status: 0 on success, 1 on a check or runtime error, 2 for a usage error or an unreadable file.
- **Engine.** `sky run [--engine=auto|ast|sir|native] [--threads=N] [--numerics=reproducible|relaxed] <file>` (the flags may also follow the file); see "Engines", "Threads" and "Relaxed numerics".
- `sky check` never executes code and is unchanged (non-negotiable 1).

#### Engines
A file that checks without errors runs on one of three engines, and the result must not depend on which:

- **`native`** compiles the optimized SIR (the module `sir` runs) to machine code for the CPU it runs on, in memory, through Cranelift (`sky-jit`), and calls it. It has the SIR engine's behaviour to the byte (see below), and is much faster on scalar code (over 100 times on a loop of arithmetic with units, where the SIR interpreter is no faster than the tree-walker); code that works on arrays calls the same runtime functions the interpreters do, so it gains less. A program it cannot compile is refused (`error: cannot run natively: <why>`, exit status 1), as `sir` refuses a program that does not lower; `sky check --emit=clif` prints the Cranelift IR it compiles. See "Native code" below.
- **`sir`** lowers the checked program to SIR, runs the default pass pipeline (`sky_opt::default_pipeline`) with verification after every pass, and executes the result on the SIR reference interpreter.
- **`ast`** is the tree-walking interpreter over the checked AST. It stays as the oracle that the SIR engine is tested against (`docs/design/ir.md`).
- **`auto`**, the default, is `native` when the program compiles, `sir` when it lowers but native code cannot take it, and `ast` when it does not lower: a lowering error (a construct SIR cannot express yet) or a compile refusal is not reported, the program just runs on the next engine (`sky check --explain` says in one note when a program runs on the tree-walker, and why). Nothing has been printed at that point, because lowering and compiling happen before the run. `--engine=sir` reports a program that does not lower as `error: cannot run on SIR: <why>` and `--engine=native` as `error: cannot run natively: <why>` (exit status 1); `--engine=ast` never lowers. Any other value, or the flag twice, is a usage error (exit status 2).

Identical means the same stdout, the same stderr (the runtime error's message, span, labels and notes), and the same exit status, including a closed stdout (`| head`), which is exit status 1 without a diagnostic. One mechanism and one rule keep the SIR engine there:

- **Programs SIR would run differently stay on the tree-walker.** A program that uses uncertainty (see "Uncertainty"; SIR has no uncertain value), and a program whose lowered SIR does not verify. (A program with an input declaration, `A: Matrix[3, 3]` with no value, runs on SIR: the declaration is an `input` operation that fails where it is reached, after any earlier output.)
- **A runtime error on SIR is labelled by the operands' spans.** A SIR operation records, besides its own span, the source span of each operand at the place it reads it (`operand_spans`: the `b` in `a / b`, the `i` in `v[i]`, which is not where `b` or `i` was bound), and lowering fills them in with the spans the tree-walker uses. The SIR interpreter builds the error through the same constructors as the tree-walker (`sky_interp::arith` and `array`), so message, primary span, secondary labels (`this is zero`, `valid indices are 0 to 2`), notes and help are the same, and `sky run` prints SIR's diagnostic as it is; nothing is run twice. Passes keep the spans sensible: a rewrite that reads an operand where the original did keeps its span, a rewrite that merges operations joins the operation spans, and a pass that cannot (the e-graph's extraction) leaves them out, so the diagnostic falls back to the operation's own span, which is then the only difference from the tree-walker. A unary `+` of a value the checker could not type is checked at run time (`expect.number`), as `sky run` checks it.

The one intended difference is resource limits: each engine meters its own Rust stack, so a program that recurses very deeply may end with "the program nests too deeply for the interpreter" on one and "recursion is too deep" on the other (in a debug build the tree-walker's frames are bigger, so it stops sooner).

#### Threads
On the SIR engine and on native code, work that cannot change what the program observes may run on several threads: big elementwise array kernels, and independent calls of pure functions (no `print`, no recursion, enough work to pay for it). `--threads=N` (or the environment variable `SKY_THREADS`; the flag wins; the default is the number of cores) sets how many; `--threads=1` is the sequential interpreter, and anything else that is not a whole number from 1 to 1024 is a usage error (exit status 2, as is the flag twice). **The output never depends on N**: the same stdout, the same stderr and the same exit status, because the first failure in program order always wins (across the elements of a kernel the lowest failing element of the earliest failing operation; across calls the earliest in program order) and nothing that prints ever moves. The tree-walker is sequential. Native code (`--engine=native`, and `auto` when the program compiles) splits the same kernels into the same chunks (a compiled kernel per chunk) and starts the same independent calls on workers, with the same rule for failures; it differs only in what is worth starting: native code runs an operation so much faster than the interpreter that a call must be estimated 64 times as expensive, and a kernel have 128 times the work, to pay for a thread (`sky check --explain` says what native code splits and starts). `sky build` executables are single-threaded. `sky check --explain --threads=N` says what would run in parallel (`[PAR-001]` a kernel, `[PAR-002]` independent calls) and what would not and why (`[PAR-003]`). See "Automatic parallelism" in `docs/design/ir.md`.

**Equations do not lower yet.** A program with an `equation` or `solve` is a `LowerError`, so it runs on the tree-walker: `--engine=auto` falls back to it and `--engine=sir` and `--engine=native` report it (see "Differential equations").

Derivatives (`derivative(f, x)(args)`) are computed on SIR in every engine. Under `ast` the tree-walker asks SIR for the derivative function (`sky-derive`); under `sir` and `native` the lowered program calls it.

#### Native code
The native engine translates every SIR function to a Cranelift function (`crates/sky-jit`, `module.rs`) and compiles the module in memory with Cranelift's `opt_level = speed`, then calls `<main>`. What it promises is that it does what the SIR interpreter does: the same stdout, the same runtime error as a whole diagnostic, the same order of effects.

- **Representation.** A value's representation follows from its type. A scalar number is an `f64` (its dimension is the type's, so it is not stored), a Bool is an `i8`, and everything else (arrays, strings, `none`, and any value of type `unknown`) is a handle to a value the runtime owns. Scalar arithmetic and comparison, `if`, `while` and calls between functions are machine code. Arrays, printing, contracts, `fused` and every operation on a value of unknown type call the runtime, which runs the same functions the SIR interpreter calls (`sky_interp::arith`, `array`, `contract`, `math`), so their results and errors are the interpreters'.
- **Arithmetic.** `+ - * /`, negation and `sqrt` are the IEEE operations and give the interpreters' bits; the compiler never contracts a multiply and an add into a fused multiply-add, except in relaxed numerics (`--numerics=relaxed`, see "Relaxed numerics"), where a scalar `a*b + c` may become one `fma` and the results may differ in the last bit. The checks come in the interpreters' order (dimensions, which are static; a zero divisor; a result that is not finite). Small integer powers make the multiplications `powi` makes; the math functions that are not exact operations (`sin`, `exp`, `round`, ...) call `sky_interp::math::apply_f64`, the numeric core of `apply`. When a check fails, generated code calls a runtime function that re-runs the operation on the same operands the interpreters' way, which builds the whole diagnostic, and returns a status up the native stack.
- **Values of unknown type.** A value the checker could not type (an unannotated parameter, a call through one) is checked when it flows into a slot a declaration types (`-> m` on a function whose body computes an unknown): a typed scalar is a bare `f64`, so if the value is not a number of that dimension the interpreters would go on with something native code cannot represent. Then native code *deoptimizes*: it stops with no diagnostic, and the run continues on the SIR interpreter from the start, skipping the output native code already wrote. Programs are deterministic and output is their only effect, so the result is the interpreter's exactly. `sky run` does this itself; it is not an error.
- **Threads.** Native code honours `--threads=N` and `SKY_THREADS` (see "Threads"; 1 is sequential): a big `fused` kernel or elementwise array operation runs in deterministic chunks on a pool, and independent pure calls of a window are started on workers, each with a runtime state of its own. The output, the error and its order are the sequential run's whatever N is. A run that deoptimizes continues on the SIR engine with the same `--threads`.
- **Limits.** Calls nest at most 1000 deep, counted as the SIR interpreter counts them (the entry call does not count), with the same "recursion is too deep" error at the same call. Native code also stops at the interpreters' stack budget, checked at the entry of each function that makes calls; a native frame is small, so the depth limit is what a program meets first, except for a function with thousands of live values.
- **What it does not compile.** A program that does not lower (see above) has no SIR; a module that does not verify is refused. Nothing else is refused: every SIR operation compiles.

### `sky repl`
- Reads stdin one input at a time. Each input is lexed, parsed and checked against the checker environment the earlier inputs built, then run against the runtime bindings they built.
- A top-level expression prints its value (like Python's REPL); an assignment prints nothing.
- **Multi-line input.** An input is one line, or several. It continues on the next line when
  - its last logical line ends in `:` (a block header: `def`, `if`, `elif`, `else`, `while`, `for`), or
  - a `(` or `[` is still open (an empty line inside brackets does not end it), or
  - it holds a block, that is, an indented body. A block ends at an **empty line** (one with only spaces), as in Python.

  An empty line also submits a header that has no body, which is then the usual error ("expected an indented block"), so the REPL cannot trap the user behind `...`. Any other lexical error (a bad character, an unterminated string, a stray `)`) does not continue: the input is run and the error reported. At end of input (Ctrl-D) an unfinished input is run as it stands, so its error (such as an unclosed bracket) is shown. A `def` is complete only after its empty line, so `def f(x: m) -> m:` then `    return x` then an empty line defines `f`.
- **Errors are reported against the whole input.** Line numbers count from the first line of the input that was submitted (`<repl>:3:11`), not from the start of the session. A runtime error inside a function that an earlier input defined is shown against that input, named `<repl:N>` for the N-th input the session accepted.
- An input with any error changes nothing, however many lines it has. The checker environment is replaced only after a clean check, the runtime bindings are restored if the run fails part way (a loop that fails on its third pass leaves nothing its first two passes bound), and the input joins the session only after it ran, so `a = 1` followed by `b = a / 0` on one line leaves neither bound, and a `def` whose body has a type error defines nothing.
- **Functions and derivatives.** A function defined in one input can be called in any later one, and `derivative(f, x)(args)` works for it. Derivatives run on SIR, which lowers a program's `def`s together, so the REPL keeps the text of every accepted input (its history) and, on the first derivative an input asks for, lowers the history followed by the current input as one program (parsed as one source, so every span is a session offset and two inputs never share one). Nothing is lowered for a session, or an input, that does not differentiate; rolled-back inputs are not in the history. A redefined `def` is the one that was defined last. As in `sky run`, a `def` that cannot lower to SIR gives a runtime error on the derivative that says why. The history is in memory only, like the rest of the session.
- Commands, only at the start of an input: `:help` (a short reminder, on stderr) and `:quit` (exit 0, like Ctrl-D). Any other line that starts with `:` is an error naming the command. There is nothing else: no history editing, no `:load` or `:save`.
- The prompt `sky> ` goes to stderr, and only when stdin is a terminal, so piped input gives clean stdout; while an input is unfinished the prompt is `...  ` (also on stderr, only for a terminal). End of input (Ctrl-D) exits 0. There is no line editing.
- The accepted inputs of a session may total at most as many bytes as a source file (16 MiB); beyond that an input is refused with an error.
- **No session saving.** A session lives only in memory: v0.1 writes no session file and reads none back, so there is no serialized format to attack (non-negotiable 3). If saving is added it must use a data-only format.

### Values and printing
- A value is a number with a dimension (exact, or carrying an uncertainty, see "Uncertainty"), an array of numbers of one dimension (a vector or a matrix, see "Arrays"), a Bool, or a string. A unit literal is converted to SI once, at the literal (see Unit values); a compound unit applies its factors one at a time, so `36 km/h` is exactly `10 m/s`. Numeric literals may contain `_` (`1_000`).
- `print(a, b, ...)` writes the values separated by single spaces and a newline; `print()` writes an empty line. A string prints as is. A user binding named `print` (or `inv`) shadows the builtin, in the checker and at run time.
- Values print in SI, as valid Sky source, so REPL output can be pasted back:
  - a dimensionless number prints bare: `0.5`;
  - a dimension that matches a unit with scale 1 in the unit table prints with it: `10 N`, `2 J`, `3 W`, `101325 Pa`, `50 Hz`;
  - any other dimension is composed from `kg`, `m`, `s`, `K` in that order, positive powers first, as `kg*m^2/s^2/K`, `m/s^2`, `m^-1`, `m^(1/2)`;
  - `10 ms` prints as `0.01 s`; a string echoes quoted and escaped (`"a\n"`).
  - `Hz` and `rad/s` share a dimension, so a value that is really an angular frequency prints as `Hz` (the known limitation in the unit table).
- Numbers print with the shortest digits that read back as the same `f64`: in plain decimal for magnitudes from 1e-4 up to (but not including) 1e16, and as `6.674e-11` outside that range. `0.1 + 0.2` prints `0.30000000000000004`, which the "Unit values" rules already accept.
- Booleans print as `true` and `false`.
- A number with an uncertainty prints as `5.31 ± 0.02 kg` (see "Uncertainty").
- `v as unit` writes a value in a chosen unit instead of SI (`print(v as km/h)` prints `90 km/h`); it is allowed only as a `print` argument or an expression statement, so the REPL echoes `sky> v as km/h` as `90 km/h`. See "Showing values in a unit".

### Arithmetic
- Numbers are IEEE `f64`, but **a Sky number is always finite**. Division by zero, an overflowing result (a finite operation whose result does not fit, such as `1e308 * 10`), a number literal too large for `f64`, and an operation with no real result (`(-8)^(1/3)`) are runtime errors on the failing expression. They never produce `inf` or `NaN`. Underflow to zero is not an error.
- Why: a scientist coming from Python expects `1/0` to stop the program (`ZeroDivisionError`), and a silent `inf` or `NaN` carried through a simulation gives a correctly-typed, correctly-united wrong answer. It also means no value is ever NaN, so `==` and the orderings are total and need no special cases.
- `^` uses repeated multiplication for an integer exponent of at most 64 in size (so `2^10` is exactly 1024) and `powf` otherwise. The result's dimension is the base's dimension raised to the constant rational exponent read from the source, as the checker computes it; a dimensionless base may take any dimensionless exponent.
- `x⁻¹` and `inv(x)` are `1/x`, with the inverse dimension.
- `and` and `or` evaluate left to right and stop at the first operand that decides the result; the operands not reached are never evaluated (`false and (1/0 > 0)` is `false`). There is no truthiness: an operand that is not a Bool is a runtime error, as it is a check error.
- Comparisons compare the SI values, and `==` between floats is exact (`3 * (100 ms) == 0.3 s` is false).
- The interpreter re-checks operand kinds and dimensions dynamically and reports a runtime error, never a panic, because the checker leaves some expressions (strings, calls it has no rule for) with an unknown type. Index and attribute writes are check errors, so a checked program never reaches them.
- Not supported yet, and a runtime error if reached: a declaration without a value (an input), attribute reads (except on the solution of a `solve`, see "Differential equations"), and the `∂` and `∇` operators except as `(∂f/∂t)(args)` (a derivative is written `derivative(f, x)(args)` or `(∂f/∂x)(args)`, see "Derivatives"). There is no transpose syntax.
- Not supported yet, and a runtime error if reached: a declaration without a value (an input), attribute reads (except on the solution of a `solve`), and the `∂` and `∇` operators (a derivative is written `derivative(f, x)(args)`, see "Derivatives").

## Building executables
`sky build` compiles a program ahead of time to a standalone native executable. It is the native engine (see "Native code") with the compiling done once, on the developer's machine, instead of at every run. "Must" is normative.

### `sky build <file>`
- **Forms.** `sky build [--emit=exe|obj] [-o <path>] [--target=<triple>] [--runtime=<path>] <file>`; the flags may also follow the file. `--emit=exe`, the default, writes a linked executable; `--emit=obj` writes the object file and stops (Mach-O on macOS, ELF on Linux). `-o` names the output; the default is the file's name without `.sky` (with `.o` for an object) in the current directory. Any other `--emit` value, a flag twice, a missing `-o` path, or no file is a usage error (exit status 2), as is a file that cannot be read.
- **Same front end as `sky run`.** The same project discovery, checking, lowering and optimization run first. A file with errors gets `sky run`'s diagnostics on stderr, exit status 1, and nothing is written. Warnings are printed by the build.
- **Which programs.** Exactly those that `--engine=native` runs. A program that does not lower to SIR or compile to machine code (an `equation`, for example) is refused as `error: cannot build: <why>` (exit status 1) and nothing is written: an executable has no other engine to fall back to, and it must not behave differently from `sky run --engine=native`. Such a program still runs with `sky run`.
- **The executable behaves like `sky run --engine=native` on the same file, byte for byte**: the same stdout, the same stderr and the same exit status (0 after a finished run, 1 after a run-time error, and 1 without a diagnostic when stdout is closed by a reader that went away). The stderr is the front end's warnings (stored at build time and printed by every run, first), then, after a run-time error, a blank line if there were warnings and the diagnostic, rendered with the path the file was built from (as given to `sky build`) and the program's source text, which the executable carries.
- **Deoptimization is supported, by embedding the SIR.** Native code stops and the run continues on the SIR interpreter when a value of unknown type is not what a declaration says (see "Native code"). Whether a program can do that depends on values at run time, so it cannot be decided when building, and refusing every program with an untyped parameter would refuse programs that run natively without ever deoptimizing. So the executable carries the SIR module (in the SIR text format, `sky check --emit-ir`) and the SIR interpreter (in the runtime library), and does what `sky run` does: it re-runs the program from the start on the interpreter, skipping the output native code already wrote. The SIR is needed anyway: a run-time error in native code is built by re-running the failing operation, which needs the operation. The module is printed and parsed back before it is compiled, so the operation indexes the code names are the ones the executable's runtime sees. The cost is size (below), not speed.
- **The runtime library.** The executable is the program's object file linked with `libsky_rt.a`, the static library of the `sky-rt` crate: the `extern "C"` functions native code calls (printing, arrays, errors, math through the interpreters' functions, the kernels and `sky-linalg`), the SIR interpreter and `sky_rt_start`, which the generated `main` calls. `sky build` looks for it in this order: `--runtime=<path>`, the environment variable `SKY_RT_LIB`, and the directory of the `sky` executable (`cargo build --workspace`, or `cargo build -p sky-rt`, puts `libsky_rt.a` next to `sky`; an installation keeps them together). A library that cannot be found is an error that says so (exit status 1). An executable needs nothing from the machine that built it except the C library; it does not need Sky.
- **Linking.** The system C compiler is the linker: `cc`, or the program named by `CC`. If none is found `sky build` says so (exit status 1) and suggests `--emit=obj`, which needs no linker: the object can be linked by hand with `libsky_rt.a` (plus `-lm -lpthread -ldl` on Linux). The linker's output is shown only when it fails.
- **Targets.** By default the executable is for the machine running `sky build`. `--target=<triple>` (`x86_64-apple-darwin`, `aarch64-unknown-linux-gnu`, ...) builds for another x86-64 or arm64 machine: an object for any of them from any host; an executable only for the host's operating system (on macOS, either architecture, which needs a `--runtime` library built for that target: `cargo build -p sky-rt --target x86_64-apple-darwin`). Code is position independent and generated for the target's baseline CPU, not for the host's extensions, so an executable runs on every machine of its architecture; the results are the same bits either way (rounding functions call the C math library where the baseline CPU has no instruction for them, and they are exact).
- **Exit status.** 0 when the output is written; 1 when the program has errors, cannot be built, or cannot be linked; 2 for a usage error or an unreadable file.
- **Size and start-up.** On macOS (Apple silicon, release build, unoptimized C linker defaults plus `-dead_strip` and `-x`) an executable is about 5.7 MB whatever the program (`print("hello")` and `examples/showcase.sky` differ by under 100 KB): almost all of it is the runtime library, which carries the SIR interpreter, `sky-linalg`, Cranelift (for compiled `fused` kernels on big arrays) and the Rust standard library; the program's own machine code and image are kilobytes. It starts in about 4 ms more than an empty process (9 ms against 5 ms for `/usr/bin/true`, spawn included), where `sky run --engine=native` on the same file takes 14 to 19 ms because it reads, checks, lowers, optimizes and compiles first. Building takes about a second for a small program, most of it the linker.
- **Tests.** `crates/sky-cli/tests/build.rs` builds every example, every IR test program and every program the checker accepts in `tests/ui/check`, plus programs from the native engine's tests (arithmetic, math functions, powers, errors after output, recursion limits, arrays, deoptimization, warnings), runs each executable and `sky run --engine=native`, and requires the same stdout, stderr and exit status. A test that needs a linker skips when there is none. With `SKY_TEST_X86_64=1` on Apple silicon it also builds for `x86_64-apple-darwin` and runs the executables under Rosetta.

## Hardware and tuning
Phase 4 makes Sky fast on the machine it runs on. Two commands and two crates (`sky-hw`, `sky-tune`) provide the groundwork. "Must" is normative.

### `sky hw`
- Prints what this machine can do: the CPU architecture and model; the SIMD features (x86: `sse2` through `avx512f`, and `fma`; Arm: `neon` always, and `sve`/`sve2` when Linux reports them); physical and logical cores, and on machines with two kinds of core (Apple Silicon, big.LITTLE) how many are performance and how many efficiency; the L1d, L2 and L3 cache sizes; total memory; the page size. It then states what Sky uses each for ("SIMD width 128 bits (NEON): kernels use 2 f64 lanes", "10 cores (6 performance): parallel kernels use 6 threads", "L2 16 MiB: matrix blocks sized to fit").
- Discovery reads only `std` and the operating system (`sysctl` on macOS, `/proc` and `/sys` on Linux), contains no `unsafe` code, and runs no shell. A fact the machine will not give is printed `unknown`, and Sky then uses a conservative default; discovery never fails and never stops a program.
- The **fingerprint** is a 64-bit hash (16 hex digits) of the architecture, CPU model, SIMD features and cache sizes. It is stable across runs and Rust versions, and deliberately ignores core counts and memory, which change with containers and load.
- Exit status 0. Any argument is a usage error (2).

### `sky tune`
- `sky tune [<kernel>]` measures every registered tunable (or those whose name contains `<kernel>`). A tunable is one kernel at one problem-size class with a small, discrete set of candidate parameter sets; the first candidate is the default. Each candidate is warmed up, timed in rotating rounds, and scored by its median, within a time budget (`--budget-ms=<n>` per tunable, 500 by default). A candidate replaces the default only if it is at least 3% faster, so measurement noise cannot change the choice. `sky tune` says what it chose and why: `unroll 16: 1.85 GB/s vs 1.19 GB/s for 4 (1.55x)`.
- The winners go to a local performance database. `sky tune --show` lists it (this machine's results first, other machines' after); `sky tune --reset` deletes it.
- Exit status: 0 on success; 1 when the database cannot be written; 2 for a usage error or a `<kernel>` that matches nothing. `sky tune` is the only command that writes the database.
- Kernels read a result with `sky_tune::lookup(kernel, size_class)`, keyed by the running machine's fingerprint; no result, no database, or a malformed entry means the built-in default. `sky_tune::tuned_note` returns the sentence `sky check --explain` cites ("tuned on this machine (2026-09-30): unroll 16, 1.55x faster than the default 4").

- What is tuned (each read once per process, clamped into a safe range, falling back to the built-in value): the GEMM cache blocks `mc`, `kc`, `nc`, the Cholesky block `nb`, each for the size classes `le64`, `le256`, `le1024`, `gt1024`; the multiply-add count from which the linear algebra kernels use threads; the element count from which a `fused` operation gets a native kernel; and the sizes from which `fused` kernels and elementwise array operations are split across threads (`sky tune` lists them by name; `sky tune linalg` and `sky tune interp` select the families). `sky check --explain` cites a tuned value where it explains the kernel choice that uses it. The LU panel width is not tunable: a panel skips a zero multiplier where the GEMM update does not, so where panels end decides the sign of some zeros.

### Guarantees
- **Tuning changes speed, never results.** A tunable must give the same answer for every candidate, and Sky's kernels do by design: their results are reproducible (in the default numerics), independent of block sizes, thread counts and SIMD width. So a database can only make a program faster or slower, never different, and deleting it (or moving to another machine) changes nothing but speed.
- **The database is data, never code.** It is a line-oriented text file (`sky-tune-db 1`, then one `result fp=... kernel=... size=... params=name:value,... ...` line per result), human-readable and editable. Nothing in it is executed, evaluated, or used as a path or command. Reading it is bounded (a regular file of at most 1 MiB, lines of at most 1024 bytes, at most 4096 results), every field is validated (a fingerprint is 16 hex digits, names are short ASCII tokens, parameter values are integers of magnitude at most 2^40), and a line that does not validate is skipped with a warning while the rest is used. A file with a missing header, or a version other than 1, is used as empty and is never overwritten or deleted by Sky. Kernels clamp what they read, and `lookup_among` accepts only a value the kernel itself offers. Writes are atomic (a temporary file, then a rename).
- **Results apply to one machine.** An entry is used only when its fingerprint equals the running machine's; entries for other machines stay in the file and are ignored.
- **Location.** `SKY_TUNE_DB` (a file path) if set; else `sky/tune.db` under `XDG_CACHE_HOME` if it is an absolute path; else `~/Library/Caches/sky/tune.db` on macOS or `~/.cache/sky/tune.db` elsewhere.
- **Not session saving.** Non-negotiable 3 forbids saved REPL sessions and requires data-only caches. The performance database is neither a session nor user data: it is written only by an explicit `sky tune`, never by `sky repl`, `sky run` or `sky check`, and holds only machine facts and timings (a fingerprint, kernel names, parameter integers, nanoseconds), never a program, a value or a history. It is a data-only cache in the sense of that rule.

## Out of scope for v0.1
Native codegen, MLIR, and GPU targets; symbolic simplification; Jacobians (the derivative of an array-valued function with respect to an array) and reverse-mode differentiation through loops (`derivative(f, x)` and `grad(f)`, including the gradient of a potential of a vector, are in, see "Derivatives"); PDEs, and equations beyond initial-value problems (second derivatives, sampled output, events, `field`); automatic precision; offset units such as `°C`; dimension arithmetic such as `N+1`; packages and plugins; notebooks.

Not yet available, though in scope for a later step: `import` statements (the project-root resolver exists, but nothing in the language calls it yet). The parser reports it as "not supported yet", precisely, and `field` as reserved.

## Non-negotiables (from Security Officer)
1. `sky check` never executes user code: no build scripts, macros, or impure compile-time evaluation.
2. Imports resolve only from the project root and the standard library, never from the working directory or environment variables.
3. Saved REPL sessions and caches use a data-only format, with no pickle-style serialization.
4. The lexer rejects bidi control characters and flags confusable identifiers.

## Imports and the project root
These rules implement non-negotiable 2. "Must" is normative.
- The project root is the nearest directory containing `sky.toml`, walking up from the checked file's directory. The walk stops after a directory containing `.git`, the user's home directory (from the passwd database), or the filesystem root. A `sky.toml` that is a symbolic link or not a regular file, or that (or its directory) is owned by another user, is refused. So is a `sky.toml` that is world-writable (the sticky bit does not matter for a file), or a root directory that is world-writable without the sticky bit: the same mode rules as the per-directory rule below, applied to the root at discovery so a root is never accepted and then refused at the first import. With no `sky.toml`, only standard-library imports resolve.
- **No `sky.toml` field may add import search paths or point resolution outside the project root.** Project imports resolve only to files under the root.
- `import a.b.c` names `<root>/a/b/c.sky`. Module names are ASCII identifiers, so a segment is never `..`, empty, or a path separator. A project module may not shadow a standard-library name.
- Resolution walks from the root using directory handles, never by rechecking a path. It opens the root, then each directory relative to the one before, then the module file relative to the last directory. It follows no symbolic links: a link anywhere below the root, even one that stays inside it, is refused.
- **Per-directory rule:** the root and every directory down to the module file's parent must be owned by the effective user and must not be world-writable unless the sticky bit is set. The module file must be a regular file owned by the effective user and must not be world-writable; the sticky bit does not matter for files. Group-writable directories and module files are allowed.
- The module is read from the handle opened during resolution and is never reopened by name. The file `sky check` is given is read the same way: from a single handle, which must be a regular file (never a FIFO or device), of at most 16 MiB (16,777,216 bytes), in UTF-8. The size limit applies both to the file's size when it is opened and to the number of bytes actually read.
- Off Unix, where handle-relative opens aren't available, any project with a `sky.toml` is refused.

## Editions
An edition is the version of the language a project is written for. It exists so Sky can grow without the meaning of old code ever changing silently. "Must" is normative.

**What an edition may change.**
- Add syntax or keywords (a word that was an identifier may become reserved in a later edition; the older edition keeps accepting it as an identifier). No edition has shipped, so `assert`, `requires` and `ensures` (Contracts) are reserved in 2026 itself.
- Add, remove, or reword diagnostics, and add new warnings or errors for programs that were already suspect.
- Turn something that was accepted into an error *only* through a diagnostic that says how to migrate.

**What an edition must never change.** The meaning of a program that compiled before: the value it computes, the units, shapes and properties it is checked to have, and the output it prints. A program accepted under edition E is accepted under every later edition with the same meaning, or is rejected by a diagnostic that names the migration. Sky never picks the newest meaning for old code because it is newer.

**Declaring it.** A project sets its edition in `sky.toml`: `edition = "2026"`. The value is a year, in a string. Only 2026 exists.
- A `sky.toml` that does not set `edition` means the first edition, 2026, and will never mean a later one.
- A file checked with no `sky.toml` (single-file mode) uses the latest edition this Sky supports. It has no history to preserve.
- The `sky repl` uses the latest edition.
- An edition newer than this Sky supports is an error, never a guess: `edition 2031 is newer than this Sky (supports 2026)`. So is a value that is not a year, or a year no edition has had.
- `sky check --explain` prints the edition it used (on stdout, before the check's result).

**The manifest format.** `sky.toml` is data-only (non-negotiable 3): no code runs, and reading it can only set the fields below. It is a strict subset of TOML, read by Sky itself with no general TOML parser:

```
manifest = { line }
line     = ws [ key ws "=" ws string ] ws [ "#" comment ] ( LF | CRLF | EOF )
key      = ( letter | digit | "_" | "-" )+
string   = '"' { character except '"', '\\', control or bidi } '"'
```

- The keys are `edition` and `numerics`. `numerics = "reproducible"` (the default) or `numerics = "relaxed"` chooses the project's numerics (see "Relaxed numerics"; `sky run --numerics=` overrides it; a value that is neither is an error, and a lone file with no manifest is reproducible). Neither can affect imports. An unknown key is an error, with a `did you mean` help when it is close to a known one (`editon`). A key that is set twice is an error, pointing at both. No key may add import search paths or point resolution outside the project root (see above); a future key would need its own edition-aware rule.
- There are no tables (`[x]`), arrays, numbers, booleans, single-quoted or multi-line strings, and no escape sequences: a backslash in a string is an error. Anything outside the grammar is an error rather than being ignored, so an older Sky never half-understands a newer manifest.
- The file is at most 64 KiB (65,536 bytes), in UTF-8. The size limit applies to the size when it is opened and to the bytes actually read.
- A bidi control character (non-negotiable 4), or any other control or invisible character (the set the diagnostic renderer escapes; tab and line breaks are whitespace), is an error anywhere in the file, comments included. A carriage return is allowed only as part of CRLF.
- Every error is reported against `sky.toml` with a line and column, in the same format as other diagnostics.
- The manifest is read from the same handle that passed the checks under "Imports and the project root", opened without following a symbolic link and without blocking; that handle must be the file discovery inspected, and must pass the owner and mode checks again. The path is never opened a second time. An invalid, oversized or unreadable manifest stops the check (exit status 1), and its edition is not guessed.

## Done means
- Golden tests in `tests/ui/` cover every example in this spec, both passing and failing cases.
- A physicist unfamiliar with Sky can write and check a small kinematics script in the REPL in under 15 minutes (target to test with a few people, not a measured result).
- The parser fuzz target and `cargo-deny` run in CI.

## Decisions made
- v0.1 is check plus interpret only, with no codegen.
- The front end is written in Rust, using the layout Eng Lead proposed.
- Uncertainty (`±`) propagation was out of v0.1 (Tom, 2026-09-29). Phase 3 adds it, first as linear propagation (see "Uncertainty").
- The license is Apache-2.0 (Tom, 2026-09-29).
- Eng Lead is cleared to create `TomOstt/sky` (Tom, 2026-09-29).
- Values are shown in a chosen unit with `v as km/h`: a keyword `as`, the loosest operator, and a display value that can only be printed or echoed (see "Showing values in a unit").
- Contracts are `assert cond`, and `requires`/`ensures` lines at the start of a function; `result` names the returned value inside `ensures`, which sees the arguments as passed. A contract failure names the values of the names in the condition, is the same message and span in both engines, and cannot be switched off; the compiler removes a check only by proving it (see "Contracts").
- Performance contracts are `cost flops <= 2 * N^3` lines in a function's header, proven or refuted by `sky check` from a static cost model over SIR, for every size from 1 up. A run-time time budget was considered and left out: time is noisy, and a contract that is sometimes false is not one (see "Performance contracts").
- `*` and `/` between arrays of one shape, and the math functions of arrays, are entry by entry; `@` is the only product that sums over an index, there is no broadcasting between arrays, and `^` on an array stays an error because `v^2` reads both as the square of each entry and as the squared length (see "Arrays: entry by entry").
- `km` is the length dimension with a scale factor, not a separate unit; a unit literal is converted to SI at the literal (see Unit values). This settles the former open question.
