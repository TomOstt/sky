# Sky v0.1: first release spec

Status: approved by Tom on 2026-09-29. Owner: Product Manager. Date: 2026-09-29.

## Goal
Prove Sky's core bet: units, tensor shapes, and matrix properties can be checked together, before anything runs, in a language that reads like Python. v0.1 is a checker plus an interpreter. It is not fast yet, and that is deliberate.

## Who it's for
Physicists, engineers, and scientific-ML developers who have shipped a unit or shape bug and would rather have the compiler catch it. The first users are us and a handful of early testers. We have no user data yet, so we will validate that this pain is real in early interviews rather than assume it.

## Why pick Sky over Julia + Unitful + ModelingToolkit
Julia checks units and shapes when code is compiled for specific argument types or when it runs, and each concern lives in a separate package. Sky checks units, symbolic shapes, and matrix properties in one static pass over the whole program, with a single set of error messages, before any data exists. v0.1 will not compete with Julia on speed or ecosystem, so the pitch for this release is correctness only.

## In scope
- Syntax: indentation-based, Python-like functions, `if`/`elif`/`else`, `while`, and bindings. Every Unicode operator (`∂`, `⁻¹`, `ħ`) has an ASCII spelling. `±` is not part of v0.1: uncertainty is out of scope, so the lexer rejects the glyph, and the ASCII `+-` is just `+` followed by unary `-`.
- Identifiers must be in Unicode NFKC form (Normalization Form KC, Unicode 18.0.0). A non-NFKC identifier, such as `e` followed by U+0301 instead of `é`, `ﬁ`, fullwidth `ｘ`, mathematical `𝑥`, or MICRO SIGN `µ`, is an error. It is never silently normalized, and keywords match only their exact ASCII spelling.
- An identifier may have at most 30 combining marks in a row (the Unicode stream-safe limit, UAX #15: characters with a nonzero canonical combining class, counted in each character's full compatibility decomposition, so U+0344 counts as two). A 31st mark in a row is an error at that mark.
- Units: SI base dimensions plus derived units (J, eV, pc, AU, rad) and physical constants. A unit may follow only a numeric literal (`10 km`). `5 meters + 20 kelvin` is a compile error.
- Shapes: `Matrix[M, N]` and `Tensor[...]` with symbolic dimension variables solved by equality. `Matrix[3,4] @ Matrix[4,8]` gives `Matrix[3,8]`, and a mismatch is a compile error.
- Matrix properties: tags such as Symmetric, PositiveDefinite, Diagonal, and Orthogonal, arranged in a subtyping lattice. `A⁻¹ @ b` with a positive-definite `A` is rewritten to a Cholesky solve, and `sky check --explain` shows the rewrite.
- Tools: `sky check`, `sky run` (tree-walking interpreter), and `sky repl`. Diagnostics include source spans, in the format defined in [`spec/diagnostics.md`](diagnostics.md).

### Operator precedence
The placement of `and`, `or`, and `not` is signed off by Eng Lead (2026-09-29). From loosest to tightest:

| level | operators | associativity |
|---|---|---|
| 0 | `a if c else b` | right (in the `else` arm); the condition `c` is an `or` expression |
| 1 | `or` | left |
| 2 | `and` | left |
| 3 | `not x` | prefix |
| 4 | `==` `!=` `<` `<=` `>` `>=` (also `≠` `≤` `≥`) | none: `a < b < c` is an error |
| 5 | `+` `-` | left |
| 6 | `*` `/` `@` | left |
| 7 | `-x` `+x` `∂x` `∇x` | prefix |
| 8 | `^` | right; its right operand may be a prefix expression (`2^-1`) |
| 9 | `A⁻¹`, `f(x)`, `M[i, j]`, `x.name` | postfix |

- `and`, `or`, and `not` are keywords. As with every keyword, they may still be used as an attribute name after `.` (`x.and`).
- `and` and `or` short-circuit: operands are evaluated left to right, and evaluation stops at the first operand that decides the result.
- `not a < b` is `not (a < b)`, `a < b and b < c` needs no parentheses, and `a and b or c` is `(a and b) or c`.
- `not` cannot be the operand of a tighter operator: `-not x`, `a < not b`, and `2^not x` are errors; write `-(not x)`.
- `&&`, `||`, and `!` are not operators. The lexer rejects `&`, `|`, and a `!` that isn't part of `!=`, and suggests `and`, `or`, and `not`.
- `-x^2` is `-(x^2)`.
- The conditional expression `a if c else b` (level 0) is looser than `or`, so `a or b if c else d` is `(a or b) if c else d`. Its `else` arm may be another conditional (`a if c else b if d else e` is `a if c else (b if d else e)`), but its condition may not: `a if b if c else d else e` needs parentheses. Anywhere a tighter operator wants an operand, a conditional needs parentheses: `(a if c else b) + 1`. Only the chosen arm is evaluated at run time. The checker types every part.

#### Booleans and conditions
Signed off by Eng Lead (2026-09-29).
- `true` and `false` are the Bool literals. They are keywords, so they can't be assigned to, but they may be attribute names after `.`. A unit may not follow them (`true m` is a parse error). `True` and `False` are ordinary names.
- The operands of `and`, `or`, and `not` must be `Bool` of shape `()` (a scalar), and the result is `Bool`. The same rule applies to the conditions of `if`, `while`, and conditional expressions.
- v0.1 has no truthiness. `0 m`, empty containers, and tensors are never implicitly true or false.
- A non-Bool or non-scalar operand is a checker error on that operand's span. For a scalar quantity, the help suggests a comparison such as `x != 0 m`. For a tensor, the help says that a condition must be a single `Bool` (shape `()`).
- At run time, `and` and `or` evaluate left to right and stop early. The checker still types every operand, so `true or (3 m + 2 s)` is a check error.

### Statements and assignment
The simple statement forms the parser accepts (a statement ends at a newline; blocks are in "Blocks and control flow" below):

```text
statement   := expr
             | target "=" expr
             | target compound_op expr
             | NAME ":" type [ "=" expr ]
target      := NAME
             | postfix "[" index_item ( "," index_item )* [ "," ] "]"
             | postfix "." ( NAME | KEYWORD )
compound_op := "+=" | "-=" | "*=" | "/=" | "^=" | "@="
index_item  := expr | [ expr ] ":" [ expr ]
```

- `x op= e` rebinds `x` to `x op e`, evaluating the target once; the result must have `x`'s declared type (unit, shape, tags) or it is a check error. `+=`, `-=`, `*=`, `/=`, `^=`, `@=` stand for `+`, `-`, `*`, `/`, `^`, `@`. There is no compound form for comparisons or `and`/`or`, and `**=` is an error (Sky writes powers as `^`, so use `^=`).
- Only a name can be annotated: `a.b: T = 1` and `A[0]: T = 1` are parse errors.
- Any other target is a parse error on the target: `f(x) = 1`, `(x) = 1`, `1 = x`, `a + b += 1`, and `true = 1`.
- Assignments don't chain: `a = b = c` and `x += y += z` are parse errors.
- Slices select a range along one axis: `A[0, :]` is row 0, `A[1:3]` is rows 1 and 2, and `A[:n, 2:]` leaves out a bound. A slice has no step: `A[1:2:3]` is a parse error. The same index items are allowed when reading and as a target.
- **The parser accepts index and attribute targets, but the v0.1 checker rejects writes through them.** Index writes (`A[i, j] = x`, `A[0, :] = v`) are check errors: that is the v0.1 checker's behaviour while array immutability is pending Tom's confirmation (see Open questions), not a settled language rule. Attribute writes (`a.b = x`, `x.true = 1`) are check errors too, until there is something whose attributes can be assigned.

### Blocks and control flow
Python-style blocks. The tokens (`Indent`, `Dedent`) come from the lexer's indentation rules; this section is the grammar on top of them and what the checker does with it.

```text
statement   := simple_stmt | if_stmt | while_stmt | def_stmt
simple_stmt := (the forms in "Statements and assignment")
             | "return" [ expr ]
             | "pass" | "break" | "continue"
if_stmt     := "if" expr ":" block { "elif" expr ":" block } [ "else" ":" block ]
while_stmt  := "while" expr ":" block
def_stmt    := "def" NAME "(" [ param { "," param } [ "," ] ] ")" [ "->" type ] ":" block
param       := NAME [ ":" type ]
block       := NEWLINE INDENT statement+ DEDENT
expr        := or_expr | or_expr "if" or_expr "else" expr        (level 0)
```

**Layout**
- A block is a line ending in `:`, then one or more lines indented further than the header, all at the same indentation; the first line back at the header's indentation (or the end of the file) ends it. Blocks nest. Blank lines and comment-only lines never end a block.
- **The body goes on its own indented line.** `if x: y = 1` is a parse error, with the help "put the body on its own indented line". Python allows it; Sky doesn't. With one canonical layout, spans, diffs and error recovery stay simple, a statement has one way to be written, and the `:` of a header can't be mistaken for the `:` of an annotation (`y: Matrix[3, 3] = ...`). The parser still reads the statement after the `:` as the body, so one mistake gives one error.
- **An empty block is an error**, with the help "use `pass`": `pass` is the statement that does nothing.
- `elif` and `else` must follow the block of an `if`/`elif` at the same indentation. `else if` is an error ("write `elif`"), and so is an `else` or `elif` with no `if` before it.
- Blocks count toward the nesting limit (256 levels) together with expressions: a block is one level, like a parenthesis. 257 nested `if`s are one clean error ("blocks are nested too deeply"), never a stack overflow, and the rest of that block is skipped.
- Not supported yet, each a precise error: `for` loops (there are no iterable values), `import` statements (there is no module loader wired into the language yet), and default parameter values (`def f(x=1)`). `equation`, `solve`, and `field` are reserved for a future version.
- A bad line does not desynchronize the blocks around it. After an error the parser resumes at the next line; a block header with an error still has its body read (and its errors reported), so the `Dedent` that ends the body is consumed by the right block.

**Conditions**
- The condition of `if`, `elif`, `while`, and of a conditional expression must be a `Bool` of shape `()` (see "Booleans and conditions": no truthiness). The diagnostic and its help are those of `and`/`or`/`not` operands, on the condition's span: "compare it instead, e.g. `x != 0 m`".
- Both arms of `a if c else b` must have the same dimension and shape, and the tags are joined (only the tags both arms guarantee survive). Otherwise it is an error on the `else` arm, with the `if` arm as a secondary label. Shapes are compared after substituting solved size variables; the check never unifies them (see below).

**Scoping**
- `if` and `while` bodies share the enclosing scope, as in Python. A `def` opens a new scope: its parameters and everything it assigns are local to it and disappear when the body ends.
- After an `if`, the states of the branches that can fall through are merged. A branch that ends in `return`, `break`, or `continue` (or in an `if`/`else` whose branches all do) does not fall through and takes no part. An `if` without `else` counts "no branch ran" as one more state.
  - A name bound in every state with the same type keeps that type. "Same" is the same dimension and shape; tags are joined.
  - A name bound in every state with different types is an error at the later binding: "`x` is a length here but a time in the other branch", with the earlier binding as a secondary label.
  - A name bound in only some states is *maybe-defined*: using it afterwards is an error, "`x` may be undefined here", with a secondary label at a binding and the help "assign it before the `if`". It is reported once per name.
- A `while` loop's body is checked once, from the state before the loop. What follows the loop merges every way out: the condition failing (before the first iteration, or after the body or a `continue`) and each `break`. A loop whose condition is the literal `true` can only be left by `break`. A name bound only inside the body is maybe-defined afterwards ("assign it before the loop"), and a name the body rebinds with a different dimension or shape than it had on entry is a conflict, as above.
- `break` and `continue` are errors outside a `while` of the same function (a `def` inside a loop does not inherit it). `return` is an error outside a `def`.

**Shape variables across branches and functions**
- Shape variables are solved by one constraint set for the whole module, and scopes never snapshot it. A constraint learned in a branch stays afterwards: a size variable names one size for the module, so `N = 3` learned in one branch is a fact about `N`, not about that path.
- Merges never unify. Two branches that leave a name with different shapes (after substituting solved variables) are a conflict, not a new constraint that neither branch wrote.
- A `def`'s size variables are its own: `N` in its annotations is not the module's `N`. After the body is checked, the variables its signature still leaves open are generic, and each call gets fresh copies, so `def apply(A: Matrix[N, N], b: Vector[N]) -> Vector[N]` can be called with size 3 and then size 4. A body that pins a variable (returning a `Vector[N]` where `Vector[3]` is declared) makes the function specific to that size.

**Functions**
- A parameter with an annotation gets the shape the annotation states. Until annotations can state units, an annotated parameter is dimensionless (the convention of a binding annotation without a value); leave a parameter unannotated to accept any unit. An unannotated parameter is unknown inside the body: nothing is checked against it and there is no error (Python-like). Duplicate parameter names are an error.
- The return type is the declared `-> T` when there is one: every `return` must have a value of that shape, and the dimension is the one the returned values agree on. Without `-> T`, the type is inferred from the `return`s, which must all give the same type (dimension and shape, tags joined), or it is an error at the later one. Mixing `return value` with a bare `return` is an error. A function that returns a value on some path but can finish without returning on another is an error at its name ("can finish without returning a value"). A function with no `return value` at all returns nothing, and a call to it is unknown.
- A call checks arity ("`f` takes 2 arguments, found 3") and each argument against its annotated parameter (shape, then dimension), and has the function's return type. Calling something that is not a function is an error. A call whose return type is unknown (unannotated parameters flowing into it) is unknown, and an unknown value is never an error by itself.
- A function's own name is in scope in its body (recursion). A recursive call is checked for arity and annotated arguments, and its result is unknown.
- **Names in a body.** A body is checked where it is defined, against the names bound so far. (Python looks names up at call time; Sky checks them at definition time, so a function that calls a helper needs the helper defined above it. The error says so: "a function body sees only names defined above its `def`".) Assigning to a name inside a function binds a new local and never changes an outer name. `x += 1` on a name that belongs to an enclosing scope is an error (Python fails it at run time with `UnboundLocalError`), with the help to bind a new name.
- A user function named `inv` shadows the built-in `inv(x)`; without one, `inv(x)` is `x⁻¹` as before.
- The checker never runs user code: bodies are typed, not executed (Security non-negotiable 1).

### Unit literals
Signed off by Eng Lead (2026-09-29). A unit literal is a numeric literal followed by a unit. `~` below means the two tokens touch, with no whitespace between them.

```text
unit_literal := NUMBER unit                  (whitespace required between NUMBER and unit)
unit         := factor ( ~("*" | "/")~ factor )*
factor       := NAME ( ~"^"~ exponent )?
exponent     := [ "-"~ ] INT
              | "("~ [ "-"~ ] INT ~"/"~ INT ~")"
```

- A unit may follow only a numeric literal, separated from it by whitespace (`10km` is rejected by the lexer: "put a space before the unit"). Unit names are ordinary names; a name is a unit only when it directly follows a number.
- `*`, `/`, and `^` are part of the unit only when there is no whitespace on either side. A spaced `*` or `/` is an ordinary operator on the quantity. A `^` right after a unit with whitespace on either side (`10 m ^2`, `10 m^ 2`, `10 m ^ 2`) is a parse error: write `10 m^2` for a power of the unit or `(10 m)^2` for a power of the quantity. For `*` and `/` the spacing never changes the value, because `(10 km)/h` equals `10 km/h`. For `^` it does (10 m² vs 100 m²) and the dimension is the same, so the checker couldn't catch the difference.
- Compound units use `*`, never juxtaposition. `*` and `/` group left to right, and `^` binds tighter.
- An exponent is a signed integer or a parenthesized rational. The denominator must not be zero. The numerator must fit in a signed 64-bit integer and the denominator in an unsigned 64-bit integer.

Examples: `10 km`, `9.8 m/s^2`, `kg*m/s^2`, `3 s^-2`, `m^(1/2)`, `m^(-3/2)`.

Counter-examples:
- `10 km / 30 min` is `(10 km) / (30 min)`, and `10 m / t` is `(10 m) / t`: spaced `/` divides the quantity.
- `5 kg m` is a parse error; write `5 kg*m`.
- `x km` is a parse error, because a unit must follow a numeric literal; write `x * km`.
- `10 km` written as `10km` is a lexer error.
- `10 m/2`, `3 s^x`, and `1 m^(1/0)` are parse errors.
- `10 m ^2`, `10 m^ 2`, and `10 m ^ 2` are parse errors (ambiguous `^` after a unit); write `10 m^2` or `(10 m)^2`.

### Unit values
- Types carry dimensions only. `km` and `m` are both the length dimension; there is no separate type per unit.
- Each unit has an `f64` factor to the coherent SI unit of its dimension (`km` is 1000, `min` is 60). The unit table in `sky-units` is the only place these factors live.
- A unit literal is converted to SI once, at the literal: `10 ms` is the value `0.01` with dimension time. After that no value remembers its unit, so `1 km + 1 m` is length plus length (the value `1001`), and there is no rule for mixing scales.
- A converted value is an ordinary `f64`, so arithmetic on it rounds like any float. `100 ms` is stored as `0.1`, and `3 * (100 ms)` is `0.30000000000000004`, so `3 * (100 ms) == 0.3 s` is false. Compare quantities with a tolerance, as with any float.
- v0.1 prints values in SI units: `10 ms` prints as `0.01 s`. Printing in a chosen unit such as `km` or `ms` is a later display feature.
- Offset units such as `°C` and `°F` (a unit that needs an added offset, not just a factor) are out of scope for v0.1. Temperature is written in `K`.

### Matrix tags
- PositiveDefinite and Diagonal each imply Symmetric, so a PositiveDefinite or Diagonal matrix can be used where a Symmetric one is expected.
- This holds only because every element of a v0.1 matrix has the same unit. Once matrices can mix element units, whether a matrix is symmetric will depend on its units as well as its values, and this rule will need revisiting.

## Out of scope for v0.1
Native codegen, MLIR, and GPU targets; symbolic simplification and autodiff; PDE and equation solving; automatic solver selection beyond the one rewrite above; automatic precision; uncertainty (`±`) propagation; offset units such as `°C`; printing values in non-SI units; dimension arithmetic such as `N+1`; packages and plugins; notebooks.

Not yet available, though in scope for a later step: `for` loops (there are no iterable values yet) and `import` statements (the project-root resolver exists, but nothing in the language calls it yet). The parser reports both as "not supported yet", precisely, and `equation`, `solve`, and `field` as reserved.

## Non-negotiables (from Security Officer)
1. `sky check` never executes user code: no build scripts, macros, or impure compile-time evaluation.
2. Imports resolve only from the project root and the standard library, never from the working directory or environment variables.
3. Saved REPL sessions and caches use a data-only format, with no pickle-style serialization.
4. The lexer rejects bidi control characters and flags confusable identifiers.

## Imports and the project root
These rules implement non-negotiable 2. "Must" is normative.
- The project root is the nearest directory containing `sky.toml`, walking up from the checked file's directory. The walk stops after a directory containing `.git`, the user's home directory (from the passwd database), or the filesystem root. A `sky.toml` that is a symbolic link or not a regular file, or that (or its directory) is owned by another user, is refused. With no `sky.toml`, only standard-library imports resolve.
- **No `sky.toml` field may add import search paths or point resolution outside the project root.** Project imports resolve only to files under the root.
- `import a.b.c` names `<root>/a/b/c.sky`. Module names are ASCII identifiers, so a segment is never `..`, empty, or a path separator. A project module may not shadow a standard-library name.
- Resolution walks from the root using directory handles, never by rechecking a path. It opens the root, then each directory relative to the one before, then the module file relative to the last directory. It follows no symbolic links: a link anywhere below the root, even one that stays inside it, is refused.
- **Per-directory rule:** the root and every directory down to the module file's parent must be owned by the effective user and must not be world-writable unless the sticky bit is set. The module file must be a regular file owned by the effective user and must not be world-writable; the sticky bit does not matter for files. Group-writable directories and module files are allowed.
- The module is read from the handle opened during resolution and is never reopened by name. The file `sky check` is given is read the same way: from a single handle, which must be a regular file (never a FIFO or device), of at most 16 MiB (16,777,216 bytes), in UTF-8. The size limit applies both to the file's size when it is opened and to the number of bytes actually read.
- Off Unix, where handle-relative opens aren't available, any project with a `sky.toml` is refused.

## Done means
- Golden tests in `tests/ui/` cover every example in this spec, both passing and failing cases.
- A physicist unfamiliar with Sky can write and check a small kinematics script in the REPL in under 15 minutes (target to test with a few people, not a measured result).
- The parser fuzz target and `cargo-deny` run in CI.

## Decisions made
- v0.1 is check plus interpret only, with no codegen.
- The front end is written in Rust, using the layout Eng Lead proposed.
- Uncertainty (`±`) propagation is out of v0.1 (Tom, 2026-09-29).
- The license is Apache-2.0 (Tom, 2026-09-29).
- Eng Lead is cleared to create `TomOstt/sky` (Tom, 2026-09-29).
- `km` is the length dimension with a scale factor, not a separate unit; a unit literal is converted to SI at the literal (see Unit values). This settles the former open question.

## Open questions
- Are arrays immutable in v0.1 (pending Tom's confirmation)? The spec assumes they are: the parser accepts index and element writes (`A[i, j] = x`, `A[0, :] = v`, `A[i, j] += 1`), and the checker rejects them.
